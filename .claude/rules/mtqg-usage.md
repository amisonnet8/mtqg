# mtqg自身の使い方（段階4から）

段階4（`PLAN.md`「開発の段階」）から、mtqg自身の開発過程を`.mtqg/`に記録する。ここでの`mtqg`は**mainから入れた安定版のバイナリ**（`go install ./cmd/mtqg`。ルート直下の開発中のビルド`./mtqg`とは別）。壊れた実装で自分自身の記録を壊さないため（distribution.md）。mainがマージで進むたびに、`go install ./cmd/mtqg`で入れ直す。

## 記録者

`.claude/settings.json`の`env`に`MTQG_AUTHOR_KIND=ai`・`MTQG_AUTHOR_NAME=claude-code`を設定済み（段階4a、`mtqg init --agent claude-code`で配線・2026-09-25）。コマンドの前に明示しなくても、このリポジトリでのmtqgコマンドは記録者`ai`/`claude-code`になる。人間が記録するときだけ、`.claude/settings.json`の値を上書きするよう明示して呼ぶ（例：`MTQG_AUTHOR_KIND=human MTQG_AUTHOR_NAME=amisonnet8 mtqg r add "..."`）。

## 何をどの種類で記録するか

qsoku側の運用（qsokuリポジトリ`.claude/rules/mtqg.md`）と同じ考え方。

| 種類 | 例 |
|---|---|
| `m add`（memo） | 実装しながらの気づき、後で見返したい観察。**不具合はここに書かない**（下の`b add`を見る） |
| `t add`（todo） | やること。**着手前に立てる**（「後でまとめて」にしない。小さな作業でもよい）。**終わったら間を置かず`t done`にする**（開いたままにしない。2026-09-25、段階4aの完了後もtodoが開いたままになっていたのを人間の指摘で気づいた） |
| `q add`（question） | 判断に迷って人間に確認したいこと。**設計や実装に関わる質問は、聞き方（チャットでの一言、`AskUserQuestion`、プランモード中の確認など）を問わず必ず`q add`で記録する。** `AskUserQuestion`で人間に聞いたときは、その場で質問と回答を`q add <id> <回答>`まで記録する（qsokuの報告「対話中のQ&Aが自動で残らない」への対応。段階4ではフックが自動記録しないため、AIが自分で書く）。**プランモード中は特に忘れやすい**（2026-09-25、段階4bのMCP実装方針・依存ライブラリ選定の確認をプランモードで`AskUserQuestion`を使って行ったが、その場で記録せず、後から人間の指摘で気づいて記録した。プランは`ExitPlanMode`の承認だけで満足せず、承認された論点をその場で`q add`する） |
| `b add`（bug） | 見つけた不具合とそのやり取り。**判定基準：「本来動くべきものが動いていなかった」「仕様と実装がずれていた」はbug、単なる気づき・設計判断はmemo。** その場で直したものも含めて記録する（qsokuの報告「もう直したから記録は軽くていい、という判断バイアス」への対応。**「直したから」は判定基準に入らない**）。**先にmemoとして書いてしまったと後から気づいたら、`b add`で改めてbugとして記録し直す**（qsokuの報告「memoとbugの使い分けをAIが自分では一貫させられなかった」への対応。2026-09-25、対策は文書・ルールの強化に留めると人間と確認した — 機械的な後押し（フック等）は作らない） |
| `g add`（glossary） | 用語の合意 |
| `r add`（rule） | 読めばそのまま従える決まり事（`docs/design/history.md`2026-09-25の線引きに従う） |

## 作業を始めるとき

- `mtqg context`を読む。段階4以降、このリポジトリの現在地の一次情報は`.mtqg/`の記録であり、`PLAN.md`はその要約・区切りの記録に役割を絞る（`PLAN.md`は引き続き置く。qsokuと違い、mtqg自身は段階1〜3の経緯を`PLAN.md`と`docs/design/`にすでに大量に持つため）

## こまめに記録する

**`mtqg context`だけで、このリポジトリの現状と次にやることが分かる状態を保つ。** `PLAN.md`を読まないと現状が追えない、という状態にしない——mtqg自身がまさにそのためのツールであり、自分の開発過程でそれを体現できていなければ説得力が無い（2026-09-25、人間からの指摘。`PLAN.md`より`mtqg`を見たほうが現状・今後が分かるようにしたい、という要望）。

- **todoは着手前に立て、終わったらすぐ`t done`にする。** まとめて書く・まとめて閉じる、をしない。開いたままのtodoは「今も残っている作業」として信用されるので、終わったのに開いたままだと現状を誤らせる
- **区切り（1つの変更、1つの決定、1つの確認が付いたところ）ごとに、その場で`m add`する。** セッションの終わりにまとめて数件書くのではなく、都度書く（`q add`をその場で書くのと同じ考え方）
- **人間に委ねる判断（今後どちらに進むか等）は、`PLAN.md`の「次」に書くだけでなく`q add`でも開けておく。** `PLAN.md`の記述だけでは`mtqg context`の「Open questions」に出ず、mtqgを見るだけでは気づけない
- 何を記録すべきか迷ったら、**「これを書かずにセッションが終わったら、次のセッション（または人間）は`mtqg context`だけで気づけるか」**で判断する

## その他

- `.mtqg/.local/`はコミットされない
- `.mtqg/`の中のファイルを直接編集しない（すべてmtqgのコマンド経由）
- mtqgはgitに対して読むだけ
