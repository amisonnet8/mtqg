# mtqg 設計：目的と原則

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 1. 何のためのツールか

### 1.1 問題：成果物に痕跡を残さない過程は失われる

gitは、ソースコード、ドキュメント、データなどの**最終成果物**を管理している。成果物がどう変わってきたかという**成果物の過程**も、コミットの履歴としてgitにすでに管理されている。

しかし、過程のすべてが成果物に痕跡を残すわけではない。

- 聞かれた質問と、その答え
- 検討したが採用しなかった案と、その理由
- まだ手をつけていないToDo
- 地味な記録、経緯、申し送り
- 用語の意味についての合意

これらは差分を生まないので、どれだけ丁寧にgitを使っても履歴に入らない。人もAIも日々生み出しているのに、人間の記憶や個人メモ、チャットツールのログ、各AIツールが個別に持つメモリ機能（Claude Codeの`Session Memory`/`/remember`など）といった、**それぞれの主体に閉じた場所**に置かれ、やがて失われる。

その結果、こうした過程は3つの軸で途切れる。

| 軸 | 途切れ方 |
|---|---|
| **時間** | セッションや日をまたぐと消える。同じ質問が繰り返され、却下した案が再提案される |
| **主体** | 人間↔AI、AI↔AI（別ツール・別セッション）、人間↔人間で受け渡せない |
| **場所** | 端末やブランチ、worktreeをまたいで共有できない |

### 1.2 mtqgの役割

**mtqgは、gitに残らない過程を、データとして残す作業をアシストする道具である。**

- 一度テキストとしてリポジトリに置かれれば、版の管理・共有・合流はgitが行い、閲覧はGitHub等の差分画面やエディタ、AIが行える
- mtqgにしかできないのは、「残らなかったはずのものを、摩擦なく残させる」部分
- 内部の仕組みと、使う人から見た姿は、意図的に分けて考える（2章）

#### 出発点：Google KeepでClaudeへの依頼を管理していた

出発点は、仕様駆動開発をAIエージェントと進める中で最も欲しいと感じたこと。

具体的には、Google KeepでToDoを管理し、「これとこれをClaudeに頼む」「これは終わった」と書いていた。このときClaudeはKeepのメモを一切見ておらず、**人間がKeepとClaudeの間に立って、依頼を伝え、終わったことを確認し、チェックを付ける中継役を手作業でしていた**。Keepのメモは個人のアカウントに閉じていて、リポジトリにも、Claudeにも、他の人にも届かない。1.1の問題の、最も身近な実例である。

mtqgは、この使い慣れた体験を残しつつ、置き場所をリポジトリの中に移す。同じ記録を、人間はKeep風のToDo画面（11.4）で、AIは`context`（9章）で見るため、中継役が要らなくなる。AIが自分で「終わった」を記録すれば、人間の画面のカードにチェックが付く。

> 理想は、Keepで管理していたときと体験はほぼ同じで、記録がもっと細かく、リポジトリに残ること。

- 体験がほぼ同じ → 導入の摩擦がない。全PJに入れられる条件
- 記録がもっと細かく → 1.4の粒度の問題への答え
- リポジトリに残る → 共有が機械的に成立すること（1.4）への答え

この理想は、サンプルPJでの評価の物差しにもなる（12.3）。「Keepに手で書いていたときより楽になったか」「Keepに戻りたくならないか」を、自分の体験として判断する。

なお、この出発点はmtqgが解く一般的な問題が最も鋭く現れた一例にすぎず、mtqgは特定のAIツール専用にはしない。

### 1.3 対象範囲

- gitで成果物を管理しているプロジェクト全般（ソフトウェア開発、仕様書・ドキュメント作成、執筆、研究、設計など）
- 記録者は人間・任意のAIエージェントのどちらでもよい
- 特定のエディタ・AIツール・ホスティングサービスに依存しない

### 1.4 既存の手段との違い

想定される反論：

- 「うちはJiraでちゃんとやっている」
- 「Gitで過程も記録している（コミットメッセージ、PR、ADRなど）」

**主張：どの道具も手法も、それ自体の中では整っている。しかし、成果物に対するgitほどには、成果物に残らない過程をうまく扱えていない。**

既存ツールや手法を否定するのではなく、「gitが成果物で到達した水準に、成果物に残らない過程はまだ到達していない」という立場をとる。

#### 「共有したつもり」と「共有が成立している」の違い

Jiraに書く、コミットメッセージに書く、Wikiに残す。どれも書き手の側では「共有した」と言える状態になる。しかし、それが受け手に届いて使われるかは、受け手がその存在を知っているか、探しに行くか、権限を持っているか、読み解けるか、といった**人の側の努力や運用に委ねられている**。

gitの共有はそうなっていない。cloneすれば必ず全部ついてくる。pullすれば必ず最新になる。並行して変更しても合流のルールが決まっている。誰かの善意や記憶に頼らず、**仕組みとして機械的に共有が成立している**。

> 既存の手段は、書き手が「共有した」と言える状態は作れるが、受け手の手元で過程が機械的に再現される状態は作れていない。mtqgは、成果物に残らない過程をリポジトリの中にデータとして置くことで、その共有をgitの仕組みに乗せる。

#### 個別の手段について

- **Jira等の課題管理ツール**：ツール単体では状態管理もAPIもあり機械的。機械的でないのは**ツールと成果物（リポジトリ）の間**。cloneやforkしても経緯はついてこない、ブランチと連動しない、オフラインで扱えない、権限のない外部協力者には見えない、ツール移行やプロジェクト移管で経緯が失われやすい。
- **gitの履歴・コミットメッセージ**：成果物の過程は確かに記録されている。変更ごとの「なぜ」を残すにも優れている。ただし、差分を生まないもの（未完了のToDo、答えの出ていない質問、却下した案、用語の合意）には置き場所がない。
- **PRのレビュー議論**：gitではなくホスティングサービス側にあり、Jiraと同じく成果物から切り離されている。
- **ADR（Architecture Decision Records）等のリポジトリ内ドキュメント**：成果物と一緒に流通するので、上の批判は当たらない。違いは、mtqgが状態や構造を持つこと、並行して書いてもマージで壊れにくいこと、記録の摩擦が小さいこと。ADRは重要な決定だけを残す道具で、そこに至る細かなやり取りは残らない。

#### 粒度の問題

AIと作業していると、数分おきに細かい質問・回答・判断が生まれる。「AIに聞かれて、こう答えた」ことをJiraのチケットにする人はいない。**この粒度の過程は、Jiraを使っていてもそこには載らず**、結局は個人の記憶やAIのメモリに流れていく。「ちゃんとやっている」チームでも起きていること。

#### 位置づけと、認めておく弱点

- mtqgは既存ツールを**置き換えるのではなく補完する**。「Jiraにもgitの履歴にも載らない粒度の過程を、成果物と同じ場所に置く」
- mtqgもリポジトリ単位で閉じている。複数リポジトリにまたがる経緯や、gitを使わない関係者（PMや顧客）との共有は苦手。これは当面、役割の外として扱う（2.7）

### 1.5 「gitほどうまくいく」の物差し：何をgitに任せ、何をmtqgがやるか

gitが成果物で実現している性質を分解すると、**その多くはmtqgが自分で実現する必要がない**。記録をリポジトリ内のテキストとして置けば、gitがそのまま実現してくれる。

| gitが成果物で実現していること | 誰がやるか | mtqgでの対応 |
|---|---|---|
| cloneすれば全部ついてくる | **git** | `.mtqg/`を普通のファイルとして置くだけ（4.1） |
| 履歴を遡れる・戻せる | **git** | 何もしない |
| 並行作業を合流させる | **git** | mtqgは衝突しにくい形で追記するだけ（7.4） |
| 差分を見られる | **git** | 差分で読みやすい形で書き出すだけ（7.2） |
| 中央サーバーなしで動く | mtqg | 記録元IDによるID生成（6章） |
| 誰が見ても同じ状態に見える | mtqg | 追記された事実から、決まった規則で表示を作る（7.5） |
| 人間でもどのツールでも読める | mtqg | データ形式を公開された契約にする（5.3） |
| どの環境にも入れられる | mtqg | 単一バイナリで配布する（10章） |

### 1.6 最大の難所：使わずに済ませられてしまう

表に載らない、gitの一番難しい性質がある。**gitは使わずに済ませる方法がない**。成果物はコミットしなければ届けられないので、面倒でも必ずgitを通る。

一方、成果物に残らない過程は、記録しなくても作業が進んでしまう。仕組みがどれだけ機械的でも、記録されなければ届かない。既存の手段が「共有したつもり」に留まっている原因の半分はここにある。

**だからmtqgの中心は「記録を作るアシスト」にある**（1.2）。

1. **登録の摩擦を最小にする**（5.4）
2. **AIエージェントには、仕組みで記録を作業の流れの一部にする**：AIが自分で記録できる入口（MCP）と、読み込み・記録漏れの確認を必ず行わせる仕組み（エージェントのフック）を用意する（11.2、11.3）
3. **人間には、使いたくなる体験で越える**：人間に記録を強制することはできない。記録するときの手間や気持ちよさ、読むときの見やすさが「記録するかどうか」を左右するため、人間向けの入口はUIを豊かにする（11.4）

AIと作業するようになった今だからこそ、この問題は解ける見込みがある。これも、今この道具を作る理由の一つ。

## 2. 役割と原則

外部ツール連携などの機能を検討する中で、mtqgの役割を超えた機能（版の追跡、gitの運用への介入、履歴の解析など）が混ざりやすいことが分かった。判断がぶれないよう、役割と原則をここに固定する。

### 2.1 役割分担：版はgit、残らない過程の追記はmtqg

| | git | mtqg |
|---|---|---|
| 扱うもの | 成果物と、成果物の過程（版の履歴） | 成果物に痕跡を残さない過程 |
| すること | 版の記録、差分、ブランチ、マージ、巻き戻し、履歴の書き換え | 過程を1件ずつ追記する。その作業をアシストする |
| しないこと | 過程の意味を解釈する | 版を管理する。変化を追跡する。gitの運用に介入する |

`.mtqg/`のファイル自体の版管理も、gitに任せる。**mtqgは「過程を記録するツール」であって、「記録を版管理するツール」ではない。**

### 2.2 仕組みと使われ方を分けて考える

作る側から見たmtqgと、使う側から見たmtqgは、**意図的に異なるイメージ**にする。

これはgit自身と同じ構図である。作る側から見たgitの中身は「内容をハッシュ値で保存するだけのファイル置き場」だが、使う側はそれを意識せず、「gitが履歴を管理してくれている」と感じて使っている。仕組みは単純な保存でも、体験は管理である。

| | 作る側（仕組み） | 使う側（体験） |
|---|---|---|
| mtqgとは | 過程のデータ作成をアシストし、追記するだけ | 過程を管理してくれるツール |
| 版や履歴 | gitに任せる | 気にしない。いつでも経緯を見られる |
| 現在の状態 | 追記された事実からその場で作る表示 | 「このToDoは完了」「この質問は回答済み」という状態がある |
| 訂正・削除 | 訂正・削除の事実を追記する | 「直した」「消した」 |

### 2.3 仕組みの原則：追記するだけ

- mtqgのデータに対する操作は**追記だけ**。既存の行は書き換えない
- 状態の変更、訂正、削除も、すべて「そういう事実があった」という行の追記で表す（7.1）
- 「現在の状態」はデータとして保存せず、追記された事実から表示のたびに作る
- 版・差分・合流・巻き戻しはgitの仕事であり、mtqgは実装しない
- gitに対しては、必要な情報を**読むだけ**で、書き込みも運用への要求もしない（4.3）

### 2.4 使われ方：過程を管理してくれる

- コマンド名、表示、ドキュメントの言葉は、**使う側の体験で選ぶ**。「管理されている状態を操作している」ように見える言葉を使う
- 内部で追記に変換されていることを、利用者が知る必要はない

| 使う側がしたいこと | 見せる操作（例） | 内部で起きること |
|---|---|---|
| ToDoを完了にする | `mtqg todo done` | 状態変更の事実を追記 |
| 質問に答える | `mtqg qa answer` | 回答の事実を追記 |
| 記録を直す | `mtqg memo edit` | 訂正の事実を追記 |
| 記録を消す | `mtqg memo delete` | 削除の事実を追記し、表示から除外 |
| 今どうなっているか見る | `mtqg status`、`mtqg todo list` | 追記された事実から表示を作る |

### 2.5 隠しきれない部分は正直に伝える

完全には隠しきれない場面がある。**「消した」「直した」はずの内容が、gitの履歴には残る**こと（8章）。ここだけは仕組みがそのまま表に出るので、使う側にも明示する。

- 削除時の表示で「表示から除外しました（gitの履歴には残ります）」と伝える
- gitでも、`git rm`してもpush済みの履歴からは消えないことを利用者が知っておくべきとされているのと同じ扱い

### 2.6 判断の基準

機能を足すかどうかは、次の2つで判断する。

1. **内部の機能**：「追記するだけ、版はgitに任せる、gitは読むだけ」の原則に反しないか
2. **使う側の機能**：「残らない過程を残す作業のアシスト」になっているか。または「管理してくれている」体験に必要か

どちらにも当てはまらないものは、便利そうでも役割の外として採らない。

### 2.7 役割外として採らないもの

これまでの検討で挙がったが、上の基準により採らないもの。

| 採らないもの | 理由 | 代わりに |
|---|---|---|
| 成果物の位置の追跡（コミットハッシュや内容ハッシュでずれを追う） | 版の追跡はgitの仕事 | 記録時の位置を事実として残すだけ（5.5）。その後の変化は`git log`や`git blame`で見る |
| 論理時計（Lamportクロック）による順序付け | 分散した版の前後関係を決める、バージョン管理寄りの仕組み | タイムスタンプと記録元IDで表示の順序を決める（7.5） |
| 専用refによるブランチ横断の保存 | git運用（refspecの設定）に負荷をかける | 記録はブランチに属する（4.2） |
| コミットトレーラーの規約 | gitの運用に要求をする | 差分に記録が並ぶことで紐づく（11.5） |
| gitフックの設定・必須化 | gitの運用に介入する | 検証や通知はmtqg側で行う |
| `mtqg why`などgitの履歴を解析する機能 | `git blame`と差分で分かる | gitとGitHubの機能を使う |
| CIでのPRコメント | 共有・閲覧はgitとホスティングサービスの仕事 | PRの差分に記録が並ぶ |
| 静的HTML出力 | 閲覧はプレーンテキストとGitHub等で足りる | 必要になったら再検討 |
| Jira・GitHub Issues等からの取り込み | 残らない過程のアシストではない | 採らない |
| SQLite索引・全文検索エンジン | 読む側は必要な分だけ（5.4） | 全件走査の簡単な検索（10.3） |
| エディタでの警告表示・ファイル監視など重いLSP機能 | 記録のアシストでも管理体験の中心でもない | 記録作成と状態・過程の表示に絞る（11.4） |
| 記録者の名寄せ（同じ人の複数の名前を束ねる） | gitでも解けていない問題で、mtqgが解くものではない | プロジェクトで`user.name`の書き方を決める（5.2） |
| 代理記録のための専用の項目 | 本文に一言添えれば足りる | 慣習として運用する（5.2） |

#### ToDo管理ツールへの引き戻しに注意する

使い始めると、**ToDo管理ツールの方向に引き戻される力**が働く。todoまわりは欲しくなる機能がいくらでもあり、どれも便利そうに見える。しかし足していくとJira等の小さな再発明になり、「全PJに入れられる軽さ」も失われる。

mtqgとよくあるToDo管理ツールの違いは、**記録の読み手が自分以外にいるかどうか**にある。ToDo管理ツールは書くのも読むのも自分で、手元で完結するため自己満足に終わりやすい。mtqgの記録はリポジトリと一緒に流通し、AI、次のセッション、チームのメンバー、レビュアー、数か月後の自分に届く。todoは4つの入口の一つにすぎず（3章、5.1）、課題管理の道具ではない。

判断の問い：**それは課題を管理するための機能か、過程を残すための情報か。** 前者は採らない。

| 採らないもの | 代わりに |
|---|---|
| 優先度、期限、見積もり・工数 | 必要なら本文やmemoに書く |
| 担当者の割り当て | 誰が記録・完了したかは記録者（5.2）として事実で残る |
| カンバン・ボード表示 | 未完了の一覧（9章）で足りる |
| 通知・リマインダー | 読み込みはセッション開始時の`context`（11.3）で行う |
| 繰り返しタスク、サブタスクの階層 | 必要ならmemoで関係を書く |
| ステータスのワークフロー（レビュー中、保留など多段階の状態） | open/doneを基本にする |

課題を本格的に管理したいプロジェクトは、既存の課題管理ツールを併用すればよい。mtqgはそれを置き換えず、そこに載らない粒度の過程を補う（1.4）。

## 3. 名前

- **mtqg** = memo / todo / qa / glossary の頭文字。ディレクトリは`.mtqg/`、コマンドは`mtqg memo add ...`、`mtqg todo add ...`の形を想定。
- **並び順には意味がある：基本のmemoと、構造を持つtodo・qa・glossary**。5.1の整理では、memoが構造を持たない基本の記録で、todo（状態）・qa（ペア）・glossary（キー値対応）はそこから独自の構造を持つものとして切り出されている。名前も基本から派生の順に並べ、データモデルの考え方と一致させる。
- memoが先頭に来ることで、課題トラッカーではなく「過程」全体を扱う道具であること（1.4）が名前にも表れる。todoが先頭だと、Jira等の課題管理ツールの仲間に見えやすい。
- 経緯：tdmqa → tmqg（glossaryを独立した入り口にしたことに合わせて改名）→ mtqg（memoを基本とする順序に変更）。
- 実用面の補足：`tm`で始まるコマンドには日常的に使われるtmuxがあり、シェル補完でぶつかりやすい。`mt`始まりのほうが衝突は少ない。
- サンプルPJや開発の中で種別が増減し、名前と中身がずれる可能性はある。gitの名前が中身を表していないのと同様、そうなっても改名はしない方針でよいか、要判断。
- 公開前に、GitHubや実装言語のパッケージレジストリで同名がないか確認する。
