# mtqg 設計：データモデルとID

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 5. データモデル

### 5.1 基本方針：単一の記録＋複数の入り口

内部的には**単一の記録形式**（本文＋種別＋状態/参照等のメタデータ）に統一する。使い勝手としては、以下の4種類の入り口（サブコマンド）に分ける。

| 入り口 | 性質 |
|---|---|
| **memo** | 構造を持たない自由記述（基本の記録） |
| **todo** | 状態を持つ（open/done 等） |
| **qa** | 質問が状態（開／閉）を持ち、回答をぶら下げる。回答は「親（質問）への参照を持つmemo」で、独自のIDを持つ（CLI設計§4.1） |
| **glossary** | キーと値の対応を持つ（用語→定義） |

Gitのオブジェクトモデルと`commit`/`branch`/`tag`のような入り口の関係と同じ構造（内部データは1つ、外側の道具は複数）。

**入り口を分ける基準は「独自の構造を持つかどうか」**。決定理由・ブロッカー・次回への申し送りは、状態・ペア・キー値対応のいずれの独自構造も持たないため、memoのバリエーションとして扱う（必要ならタグで区別する）。用語集はキー値対応という独自構造を持つため、glossaryとして独立させる。

### 5.2 記録者（author）の区別

人間と様々なAIが同じ記録に書き込むため、各イベントに記録者を持たせる。

```json
"author": {"kind": "human", "name": "yamada"}
"author": {"kind": "ai", "name": "claude-code"}
```

- 「誰が書いたか」だけでなく「人間かAIか、どのエージェントか」が分かる
- 特に**qa**で効く。AIが暫定で書いた回答と、人間が確定させた回答を区別できる（回答に対する「確定」の事実を追記する形にするかは要検討）
- 利用者に毎回入力させない。人間はgitの設定（`user.name`）を読み、AIはMCP接続時にクライアントが名乗る名前を使う（11.2）

#### `author`が表すもの：その内容に責任を持つ主体

- AIが自分の判断で書いたものはAI、**人間の判断をAIが代わりに書いたものは人間**
- 代理で書いた場合は、AIが代わりに書いたことを本文に添える。**慣習として運用し、専用の項目は持たない**（2.6の基準：機能として作り込むほどのものではない）
- mtqgが自動で付けるのは接続している主体なので、代理のときは記録者を明示的に指定できる引数だけ用意する（11.2）
- 指示ファイルに一行書いて運用する（11.3）：「人間の判断を記録するときは、その人を記録者にして、AIが代わりに書いたことを本文に添える」

#### 名前の粒度と表示

- AIの名前は、MCPのクライアント名（`claude-code`）まで自動で付ける。モデル名まで残すかはサンプルPJで判断する（14章）
- **同じ人の複数の名前（`user.name`のゆらぎ）は名寄せしない**（2.7）。きちんとやりたいプロジェクトは、`user.name`の書き方を最初に決める
- **表示は名前を主にする**。記録元ID（6章）は衝突を避けるための内部の値で、同じ人が複数持つのが普通なので、通常の表示には出さない
  - 記録のID（記録元ID＋連番）は、記録を指すために必要なので控えめに表示する
  - 記録元IDは、`show`や`review`（9章）など必要な場面でだけ出す。同じ人が別のworktreeから並行して状態を変えた場合、名前だけでは何が起きたか分からないため

### 5.3 データ形式そのものを契約にする

特定のツールに依存しないため、**データ形式を文書化されたプレーンテキストとして公開**する。

- mtqgのCLIがない環境でも、人間やどのAIでも直接読める
- CLIは「形式を扱う入り口の1つ」にすぎなくなる
- `.mtqg/SCHEMA.md`のように、仕様をデータと同じ場所に置いておくと、初見のAIでも読み方が分かる
- SCHEMA.mdの元の文書は`docs/reference/`に置き、`init`・`upgrade`がバイナリに埋め込んだものを書き出す（10.8）
- SCHEMA.mdは**英語で書く**。初見のAIにも、公開後の利用者にも読めるようにするため（10.6）
- SCHEMA.mdは、`version`が宣言している形式までの仕様を書く。書き換えるのは`init`と、形式を上げるとき（`mtqg upgrade`）だけで、普段の記録では触れない（5.6）
- gitは形式の文書を本体のソース側に置き、リポジトリには番号だけを持たせている。mtqgはそれと違い、初見のAIがその場で読めることを優先して仕様をリポジトリ内に置く

### 5.4 記録作成は手厚くアシストし、読む側は必要な分だけ

mtqgの中心は「残らない過程を残す作業のアシスト」（1.2）なので、力の入れ方を非対称にする。

- **記録作成**：手厚くアシストする。操作はシンプルに、付帯情報は自動で付け、AIが自分で記録できる入口と、記録漏れを促す仕組みを用意する
- **読む側（表示・検索・振り返り）**：記録はプレーンテキストでgitに載るので、GitHubの差分、エディタ、AIがそのまま読める。mtqgは「管理してくれている」体験に必要な分だけ用意する（9章）

（旧方針「登録はシンプルに、振り返り・検索は手厚く」から変更）

### 5.5 付帯情報の自動付与

記録作成の摩擦を下げるため、次の情報は利用者が入力しなくても自動で付ける。

- 記録時刻（`ts`）、記録元ID（`origin`）、記録者（`author`）
- **端末識別子（`tty`）**：ttyのパスをハッシュ化した短い値。同じターミナルからの記録を見分けるために使う（CLI設計§4.5の`undo`）。ttyが取れない環境（MCPサーバー、CI等）では値なし
- **成果物の位置（任意）**：エディタで選択範囲から記録を作った場合などに、「このときこのファイルのこの行について書いた」という**事実**を残す

```json
"at": {"path": "docs/spec.md", "line": 42, "head": "3f9a1c0"}
```

位置は記録時の事実として残すだけで、**その後コードが変わったときの追跡はしない**（2.7）。どう変わったかは`git log -L`や`git blame`などgitに聞けばよい。`head`は「どの版を見て書いたか」という事実の補足。

### 5.6 形式のバージョン（決定）

gitの考え方（`core.repositoryformatversion`と`extensions.*`、インデックスの拡張の扱い）を参考にする。

**`.mtqg/version`：データ形式の宣言**

- `.mtqg/version`に、データ形式の番号を1つだけ書く（中身は`1`のような数字1行）
- mtqgは、**自分が知らない（より新しい）番号を見たら、読むのも書くのも拒否する**。「このリポジトリの形式は新しいので、mtqgを更新してください」と案内する。古いmtqgが新しい形式を黙って読み違えることを防ぐ
- gitの形式番号は`.git/config`にあってクローンごとだが、mtqgのデータは普通のファイルとして交渉なしに運ばれるため、**宣言はコミットされる側に置く**
- ほとんど書き換わらないファイルなので、ブランチ間の衝突はまず起きない

**形式は勝手に上げない**

- mtqgは、**リポジトリが宣言している形式で書く**。手元のmtqgが新しい形式を扱えても、宣言が古ければ古い形式で書き続ける
- 新しい版の機能のうち、形式を変えずに済むもの（表示の改善、無視されても困らないフィールドの追加など）はそのまま使える。形式の変更が必要な機能は使えず、「この機能は形式vNが必要です。`mtqg upgrade`で上げられます」と案内する
- 形式を上げるのは、**利用者が`mtqg upgrade`を明示的に実行したときだけ**。このとき`version`の番号と`SCHEMA.md`を同時に書き換える
- 理由：チームの中でmtqgのバージョンはそろっていないのが普通。1人が新しいmtqgを入れただけで形式が上がると、他の人は次のpullで読めなくなる。`upgrade`を明示的な操作にして、「全員が更新したのを確認してから上げる」判断の場を作る
- `upgrade`しても**過去の行は書き換えない**（2.3）。以降の行が新しい形式で書かれ、古い行は古い形式のまま読まれ続ける

**各行の`v`：その行の書き方**

- 各イベント行に、その行を書いたときの形式の番号（`v`）を持たせる。読み取り側は行ごとに`v`を見て読み方を決める
- **番号を上げずに済む変更と、上げる変更を分ける**（gitのインデックスで、拡張名の1文字目が大文字なら「知らなくても無視してよい」とする区別にならう）
  - **知らないフィールドは無視してよい**：フィールドの追加は、古いmtqgが無視しても意味が壊れない限り、番号を上げない
  - **意味が変わる変更は番号を上げる**：既存フィールドの意味の変更、新しい`op`の追加など、無視すると読み違える変更
- これにより、番号を上げる（＝`upgrade`が要る）頻度を抑える

**v1確定前**

この原則は、データ形式をv1として確定した後の記録に適用する。v1確定前は`version`と`v`を`0`（形式が未確定）とし、書き換えや破棄をしてよい。サンプルPJのデータは使い捨て、mtqg自身の11章の開発中の記録はv1確定時にAIがv1の形式へ変換する（12.4）。

## 6. ID設計：分散環境での衝突回避

> **追記（2026-09-19）：この章のID設計は変更された。** 記録のIDは「記録元ID＋連番」から、**UUIDv4（ハイフンなしの16進32桁）**に変わった。表示は先頭10桁、入力は前方一致、曖昧なときは候補を完全なIDで並べる。これにより、記録元ID（`origin`フィールドを含む）、カウンタ、`<git-dir>/mtqg/`はすべて廃止された。ロックと書き直しの一時ファイルは`.mtqg/.local/`（`.mtqg/.gitignore`で無視）に置く。以下は変更前の設計と、その理由の記録として残す。変更の経緯は`history.md`の2026-09-19、現在の仕様は`docs/reference/schema.md`。


### 6.1 問題

連番ID（`#3`のような）は、複数人・複数端末がオフラインで同時にエントリを追加すると衝突する。

```
Aさん(オフライン): mtqg todo add "C言語対応"     → #3
Bさん(オフライン): mtqg todo add "テスト追加"     → #3   ← 同じ番号！
```

### 6.2 解決：記録元識別子を組み込む

ID = **記録元ID + ローカル連番**

- 初回実行時にランダムな記録元IDを生成して保持する（gitには含めない）
- ホスト名は表示用の補助情報として使う（同名端末の衝突を避けるため、実体はランダムID）
- 分散システムのSnowflake ID的な発想（中央調整なしにグローバルユニークなIDを作る）

```
a7f3c2-3, b21c09-3   ← 記録元が違えば連番が被っても衝突しない
```

### 6.3 記録元IDの保持場所：worktree単位

マシン単位で保持すると、以下のケースで同じIDが使い回される危険がある。

- dotfilesの同期、VMイメージやコンテナイメージの複製
- devcontainer、CIランナー、クラウド上のエージェント実行環境

さらに、同じクローンでも**worktreeを並列に使う**と、別々のworktreeで同時に同じ連番を採番しうる。

そこで、**worktreeごとのgitディレクトリ内**（`git rev-parse --git-dir`が指す場所、コミットされない）に記録元IDと連番カウンタを保持する。

```
<git-dir>/mtqg/origin-id     # 例: a7f3c2
<git-dir>/mtqg/counter       # 例: 3
```

- 新しいクローン・新しいworktreeでは自動的に新しい記録元IDになる
- 連番をイベントから再計算する方式は採らない。ブランチを切り替えると他ブランチのイベントが見えず、同じ番号を再採番して後のマージで衝突するため
- カウンタが失われた場合は、再計算せず**新しい記録元IDを発行し直す**（名前空間ごと変えれば衝突しない）

### 6.4 ローカルの状態の置き場所と中身（決定）

`<git-dir>`は、`git rev-parse --git-dir`が返す場所。mtqgは場所を推測せず、gitに聞くだけにする（10.2）。

| リポジトリの形 | `<git-dir>` | mtqgの状態 |
|---|---|---|
| 普通のクローン | `<ルート>/.git/` | `.git/mtqg/` |
| 追加したworktree | `<元のルート>/.git/worktrees/<名前>/`（worktree側の`.git`はファイル） | `.git/worktrees/<名前>/mtqg/` |
| サブモジュール | `<親>/.git/modules/<名前>/` | `.git/modules/<名前>/mtqg/` |

```
<git-dir>/mtqg/
  origin-id     記録元ID（16進6桁、例: a7f3c2）
  counter       最後に発行した連番（例: 19）
  lock          書き込みの排他用（10.4）
  sessions/     フックのセッション記録（段階4以降・11章）
```

**ここに置く理由**

- **コミットも共有もされない**：`.git/`の中はgitの管理対象にならない。記録元IDは「このworktreeだけのもの」でなければならず、`.mtqg/`のようにコミットされる場所に置くと、cloneした全員が同じIDを持ってしまう
- **単位が合う**：gitが`<git-dir>`をworktree単位で用意しているので、mtqgがworktreeを見分ける仕組みを作らずに済む
- **寿命が合う**：`git worktree remove`でworktreeを消せば、gitが`<git-dir>`ごと消す。新しくcloneすれば空から始まる。「新しいクローン・worktreeでは新しい記録元ID」（6.3）が何もしなくても成り立つ
- mtqgはgitを前提にしている（4.4）ので、gitの領域を使うことに無理がない
- `.git/`の中にツールが自分用のディレクトリを置くのは一般的（Git LFSの`.git/lfs/`、gitの`rerere`の`.git/rr-cache/`など）。4.3の「gitへの書き込みを行わない」は、コミット・設定・フックなど**gitの動きを変える書き込み**をしないという意味で、これとは矛盾しない
- 全worktreeで共有される`.git/`本体（`git rev-parse --git-common-dir`）は使わない

**記録元IDの発行**

- ランダムな16進6桁（約1,700万通り）
- 発行時に、`journal.jsonl`と`archive/`に**すでに現れる記録元IDと重なっていないか確認し、重なっていたら作り直す**。1ファイルにしたことで全記録元のIDが同じファイルに並ぶため。共有済みの履歴とは確実に重ならず、残るのは「まだマージされていない別ブランチで同時に生まれた記録元と一致する」場合だけで、実用上は無視できる
- 入力はIDの前方一致で短縮できる（CLI設計§6章）ので、長さは入力の手間に響かない。偶然の一致が実際に問題になったら桁数を増やす（形式の変更として5.6で扱う）

**カウンタ**

- 中身は「最後に発行した番号」。次の番号はそれに1を足したもの
- 書き換えは、一時ファイルに書いてから置き換える（書きかけで壊れない）
- **カウンタを先に進め、その後で`journal.jsonl`に追記する**。追記の前に落ちても番号が1つ飛ぶだけで、同じ番号を二度使うことはない。IDは詰まっている必要がないので、飛びは実害がない

**失われたとき・壊れたとき**

- `origin-id`も`counter`もない：新しいクローンかworktree。新しい記録元IDを発行し、カウンタを0から始める
- どちらか片方がない、または中身が読めない：再計算せず、**新しい記録元IDを発行し直す**（6.3）
- どの場合も「記録元IDを新しくしました: <ID>」と表示し、気づけるようにする
