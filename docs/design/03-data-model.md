# mtqg 設計：データモデルとID

> 今の設計と、その判断の理由。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 5. データモデル

### 5.1 基本方針：単一の記録＋複数の入り口

内部的には**単一の記録形式**（本文＋種別＋状態/参照等のメタデータ）に統一する。使い勝手としては、以下の6種類の入り口（サブコマンド）に分ける。

| 入り口 | 性質 |
|---|---|
| **memo** | 構造を持たない自由記述（基本の記録） |
| **todo** | 状態を持つ（open/done 等） |
| **qa** | 質問が状態（開／閉）を持ち、回答をぶら下げる。回答は「親（質問）への参照を持つmemo」で、独自のIDを持つ（CLI設計§4.1） |
| **bug** | qaと同じ形：バグが状態（開／閉）を持ち、返信をぶら下げる。返信は「親（バグ）への参照を持つmemo」で、独自のIDを持つ。**課題管理の機能は足さない**（設計§2.7） |
| **glossary** | キーと値の対応を持つ（用語→定義） |
| **rule** | 構造はmemoと同じ（本文だけ）。読み方の意味が違う：この先も効き続ける、読めば従える決まり事 |

Gitのオブジェクトモデルと`commit`/`branch`/`tag`のような入り口の関係と同じ構造（内部データは1つ、外側の道具は複数）。

**bugを足した理由：** 質問と不具合は明確に違うものなので、qaに混ぜずに種類を分けた。ただし**構造はqaと同じ**（状態を持つ親と、`re`を持つ子）で、データ形式では`type`の値が`bug`になるだけ。返信の`re`は同じ`type`の親だけを指す（`qa`の`re`は質問、`bug`の`re`はバグ）。qaとbugの実装はモデル層の1か所にまとめ、種類ごとに分けない。

**入り口を分ける基準は「独自の構造を持つかどうか」**。決定理由・ブロッカー・次回への申し送りは、状態・ペア・キー値対応のいずれの独自構造も持たないため、memoのバリエーションとして扱う（必要ならタグで区別する）。用語集はキー値対応という独自構造を持つため、glossaryとして独立させる。

**ruleを足した理由（この基準の唯一の例外）：** ruleは構造としてはmemoと同じ（本文だけ、状態を持たない）で、上の基準だけに従えばmemoのバリエーションになるはずだった。分けたのは、構造ではなく**振る舞い**が違うため：①`archive`で移さない（glossaryと同じ。効き続ける決まり事は、古くなったからといって片付けるものではない）、②`context`で予算に関わらず削らず、本文も切らない（AIがセッションの始めに読むものとして、従うべき決まりが予算で消えたり途中で切れたりすると意味がない）。glossaryの`word`＋`text`の形にしないのは、ruleが「mtqgには日本語で登録する」のように、それ自体で完結した文だから。「読めばそのまま従える決まり事」に向き、知識・技術が問われる基準や個人の期限には向かない、という使い分けはmtqgが検査しない使い方の判断。

### 5.2 記録者（author）の区別

人間と様々なAIが同じ記録に書き込むため、各イベントに記録者を持たせる。

```json
"author": {"kind": "human", "name": "yamada"}
"author": {"kind": "ai", "name": "claude-code"}
```

- 「誰が書いたか」だけでなく「人間かAIか、どのエージェントか」が分かる
- 特に**qa**で効く。AIが暫定で書いた回答と、人間が確定させた回答を区別できる（回答に対する「確定」の事実を追記する形にするかは要検討）
- 利用者に毎回入力させない。人間はgitの設定（`user.name`）を読み、AIはMCP接続時にクライアントが名乗る名前を使う（11.2）
- **AIがCLIで書くときは、環境変数`MTQG_AUTHOR_KIND`・`MTQG_AUTHOR_NAME`で名乗る**（`ai`のとき名前は必須）。名乗らずにCLIで書くと、gitの`user.name`で記録され、AIの記録がすべて人間の記録になって「誰が書いたか」が失われる。設定ファイルではない（エージェントの設定の`env`に書く。11.3）

#### `author`が表すもの：その内容に責任を持つ主体

- AIが自分の判断で書いたものはAI、**人間の判断をAIが代わりに書いたものは人間**
- 代理で書いた場合は、AIが代わりに書いたことを本文に添える。**慣習として運用し、専用の項目は持たない**（2.6の基準：機能として作り込むほどのものではない）
- mtqgが自動で付けるのは接続している主体なので、代理のときは記録者を明示的に指定できる引数だけ用意する（11.2）
- 指示ファイルに一行書いて運用する（11.3）：「人間の判断を記録するときは、その人を記録者にして、AIが代わりに書いたことを本文に添える」

#### 名前の粒度と表示

- AIの名前は、MCPのクライアント名（`claude-code`）まで自動で付ける。モデル名まで残すかは未決（`PLAN.md`）
- **同じ人の複数の名前（`user.name`のゆらぎ）は名寄せしない**（2.7）。きちんとやりたいプロジェクトは、`user.name`の書き方を最初に決める
- **表示は名前を主にする**。記録のIDは、記録を指すために必要なので控えめに（先頭10桁で）表示する（6章）

### 5.3 データ形式そのものを契約にする

特定のツールに依存しないため、**データ形式を文書化されたプレーンテキストとして公開**する。

- mtqgのCLIがない環境でも、人間やどのAIでも直接読める
- CLIは「形式を扱う入り口の1つ」にすぎなくなる
- `.mtqg/SCHEMA.md`のように、仕様をデータと同じ場所に置いておくと、初見のAIでも読み方が分かる
- SCHEMA.mdの元の文書は`docs/reference/`に置き、`init`・`upgrade`がバイナリに埋め込んだものを書き出す（10.8）
- SCHEMA.mdは**英語で書く**。初見のAIにも、公開後の利用者にも読めるようにするため（10.6）
- SCHEMA.mdは、`version`が宣言している形式までの仕様を書く。書き換えるのは`init`と`mtqg upgrade`だけで、普段の記録では触れない（5.6）。`upgrade`は、形式を上げるときに加えて、**SCHEMA.md自身が古いとき**（形式は変わらず、説明だけが変わったとき）にもSCHEMA.mdだけを書き直す。形式を上げるときだけに連動させると、形式を変えない説明の変更（フィールドの廃止など）が、既存のリポジトリのSCHEMA.mdに届かないまま残る（CLI設計§11.4）
- gitは形式の文書を本体のソース側に置き、リポジトリには番号だけを持たせている。mtqgはそれと違い、初見のAIがその場で読めることを優先して仕様をリポジトリ内に置く

### 5.4 記録作成は手厚くアシストし、読む側は必要な分だけ

mtqgの中心は「残らない過程を残す作業のアシスト」（1.2）なので、力の入れ方を非対称にする。

- **記録作成**：手厚くアシストする。操作はシンプルに、付帯情報は自動で付け、AIが自分で記録できる入口と、記録漏れを促す仕組みを用意する
- **読む側（表示・検索・振り返り）**：記録はプレーンテキストでgitに載るので、GitHubの差分、エディタ、AIがそのまま読める。mtqgは「管理してくれている」体験に必要な分だけ用意する（9章）

### 5.5 付帯情報の自動付与

記録作成の摩擦を下げるため、次の情報は利用者が入力しなくても自動で付ける。

- 記録時刻（`ts`、UTC）、記録者（`author`）、形式の番号（`v`）
- **端末識別子（`tty`）**：端末のデバイス番号（`dev:<rdev>`）か`MTQG_TTY`（`env:<値>`）のsha256の先頭16進8桁。同じ端末からの記録を見分けるために使う（CLI設計§4.5の`undo`）。標準入力・標準出力・標準エラー出力の順で、最初に端末のものを使う（コマンドの出力をパイプに流していても、人が打った端末を見分けられる）。生のデバイス番号や`MTQG_TTY`の値は書かない（記録はコミットされ、他の人にも見える）。Windowsと、どれも端末でないとき（パイプ越しのAI、MCPサーバー、CIなど）は値なしで、値なしの行どうしは同じ端末として扱う

**成果物の位置は持たない。** 記録時の位置（ファイルと行）を事実として残す`at`を用意したことがあるが、廃止した。VSCode拡張で実際に使うと、「位置に紐付ける」という発想自体が分かりにくく、コードが変わっていく以上あまり価値がなかった。ファイル名は本文に書く。既存の`journal.jsonl`に書かれた`at`は、追記だけの原則（2.3）どおり書き換えず、読むときに無視する（知らないフィールドと同じ。5.6）。

### 5.6 形式のバージョン

gitの考え方（`core.repositoryformatversion`と`extensions.*`、インデックスの拡張の扱い）を参考にする。

**`.mtqg/version`：データ形式の宣言**

- `.mtqg/version`に、データ形式の番号を1つだけ書く（中身は`1`のような数字1行）
- mtqgは、**自分が知らない（より新しい）番号を見たら、読むのも書くのも拒否する**。「このリポジトリの形式は新しいので、mtqgを更新してください」と案内する。古いmtqgが新しい形式を黙って読み違えることを防ぐ
- gitの形式番号は`.git/config`にあってクローンごとだが、mtqgのデータは普通のファイルとして交渉なしに運ばれるため、**宣言はコミットされる側に置く**
- ほとんど書き換わらないファイルなので、ブランチ間の衝突はまず起きない

**形式は勝手に上げない**

- mtqgは、**リポジトリが宣言している形式で書く**。手元のmtqgが新しい形式を扱えても、宣言が古ければ古い形式で書き続ける
- 新しい版の機能のうち、形式を変えずに済むもの（表示の改善、無視されても困らないフィールドの追加など）はそのまま使える。形式の変更が必要な機能は使えず、「この機能は形式vNが必要です。`mtqg upgrade`で上げられます」と案内する
- 形式を上げるのは、**利用者が`mtqg upgrade`を明示的に実行したときだけ**。このとき`version`の番号と`SCHEMA.md`を同時に書き換える
- 理由：チームの中でmtqgのバージョンはそろっていないのが普通。1人が新しいmtqgを入れただけで形式が上がると、他の人は次のpullで読めなくなる。`upgrade`を明示的な操作にして、「全員が更新したのを確認してから上げる」判断の場を作る
- `upgrade`しても**過去の行は書き換えない**（2.3）。以降の行が新しい形式で書かれ、古い行は古い形式のまま読まれ続ける

**各行の`v`：その行の書き方**

- 各イベント行に、その行を書いたときの形式の番号（`v`）を持たせる。読み取り側は行ごとに`v`を見て読み方を決める
- **番号を上げずに済む変更と、上げる変更を分ける**（gitのインデックスで、拡張名の1文字目が大文字なら「知らなくても無視してよい」とする区別にならう）
  - **知らないフィールドは無視してよい**：フィールドの追加は、古いmtqgが無視しても意味が壊れない限り、番号を上げない
  - **意味が変わる変更は番号を上げる**：既存フィールドの意味の変更、新しい`op`の追加など、無視すると読み違える変更
- これにより、番号を上げる（＝`upgrade`が要る）頻度を抑える

**形式0の行**

今の形式は1。形式1は、形式0（v1確定前の、形式を自由に変えてよかった期間）とフィールド・構造が同じで、番号だけを上げたもの（12.4）。`v:0`の行は書き換えず、`v:1`の行と同じ意味で読む。

**`.mtqg/version`は、形式の互換性だけを表す1つの非負整数。** 形式そのものを上げるとき以外は、値も形（数字1つ）も変えない。古いmtqgは、中身が数字でなければ「形式が新しすぎる」ではなくエラーで止まるので、`X.Y.Z`のような形にすると既存のバイナリが壊れる。SCHEMA.mdの鮮度は、別の仕組み（SCHEMA.mdの中のマーカー。5.3、CLI設計§11.4）で扱う。

## 6. ID設計：分散環境での衝突回避

### 6.1 問題

連番ID（`#3`のような）は、複数人・複数端末がオフラインで同時にエントリを追加すると衝突する。

```
Aさん(オフライン): mtqg todo add "C言語対応"     → #3
Bさん(オフライン): mtqg todo add "テスト追加"     → #3   ← 同じ番号！
```

### 6.2 解決：UUIDv4

- 新しい記録を作るときに、`crypto/rand`でUUIDv4を作り、**ハイフンを除いた小文字の16進32桁**で保存する。保存するデータ（`id`、`re`）は常に完全な32桁。IDのための調整（採番、カウンタ、ロック中の確認）は何もしない。完全なIDの衝突は考えない
- **表示は先頭10桁**（`--full-id`で32桁）。16進10桁は、10万件でも先頭が重なる確率が0.5%未満。一覧で先頭10桁が重なって同じに見えるのは、まれな場面として割り切る（表示の桁を自動で伸ばさない）
- **入力は、4桁以上で一意に決まる前方一致。** 複数に当てはまるときは止まり、候補を完全なIDで並べる（そこから好きな長さを写して打ち直せる）。3桁以下を受け付けないのは、`add`・`bad`のような語をIDと取り違えないため（CLI設計§6）
- 記録どうしの参照（`re`）は完全なIDなので、短縮IDが後から曖昧になっても、指す先は変わらない
- 同じ秒の並びは`id`で決める（7.5）。`undo`の対象は「この記録者の、この端末（`tty`）の最後の行」で決める（5.5、CLI設計§4.5）

**採らないもの**

- **記録元ID＋ローカル連番**（Snowflake ID的な発想。`a7f3c2-3`のように打ちやすい）：中央調整なしに一意にはできるが、それを支える仕組みがまるごと要る。記録元IDは、マシン単位に持つとdotfilesの同期やコンテナイメージの複製で使い回され、同じクローンでもworktreeを並列に使うと同じ連番を採番するので、worktree単位（gitの私的な領域）に置くことになる。連番をイベントから再計算すると、ブランチを切り替えたときに他のブランチの番号が見えず、同じ番号を採番してマージで衝突するので、カウンタを持ち、失われたら記録元IDごと作り直すことになる。UUIDならこれらがすべて要らない。失うのは「番号だけで打てる」手軽さで、前方一致の入力で補う
- **UUIDv7**：先頭が時刻なので、近い時刻に作った記録の短縮表示がそろい、10桁で見分けられない

### 6.3 ローカルの状態：`.mtqg/.local/`

このマシンでだけ意味を持つ一時的なものは、`.mtqg/.local/`に置く。`mtqg init`が`.mtqg/.gitignore`に`.local/`の1行を書くので、コミットされない。

```
.mtqg/.local/
  lock          書き込みの排他用（10.4）
  tmp/          書き直し（undo・archive）の一時ファイル
  sessions/     エージェントのフックのセッション記録（11.3）
```

- **いつ消えても困らないものだけを置く。** ロックは次に書くときに作り直し、`tmp/`の残骸は書き直しの途中のものなので消してよい。cloneした直後は無いので、必要になったときに作る。他の読み手が必要とする情報や、消えると記録の意味が変わる情報は置かない
- **ロックを一時ディレクトリ（`os.TempDir()`）に置かない。** シンボリックリンクや大文字・小文字の違いで、同じ`.mtqg/`が別の名前になり、排他が効かなくなる。`.mtqg/.local/`なら、どのパスでたどっても同じファイルになる
- 書き直しの一時ファイルは、置き換えを一瞬で終わらせるため、`journal.jsonl`と同じファイルシステムに要る。`.local/`はこれを満たす
- **gitの私的な領域（`git rev-parse --git-dir`の先）には何も置かない。** mtqgの状態はすべて`.mtqg/`の中に収まる（4.3）。worktreeはそれぞれ自分の作業ツリーに`.mtqg/`を持つので、`.local/`も、その排他も、worktreeごとに分かれる
