# mtqg 設計：追記とマージ、削除

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 7. 追記とマージ

### 7.1 すべての操作を追記で表す

状態の変更、回答、訂正、削除も、既存行の書き換えではなく**新しいイベント行の追記**として表現する。1行 = 1イベントで、各行は単独で意味が通るようにする。

```jsonl
{"id":"a7f3c2-3","op":"create","type":"todo","status":"open","text":"C言語対応やりたい","v":1,"ts":"2026-09-17T00:00:00Z","origin":"a7f3c2","author":{"kind":"human","name":"yamada"}}
{"id":"a7f3c2-3","op":"status","from":"open","status":"done","v":1,"ts":"2026-09-17T01:00:00Z","origin":"b21c09","author":{"kind":"ai","name":"claude-code"}}
{"id":"a7f3c2-5","op":"edit","text":"（訂正後の本文）","v":1,"ts":"...","origin":"a7f3c2","author":{...}}
{"id":"a7f3c2-6","op":"delete","v":1,"ts":"...","origin":"a7f3c2","author":{...}}
```

最低限必要なフィールド：`id`、`op`（create/status/edit/delete）、`v`（スキーマのバージョン）、`ts`（記録時刻）、`origin`（記録元ID）、`author`。状態変更には、変更前の状態（`from`）も事実として残す（7.6）。

使う側には「完了にした」「直した」「消した」として見せる（2.4）。

### 7.2 書き出し規則（決定）

イベント行は、GitHubのコミット画面やPRの差分で人間に読まれる（11.5）。一方で、独自の整形処理は持ちたくない。そこで、**Goの標準ライブラリ（`encoding/json`）が素直に出す形を、そのまま規則にする**。規則と実装がずれない。

**書き方**

- Goの構造体にフィールドを決まった順で並べ、標準の`json.Encoder`で書く
- 区切りの空白は入れず、詰めて書く（Goの標準の出力）
- 値がないフィールドは`null`を書かずに**省く**（`omitempty`）
- 日本語などはエスケープしない（Goの標準）。Goが既定でエスケープする`<`・`>`・`&`は、`SetEscapeHTML(false)`で止める
- 本文中の改行はJSONの`\n`になり、**1イベントは必ず1行**
- **すべての行を改行（LF）で終える**。ファイルの末尾は必ず改行になる。unionマージ（7.4）で行がきれいに足され、アーカイブを`cat ... >> journal.jsonl`で戻せる（9.1）のはこのおかげ
- 文字コードはUTF-8（BOMなし）、改行はLF（`.gitattributes`の`eol=lf`・7.4）

**キーの順番**

全種類を1つの構造体でまかない、1本の固定の順にする。

```
id, op, type, re, from, status, word, text, at, v, ts, origin, author, tty
```

- 前半が「何のどんな記録か」と本文、後半がメタデータ。画面で本文が見切れないように、メタデータを後ろに回す
- 状態（`from`、`status`）は短いので本文より前に置き、状態変更の行で状態が見切れないようにする
- `author`の中は`kind`、`name`の順

```
{"id":"a7f3c2-3","op":"create","type":"todo","status":"open","text":"C言語対応やりたい","v":1,"ts":"2026-09-17T00:00:00Z","origin":"a7f3c2","author":{"kind":"human","name":"yamada"}}
{"id":"a7f3c2-3","op":"status","from":"open","status":"done","v":1,"ts":"2026-09-17T01:00:00Z","origin":"b21c09","author":{"kind":"ai","name":"claude-code"},"tty":"3e9a0b12"}
{"id":"a7f3c2-8","op":"create","type":"glossary","word":"記録元","text":"ID発行の単位。worktreeごとに1つ","v":1,"ts":"2026-09-17T02:00:00Z","origin":"a7f3c2","author":{"kind":"human","name":"yamada"}}
```

**glossaryの形**

- 用語名は`word`、定義は`text`に入れる。**本文はどの種類でも`text`**になり、`edit`もどの種類でも`text`を直すだけで統一される
- `word`は、同じ用語の重複定義を突き合わせるため（9章）に別のフィールドにしている。`edit`では変えられない

**読むときは寛容に**

- キーの順番、空白の有無、エスケープの有無を問わず、正しいJSONなら読む
- 書き出し規則は差分の見た目のためのもので、手で直した行や他のツールが書いた行を拒む理由にはしない

**差分を折りたたまない**

- `.gitattributes`の`linguist-generated=true`などで**差分を折りたたまない**。記録はレビューで読まれるべき情報であるため

### 7.3 注意：追記だけではgitのマージは衝突する

2人が**同じファイルの末尾**にそれぞれ別の行を追記すると、gitは「同じ位置に異なる変更が入った」と判断してコンフリクトにする。合流はgitの仕事だが、mtqgは**gitが合流しやすい形で追記する**必要がある。

### 7.4 対策：1ファイル＋unionマージ（決定）

イベントはすべて**1つのファイル**（`.mtqg/journal.jsonl`）に追記し、gitの組み込みunionマージを指定する。

```
# .mtqg/.gitattributes
*.jsonl text eol=lf merge=union
```

- unionマージは、衝突した箇所で**両側の行をすべて残す**。追記だけの設計なので、両方残せば必ず正しい
- unionマージは**行の順序を保証しない**。読み取り側はファイル内の行順に依存せず、7.5の順序で並べる
- `eol=lf`で改行コードをLFに固定する。WindowsでCRLFに変換されると、同じイベントが別の行として扱われかねないため
- この`.gitattributes`はmtqgの初期化時に`.mtqg/`の中にだけ置く。リポジトリ全体のgit設定には触れない（4.3）

**記録元ごとにファイルを分ける案は採らない**

以前は`.mtqg/events/<origin-id>.jsonl`のように記録元ごとに分ける案だった。別の記録元どうしが同じファイルに触れないので、衝突そのものが起きにくい。しかし記録元IDはクローン・worktreeごとに発行される（6.3）ため、worktreeを作り捨てる使い方（AIエージェントの並列実行など）ではファイルが増え続け、`.mtqg/`の見た目も管理も散らかる。

1ファイルにして困るのは「unionマージが効かない場面で衝突が出る」ことだけであり、それは運用でカバーする。IDの一意性は記録元ID（6章）で保たれていて、ファイルの分け方には依存しないので、IDの設計は変わらない。

**unionマージが効かない場面の運用**

GitHub等のWeb画面でのマージなど、`.gitattributes`のマージ指定が使われない場面では、`journal.jsonl`に通常の衝突が出る。そのときは：

- **両側の行を全部残し、衝突マーカー（`<<<<<<<`／`=======`／`>>>>>>>`）だけを消す**。どちらかを選ぶ解決はしない（選ぶと記録が消える）
- 行の順序は気にしなくてよい（7.5）
- 利用者が覚えておくのは「追記だけで、unionマージである」ことだけ

mtqgの側の備え（どれも「自分のデータを読む・書く」範囲に収まる）：

- 読み込み時、衝突マーカーの行はJSONとして読めないので飛ばし、**衝突が解決されていないことを警告する**（10.4の「壊れた行を飛ばして警告する」の特例）
- 衝突マーカーが残ったままのファイルには**書き込まない**。解決を促すメッセージを出す
- 自動で解決するコマンド（マーカーを消して両側を残す）は、手作業で困る場面が出てから検討する（サンプルPJで判断・14章）

**注意：undoで消した行の復活**

`undo`（CLI設計§4.5）は、行を消す操作（もう1つはアーカイブでの移動・9.1。こちらは行が戻っても、もう一度アーカイブすれば済む）。消した行がすでに他のブランチに取り込まれていると、次のunionマージで**消した行が戻ってくる**ことがある。記録元ごとにファイルを分けていた頃より起きやすくなるので、`undo`は「まだ共有していない直前のミス」に使い、共有後は`delete`を使う。

### 7.5 表示の順序（決定）

表示や「現在の状態」を作るときの順序は、**タイムスタンプ（`ts`）、同時刻なら記録元ID（`origin`）**で決める。`ts`は**UTCで持ち、表示のときに各自のロケールの時間へ直す**（文字列の並びがそのまま時系列になる）。

- 端末間の時計のずれによる逆転は許容する
- 論理時計のような、版の前後関係を厳密に決める仕組みは持たない（2.7）
- 順序は表示のためのものであり、どちらの記録が「正しい」かをmtqgが決めるためのものではない

### 7.6 重複・食い違いは、事実として見せる

- 読み取り側は冪等な設計とし、同じIDに対するイベントを7.5の順序で並べて現在の状態を表示する
- 同じ状態変更が複数あってもエラーにしない
- **同じ変更前の状態（`from`）から、別々の状態変更が記録されている場合**は、互いに気づかず並行して変更した可能性がある。mtqgはどちらが正しいかを決めず、「両方の事実がある」として利用者に見せる（9章の`review`）

```
例：a7f3c2-3 に対して
  from:open → done   （yamada, 10:00）
  from:open → done   （claude-code, 14:30）
```

この重複は「互いに気づかず同じToDoを別々の方法で完了させた」という事実そのものであり、ノイズではなく**振り返りに使える情報**になる。

## 8. 削除と機密情報

追記だけの仕組みで、かつgitにコミットされるため、書いた内容は履歴から消えない。

- **削除**：使う側には「消す」操作として見せ、内部では削除の事実を追記して表示から除外する（2.4）
- **消えないことは正直に伝える**：削除時に「表示から除外しました（gitの履歴には残ります）」と表示する（2.5）
- **機密情報の誤記録**：APIキーや個人情報を書いてしまった場合、本当に消すにはgitの履歴の書き換えが必要。これはgitの操作であり、mtqgは手順を案内するだけにとどめる
- **記録時の検査**：AIが自動で記録する運用では誤記録のリスクが上がるため、記録する時点で秘密情報らしき文字列を検査して警告する。これは記録作成のアシストの一部
