# mtqg 設計：表示と振り返り、アーカイブ

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 9. 表示と振り返り：「管理してくれている」体験に必要な分だけ

読む側の機能は、使う側に「過程を管理してくれている」と感じてもらうために必要な分に絞る（5.4）。

1. **`mtqg context`**：現在の状態の要約。未完了のToDo、未回答・未確定の質問、用語集、最近のmemo、未コミットの記録の件数など。AIが次の記録を正しく作るための前提を渡す入口でもあり、読む側の機能の中で最も重要（11.3）
2. **`mtqg status`**：今どうなっているかの概況。未コミットの記録の件数も表示する（4.3）
3. **一覧と表示**：`mtqg todo list`、`mtqg qa list --open`、`mtqg show <id>`など
4. **簡単な検索**：本文の部分一致で探す。索引や全文検索エンジンは持たない（10.3）
5. **`mtqg review`**：7.6の「並行した状態変更」を一覧する。誰がいつどう変更したかを並べて見せる

```
$ mtqg review
a7f3c2-3 "C言語対応やりたい"
  2026-09-17 10:00  yamada       open → done
  2026-09-17 14:30  claude-code  open → done
```

状態変更にメモは添えない（`--note`は持たない）。todoの完了にメモを認めると、「やることと、その結末の説明」になってqaと役割が重なる。qaには回答があるので不要。経緯を残したければ、別にmemoを書くか、qaとして記録する

6. **glossaryの重複定義の表示**：2人が同じ用語を別々に定義すると、IDは別でもキーが重なる。キー単位で複数の定義を並べて見せる
7. **時系列の一覧（`mtqg log`）**：memo/todo/qa/glossaryを時系列で並べて見る

いずれも、人間向けの整形表示とAI向けの`--json`出力を用意する（10.5）。

### 9.1 アーカイブ：終わった時期を視界から外す（決定）

何年も使うと、一覧・検索・`context`に昔の記録が混ざり続ける。期間を指定して「この時期のものはもう終わった」と区切れるようにする。ファイルのサイズ対策ではなく、**利用者とAIの視界を整理するための機能**。AIに渡す`context`が古い経緯に引っ張られにくくなる効果もある。

```
$ mtqg archive 2021-01-01..2024-09-18
Range: 2021-01-01..2024-09-18
Archived: 412 memos, 138 todos, 57 questions -> .mtqg/archive/2021-01-01..2024-09-18.jsonl
Skipped: 3 open todos, 1 open question, 24 glossary entries
```

**対象になるもの**

| 種類 | 対象 |
|---|---|
| todo | 完了したものだけ。未完了は期間内でも残す |
| qa | クローズしたものだけ。未クローズは期間内でも残す |
| glossary | 対象にしない。期間に関係なく全部残す |
| memo | 期間内のものは全部対象 |

- **親を持つmemo（qaの回答）は、親の質問の扱いに従う**。質問が残るなら回答も残り、質問がアーカイブされるなら一緒にアーカイブされる。「memoは全部対象」は、親を持たない単独のmemoについてのルール
- 期間の判定は、**その項目の最後のイベントの日付**で行う。完了したtodoなら完了した日、クローズした質問ならクローズした日。「その時期に終わったもの」という感覚に合わせる
- 実行時に、何件をアーカイブし、何を対象外にしたかを表示する

**仕組み：期間を指定して、行を移すだけ**

`mtqg archive`は、対象の項目の行を`journal.jsonl`から`.mtqg/archive/<開始>..<終了>.jsonl`に**移す**。それ以外のことはしない。アーカイブしたという事実の記録も持たない。

- **どのファイルにあるかが、そのまま状態になる**。`journal.jsonl`にあれば普段の視界に入り、`archive/`にあればアーカイブ済み
- 期間の指定方法はCLI設計§4.7。日付は利用者のローカル時間の日付として解釈し、両端を含む
- ファイル名は、どう指定しても`YYYY-MM-DD..YYYY-MM-DD`の正規化した形になる
- 対象は完了済みの項目なので、その項目のイベントはすべて期間内に収まる。**項目単位でまとめて移す**ので、1つの項目がファイルをまたいで分断されない
- ファイルは**期間の名前で作る**。どの時期をアーカイブしたかがファイル名で分かる。同じ期間でもう一度実行したら、同じファイルに追記する
- 別々のブランチで違う期間をアーカイブしても別ファイルなので衝突しない

**戻すとき：ファイルを結合するだけ**

```
$ cat .mtqg/archive/2021-01-01..2024-09-18.jsonl >> .mtqg/journal.jsonl
$ rm .mtqg/archive/2021-01-01..2024-09-18.jsonl
```

- 行の順序は`ts`で決まり、ファイル内の行順に依存しない（7.5）ので、**末尾に結合するだけで元どおり**になる。mtqgのコマンドがなくても戻せる
- そのため、専用の`unarchive`コマンドは作らない

**割り切っていること**

- unionマージ（7.4）で、移した行が`journal.jsonl`に戻ってくることがまれにある（移した箇所のすぐ近くに、別のブランチの追記が重なった場合）。戻った項目は普段の視界に出るので、気づいたらもう一度`archive`すればよい。古い時期の行はファイルの前の方にあり、他のブランチの追記は末尾に付くので、実際にはほとんど起きない
- アーカイブの後に古いブランチがマージされ、期間内に完了した項目が入ってきた場合、それは`journal.jsonl`に残る。必要ならもう一度同じ期間で`archive`する
- 読み取り側は、**中身が完全に一致する行は同じイベントとして1つに扱う**。戻す・移すを重ねて重複が生じても表示が崩れない

**mtqgはアーカイブを見ない**

- 一覧・検索・`context`・`log`・`show`など、すべてのコマンドは`journal.jsonl`だけを読む。アーカイブ済みの項目は、mtqgからは存在しないものとして扱う
- アーカイブ済みのIDを指定した操作（`show`、`reopen`、`edit`など）は、ふつうの「IDが見つかりません」になる。特別な案内はしない
- 中身を読みたいときは、ファイルを直接開くか、`mtqg format .mtqg/archive/<ファイル>`で整形して読む（CLI設計§4.6）
- 例外は記録元IDの発行時の重なりの確認（6.4）だけで、ここでは`archive/`も見る。アーカイブを戻したときにIDがぶつからないようにするため

**原則との関係**

- 「過去の行は書き換えない」（2.3）に対しては、**行の中身は変えず場所を移すだけ**で、利用者が明示的に実行したときだけ起きる例外と位置づける
- `archive/`はv1の形式に最初から含める。形式の変更（`upgrade`・5.6）は要らない
- `journal.jsonl`だけを読むので、読み込みの量も減る（副次的な効果）
