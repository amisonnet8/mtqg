# mtqg 設計：実装方針

> 今の設計と、その判断の理由。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 10. 実装方針

### 10.1 言語：Go

CLIはGoで実装する。

選定の軸と理由：

- **配布のしやすさ**：開発者のマシンだけでなく、CI、コンテナ、クラウド上のエージェント環境でも動く必要がある。ランタイム不要の単一バイナリで、クロスコンパイルも簡単
- **起動の速さ**：AIエージェントは作業中に`mtqg context`や記録コマンドを何度も呼ぶため、1回ごとの起動の遅さが積み重なる
- **クロスプラットフォーム**：Windowsでもパスや改行コードで壊れないこと
- **ブートストラップ期の書きやすさ**：スキーマが何度も変わる前提なので、型が厳密すぎず変更に追従しやすい言語がよい
- **読みやすさ**：実装はAIに任せても、レビューするのは人間。言語が単純でAIが書いたコードを読みやすい
- **先行事例**：git-bugもBeadsもGoで書かれており、同種の問題を解いた実績がある

比較した候補：

| | Go | Rust | TypeScript | Python |
|---|---|---|---|---|
| 単一バイナリ | ◎ | ◎ | △ | × |
| 起動速度 | ◎ | ◎ | ○ | △ |
| スキーマ変更への追従 | ○ | △ | ◎ | ◎ |
| AIが書くコードの安定度・読みやすさ | ◎ | ○ | ◎ | ◎ |

データ形式そのものを契約にしている（5.3）ので、言語選択は致命的なロックインにはならない。

### 10.2 gitとの関わり：読むだけ

- gitの情報は、ライブラリ（go-gitなど）ではなく`git`コマンドを呼んで**読む**（`git config user.name`、`git branch --show-current`、`git show HEAD:.mtqg/journal.jsonl`、`git status`など）。gitの設定・フック・worktree・サブモジュールの扱いが本物とずれない挙動にするには、本物のgitに聞くのが最も確実
- ブランチ名は`git branch --show-current`で読む。`git rev-parse --abbrev-ref HEAD`は、最初のコミットの前はエラーになり、detached HEADでは`HEAD`という名前を返す。`--show-current`は、最初のコミットの前でもブランチ名を返し、detached HEADでは空になる
- gitへの書き込み（コミット、フックの設定など）は行わない（4.3）

### 10.3 読み取りと検索：全件走査で十分

- jsonlを毎回全部読んで、表示を作る。数千〜数万件程度なら十分速い
- スキーマが変わっても、作り直すべき索引がない
- 検索は本文の部分一致で行う
- 索引や全文検索エンジンは持たない。実際に遅さが問題になり、かつ5.4の「必要な分」に当たると判断できた時点で再検討する（2.7）

### 10.4 書き込みの安全性

複数のプロセス（複数のAIエージェントのMCPサーバー、人間のCLI）が同時に同じファイルへ追記しうる。

- イベントは1行を1回の書き込みで追記し、書きかけの行が読まれないようにする。追記に`fsync`は付けない（書き込みの速さが最優先）
- 追記の前に、ファイルの末尾が改行でなければ改行を足す。途中で落ちて残った書きかけの行に、次の正しい行がくっついて壊れるのを防ぐ
- **`.mtqg/`の中のファイルは、すべて`.mtqg/`を開いた`os.Root`経由で開く。** `os.Root`は、`..`でも外を指すシンボリックリンクでも`.mtqg/`の外に出さない。mtqgは他人のリポジトリをcloneした直後に動かされるので、`.mtqg/journal.jsonl`や`.mtqg/.local`が外へのリンクとしてコミットされていても、リンク先に書かない（`.mtqg`自体のリンクは4.4）

**ロックの方式：OSのファイルロック**

- `.mtqg/.local/lock`（6.3）に、OSのファイルロック（Linux・macOSは`flock`、Windowsは`LockFileEx`）をかける
- gitの`index.lock`のような「ロックファイルを作れたら持ち主、終わったら消す」方式は採らない。プロセスが強制終了されるとロックファイルが残り、手で消すまで動かなくなるため。mtqgはAIエージェントから呼ばれ、エージェントごと止められることが普通にある。OSのロックなら、プロセスが死ねばOSが自動で解放する
- 取れないときは5秒待ち、それでも取れなければエラーにする。`flock`は待ちを中断できないので、ロックを非ブロッキングで試して短い間隔で再試行する
- **ロックのファイルは`journal.jsonl`とは別に持つ。** `journal.jsonl`そのものにロックをかけると、`undo`・`archive`の置き換えの後、置き換え前の古いファイルでロックを待っていたプロセスが、消えたファイルに書き込んでしまう
- **ロックのファイルは消さない。** 消すと、消す前のファイルと新しいファイルにそれぞれロックをかけた者どうしで、排他が効かなくなる

**ロックで守る範囲：`journal.jsonl`への書き込み全体**

- 普通の記録（`add`、`done`など）：ロックを取る → 衝突マーカーが残っていないか確かめる（残っていれば書かない・7.4）→ 1行追記する → ロックを外す
- **`undo`と`archive`**：行を消す・移すため、ファイル全体を書き直す。書き直しの最中に別プロセスが追記した行が消えないよう、**同じロックを取り**、一時ファイル（`.mtqg/.local/tmp/`）に書いて`fsync`してから置き換える。行は**元のバイト列のまま**書き戻す（知らないフィールドも、読めなかった行も、手で直した整形も消えない）
- Windowsは、開いているファイルを置き換えられないことがある。自分のハンドルは置き換える前に閉じ、読み込み中の別プロセスに備えて、上限を決めて短く再試行する
- ロックはworktreeごと（`.mtqg/`がworktreeごとのため）。worktreeが違えば`journal.jsonl`の作業コピーも別なので、worktreeをまたいだ排他は要らない
- 書き込み時に形式を検証し、読み込み時は壊れた行を飛ばして警告する

### 10.5 出力：人間向けとAI向け

- 表示系のコマンドは、同じ結果を**人間向けの整形表示**と**AI向けの`--json`出力**の両方で出せるようにする
- 補助ツール（11章）はこの`--json`出力を使い、データ形式を自前で解釈しない

### 10.6 表示の言語：英語

**mtqg自身が出す文言は英語にする**。CLIのエラー、案内、確認、見出しや列名、結果の表示、`--help`、`context`の冒頭の指示文、フックの出力、VSCode拡張のUI（11.4）、SCHEMA.md（5.3）が対象。

**利用者が書いたものは、書いた言語のまま**。記録の本文、用語名、記録者名などは翻訳も制限もしない。日本語で使う人の画面は「枠は英語、中身は日本語」になる。gitのログでコミットメッセージだけ日本語になるのと同じ。

理由：

- gitやGoのツールなど、周りのCLIはほぼ英語。並べて使っても違和感がない
- AIエージェントがmtqgのメッセージを読んで次の行動を決める場面が多い。英語ならどのAIでも確実に解釈される
- 公開したとき、日本語を読めない人もそのまま使える
- 翻訳の仕組み（多言語化）を持たずに済み、実装が単純になる

補足：

- 多言語化しない。メッセージはCLIの層の1か所にまとめる（10.7）
- 日付・時刻の表示はロケールに合わせる（7.5）。これは表示の言語とは別の決まり
- この設計文書やCLI設計のような**設計文書は日本語のまま**。本文中で「」で書いているメッセージは意味を表したもので、実際の文言は英語になる

### 10.7 コアの構成：ジャーナル層とモデル層

データを扱う処理は、入口（CLI、`mtqg mcp`、`mtqg hook`）から切り離した**コア**にまとめる。コアは2層に分ける。

```
CLI ／ mtqg mcp ／ mtqg hook        引数の解釈、英語の文言・表の整形、--json
        ↓
モデル層                            イベントの意味を扱う
        ↓
ジャーナル層                        journal.jsonlの読み書きだけ
        ↓
.mtqg/（journal.jsonl・archive/・version・.local/）
```

入口（CLI、`mtqg mcp`、`mtqg hook`）は、どれもCLIの層（`internal/cli/`）に置く。MCPやフックが要るもの（エラーの文言と種類、記録のJSONの形、`context`の文章、ジャーナルの開き方）は、すべてCLIの層に1か所ずつあり、別の層に分けると、それを公開して入口どうしの依存を作るか、複製することになるため（11.2、11.3）。

**ジャーナル層：journal.jsonlの読み書き**

イベントが「todoの完了」か「用語の定義」かは知らず、1行のイベントとして扱う。どのコマンドにも紐づかない、共通の読み書きの部品。

- **読み込み**：`.mtqg/`の探索（4.4）、`version`の確認（知らない形式なら断る・5.6）、全行をイベントとして返す。壊れた行・衝突マーカーは飛ばして警告する（7.4、10.4）。中身が完全に一致する行は1つにまとめる（9.1）
- **追記**：呼び出し側は`op`・`type`・`re`・本文など**意味の部分だけ**を渡す。`id`（新規作成のとき）、`ts`、`author`、`tty`、`v`はジャーナル層が埋める。ロックを取り、書き出し規則（7.2）で1行を書く
- **書き直し**：`undo`や`archive`のために、「ロックを取り、全行を渡し、変更後の行を受け取り、一時ファイル経由で置き換える」汎用の操作を持つ（10.4）。`archive`は、アーカイブへの追記と置き換えを1回のロックで行う（9.1）
- ローカルの状態（ロック、一時ファイル、フックのセッション・6.3）と、gitを読むこと（10.2）もここで扱う

書き出し規則・ロックの手順・形式の確認は、**この層の1か所にしか存在しない**。MCPやフック、将来の補助ツールも、コマンドを経由せずに同じ書き出しを使える。

**モデル層：イベントの意味**

- イベントを並べて、todo・qa・glossaryの現在の状態を組み立てる（順序は7.5）
- 検証（memoは完了にできない、アーカイブ済みのIDは見つからない、など）
- `undo`の対象の選び方（4.5）、アーカイブの対象の選び方（9.1）
- 並行した状態変更・用語の重複定義の検出（9章）
- `context`の中身の組み立て（区画・削り方）

**入口の層**

- 引数の解釈（`archive`の期間の解釈など）、英語の文言・表の整形、`--json`の出力
- コアは文章ではなく**構造化された結果やエラーの種類**を返し、それを文言にするのは入口の仕事。メッセージは入口の側で1か所にまとめる（10.6）

**公開しない**

- コアはGoの`internal/`の下に置き、リポジトリの外からは使えないようにする。公開すると、そのAPIが他人との約束になり、自由に変えられなくなる
- mtqgの外との約束は、データ形式（5.3）とCLIの`--json`だけ。VSCode拡張（TypeScript）も`--json`経由で使う（11.4）
- 公開ライブラリにするかは、v1の後に考える

**作り方：最初から層を分けて書く**

- 「コアを完成させてからCLIに着手する」ではなく、**CLIを作るときから、ジャーナル層・モデル層・CLIの層を分けて書く**。使われ方が見えないまま作り込むと、要らない汎用性を作りがちなため
- CLIがコアの最初の利用者、段階4の`mtqg mcp`が2番目の利用者になり、コアの形が正しいかを試す
- コアは単体でテストする。一時的なgitリポジトリを作り、追記・状態の組み立て・ロック・アーカイブなどを、表示と切り離して確かめる

### 10.8 文書の構成：`docs/`

```
docs/
  reference/     仕様の辞書（英語版が正、日本語版 *_ja.md）
  examples/      入門から実例まで（英語版・日本語版）
  design/        設計文書（日本語）
  assets/        READMEのロゴ・デモ
```

「調べるときに引く辞書」と「順に読む手引き」という**読み方の違い**で分ける。どこに置くか迷わないようにするため。

- **`reference/`**：コマンドごとの説明、データ形式の仕様。`journal.jsonl`の衝突の直し方（7.4）も、「unionマージが効かない場面ではこうなる」という仕様の説明としてここに置く。困ったときに引くものはここ
- **`examples/`**：最初から順に読む文書。`mtqg init`から6つの種類、ブランチとマージ、AIエージェントとの連携までを歩いて回る入門と、記録が溜まったリポジトリを通しで読む実例
- **`design/`**：この設計文書やCLI設計。今の設計と「なぜこうなっているか」を書く、日本語（10.6）。経緯は、前のやり方に戻すと同じ問題がまた起きるものだけを書き、それ以外の経緯は`.mtqg/`に記録する（`.claude/rules/documentation.md`）
- `reference/`と`examples/`の実行例は手で書かず、実際に動かした出力をテストが突き合わせる（10.10）

**SCHEMA.mdの元は`docs/reference/`に置く**

- データ形式の仕様の元の文書を`docs/reference/`に置き、`mtqg init`（と`mtqg upgrade`）は、それをGoの`embed`でバイナリに埋め込んで`.mtqg/SCHEMA.md`として書き出す（5.3）
- 仕様の文書が1つで済み、リポジトリで読む仕様と、各プロジェクトの`.mtqg/`に置かれる仕様が必ず同じになる

### 10.9 リポジトリの構成

Goのコードに関わる骨格だけを示す。リポジトリ全体の構成と配置の判断基準は`.claude/rules/directory-structure.md`が持つ（二重に持つと食い違うため）。

```
cmd/
  mtqg/
    main.go              引数をinternal/cliに渡すだけ
internal/                コア（10.7）。リポジトリの外からは使えない
  journal/               ジャーナル層：探索、version確認、読み書き、ロック、gitを読む
  model/                 モデル層：状態の組み立て、検証、archiveの対象選び、context
  cli/                   入口の層：CLI・mtqg mcp・mtqg hook、英語の文言、表の整形、--json
e2e/                     本物のバイナリと本物のgitで動かすテスト（10.10）
schema.go                docs/reference/schema.md を embed する小さなパッケージ
.golangci.yaml           lintの設定
trivy.yaml               Trivyの設定（10.10）
.goreleaser.yaml         各OS向けのバイナリ（10.11）
qsokufile                ビルド・テスト・lintの入口（10.10）
```

**理由と補足**

- **`cmd/mtqg/`**：Goの慣習どおり、`cmd/`の下にコマンド名のディレクトリを1段挟む。`main.go`は数行にし、処理は`internal/`に置く
- **`internal/`**：10.7のコアの2層とCLIの層。`internal/`の下に置くことで、Goの仕組みとして外部から使えなくなる（コアを公開しない・10.7）
- **`schema.go`**：Goの`embed`は、そのパッケージのディレクトリより下のファイルしか埋め込めない。`internal/journal/`からは`docs/reference/schema.md`を埋め込めないため、ルートに埋め込むだけのパッケージを置き、`internal/`からそれを使う。コピーを作らずに「仕様の元の文書は1つ」（10.8）を守る
- **`ci.yml`**：**Linux・macOS・Windowsの3つでテストを回す**。ロックの実装がOSで分かれている（`flock`と`LockFileEx`・10.4）ため、片方だけでは壊れに気づけない
- **`.golangci.yaml`**：lintの基準を固定し、AIがコードを書くときにも同じ基準で指摘が出るようにする。層の依存の向き（`cli → model → journal`）や、文言をCLIの層に限ることも、ここで機械的に検査する
- **`trivy.yaml`**：既知の脆弱性とライセンスの検査の基準を固定する（10.10）

**`.gitignore`に入れるもの**

- `.claude/settings.local.json`（個人の設定）
- ビルドした`mtqg`のバイナリ、`dist/`（ルート直下に限定する。`mtqg`とだけ書くと、ソースの`cmd/mtqg/`まで無視される）

**VSCode拡張は別リポジトリ**

- VSCode拡張（11.4）は`--json`でつながるだけでコードを共有しないため、別リポジトリにする。本体をGoのツールチェーンだけで完結させ、公開（VS Code Marketplace）やリリースの頻度も分けられる
- 一方、`mtqg mcp`・`mtqg hook`は同じバイナリのサブコマンドで、`internal/`のコア（別リポジトリからimportできない）を使うため、本体に置く

### 10.10 テストと検査の方針

**Goのテスト**

- コア（ジャーナル層・モデル層）は単体でテストする（10.7）。一時的なgitリポジトリを作り、追記・状態の組み立て・ロック・アーカイブなどを、表示と切り離して確かめる
- 一時ファイル・ディレクトリは`t.TempDir()`で作る。作成も後片付けもテストの仕組みに任せ、`rm -rf`で片付けない
- CIではLinux・macOS・Windowsの3つで回す（10.9）
- lintは`golangci-lint`（`.golangci.yaml`）。`GOOS=windows`・`darwin`でも動かす（ロックと端末のファイルがOSで分かれ、Linuxだけでは壊れに気づけない）

**Trivy：既知の脆弱性とライセンス**

- `trivy fs`で、依存しているモジュールの**既知の脆弱性（CVE）**と**ライセンス**を検査する
- mtqgはMITで配布する。依存にGPL・AGPLなど、MITのバイナリとして配布できない（互換性のない）ライセンスが入ったら失敗にする
- 設定は`trivy.yaml`にまとめ、何を失敗とみなすか（深刻度、禁止するライセンスの種類）をファイルで固定する
- 依存は、Goの標準ライブラリと`golang.org/x/`だけにする。それ以外は、標準・`x/`に無い、または自前で書くと量が多く正しさや安全性の確認が難しい、という「どうしても必要な場合」の例外で、理由を説明して確認を取る（MCPの公式SDKが例外・11.2）。「少なく保つ」だけでは追加のたびに議論になる。線引きにすれば信頼の根がGoチームに絞られる。代償は、引数の解釈・シェル補完・文字幅の関数などを自前で書くこと
- 依存を足したら、Trivyを通す
- Trivyは脆弱性データベースを取得するため、初回や更新時に通信が要る

**ShellCheck：シェルスクリプト**

- シェルスクリプトを書く場合は、`shellcheck`で検査する
- 対象になりそうなもの：`.devcontainer/postCreate.sh`、`.claude/hooks/`のスクリプト、段階4のフックの導入まわり
- シェルスクリプトは最小限にする。処理が込み入るならGoで書く（mtqgのフックも`mtqg hook`としてGoのバイナリに入れる・11.3）

**e2eとdocsの例の確認**

- **e2e**：ビルドした`mtqg`と本物の`git`を組み合わせて動かす。単体テストでは確かめにくい、**複数のクローンやブランチをまたぐ動き**（2つのクローンで記録してマージする、unionマージで行が混ざる、衝突マーカーが残った状態で読む、アーカイブの後に古いブランチをマージする、など）を押さえる。mtqgの設計の芯なので重視する
- **docsの例の確認**：`docs/reference/`のコマンドの実行例と出力例が、実際の動きとずれていないかを確かめる。AIが文書を読んで使うため、古い例は誤った使い方を覚えさせる
- どちらもシェルではなくGoで書く。e2eは、ビルドした本物の`mtqg`を`exec`するGoのテスト（ビルドタグ`e2e`）。`testscript`（`rogpeppe/go-internal`）は`golang.org/x/`ではないので、依存の基準で使わない（要らないことも確かめた）
- **docsの例は手で書かない。** 例のフェンスの直前にHTMLコメントの印（どのフィクスチャで動かすか）を置き、テストが実際に動かして文書と突き合わせ、`-update`で実際の出力を書き戻す。手で書くと、節ごとに別の記録から取った例が文書の中で食い違う
- 例は、`Run(env, args)`を時計（`Env.Now`）と表示の地域を固定して直接呼んで取る。「今日の記録はHH:MM、それ以前は日付」の表示が実行日で変わるため。`MTQG_NOW`のような、テストのためだけの裏口を製品に作らない。本物のバイナリとの差が例の出力に効かないことは、時計に依存しない例を本物のバイナリでも動かして確かめる
- 例は、日時とIDを固定した1つの整合したフィクスチャから、節をまたいで取る（`ts`は秒単位なので、続けて打って作ると同じ秒の記録が`id`の順に並び、意図と違う並びになる）

**どこで回すか**

- 手元：`qsokufile`に、テスト・lint・Trivy・ShellCheckなどを名前を付けて置き、`qsoku check`のように呼ぶ。Claude Codeは作業の区切りでこれを通す
- devcontainer：`golangci-lint`、`trivy`、`shellcheck`を最初から入れておく。実装の途中でツールのインストールが要らないようにする
- CI：手元と同じ名前を回す

### 10.11 配布方法

**`go install`**

```
go install github.com/amisonnet8/mtqg/cmd/mtqg@latest
```

- 配布のための仕組みを何も作らずに済む。タグを打てば、それだけでバージョンを指定して入れられる

**GitHub Releasesのバイナリ**

- `go install`は、Goが入っていない人は使えない。mtqgの利用者（AIエージェントと開発する人）には、Goを入れていない人も多い。VSCode拡張も、手元に`mtqg`のバイナリがある前提
- GoReleaser（`.goreleaser.yaml`・10.9）で各OS向けのバイナリを作る。人間がタグを打ってpushすると、CIがテストを通してから作り、**下書きの**Releaseに置く。中身を見て公開するのは人間（`.claude/rules/distribution.md`）
- Homebrewなどのパッケージマネージャーは、使う人が増えて要望が出てから考える

**実装で守ること**

- **cgoを使わない**。純粋なGoにしておけば、各OS向けのバイナリを簡単に作れる。ロック（`flock`、`LockFileEx`・10.4）も`golang.org/x/sys`経由ならcgoなしで呼べる
- **`mtqg version`のバージョンは`runtime/debug.ReadBuildInfo`で取る**。ビルド時の埋め込み（`-ldflags`）は`go install`では効かないため。`ReadBuildInfo`なら`go install ...@v0.2.0`で入れたときのバージョンも取れ、どちらの配布方法でも正しく表示される
