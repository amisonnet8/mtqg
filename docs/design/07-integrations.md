# mtqg 設計：外部ツール連携

> 今の設計と、その判断の理由。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 11. 記録作成のアシスト：外部ツール連携

### 11.1 位置づけと構成の原則

外部ツール連携は、**残らない過程を残す作業のアシスト**（1.2）と、**「管理してくれている」体験**（2.4）のためにだけ用意する。2.7に挙げた、役割を超える連携は採らない。

- 補助ツールは**データ形式を自前で解釈しない**。解釈はGoのバイナリの1か所に集約する
- 使う相手ごとに入口を分けるが、中の共通コアとデータは1つ。どの入口から書いた記録も、どの入口からも同じように見える

| 相手 | 入口 | 1.6の「使わずに済ませられてしまう」の越え方 |
|---|---|---|
| AIエージェント | MCP、エージェントのフック | 仕組みで必ず読ませ、記録を促す。UIは要らない |
| 人間 | CLI、VSCode拡張（豊かなUI） | 使いたくなる体験にする |

```
mtqg（単一バイナリ）
 ├─ CLI       ── 人間（ターミナル）
 ├─ mtqg mcp  ── AIエージェント・AIアプリ（AI用の入口）
 ├─ mtqg hook ── エージェントのフックから呼ばれる
 └─ --json    ── エディタ拡張など
       ↓
    共通コア（モデル層 → ジャーナル層・10.7）
       ↓
    .mtqg/
```

`mtqg mcp`・`mtqg hook`は、CLIと同じ入口の層（`internal/cli/`）に置く。どちらも、要るもの（エラーの文言と種類、記録のJSONの形、`context`の文章、本文の正規化、ジャーナルの開き方）がすでにCLIの層に1か所ずつあり、別の層に分けると、それを公開して入口どうしの依存を作るか、複製することになるため（10.7）。

AIエージェント向けの組み込み（指示ファイル→フック→MCP）を、VSCode拡張より先に作った。記録の多くはAIとのやり取りから生まれるため。人間と一緒に作業するプロジェクトでは、VSCode拡張が必須になる（11.4）。

### 11.2 AIエージェント向け：MCPサーバー（AI用の入口）

`mtqg mcp`としてMCPサーバーを提供する。人間にとってのCLIに当たる、AIにとって一番使いやすい入口。

- **起動**：AIエージェントがセッション開始時にサブプロセスとして起動し、標準入出力でやり取りする。常駐もネットワークのポートも使わない。標準出力はJSON-RPCのメッセージ専用で、人間向けの文言や警告は混ぜない
- **プロトコルの実装**：MCP（JSON-RPC 2.0、stdio）は、公式Go SDK（`github.com/modelcontextprotocol/go-sdk`）に任せる。依存の基準（標準ライブラリと`golang.org/x/`だけ・10.10）の例外で、プロトコルを自前で書くと量が多く、正しさの確認が難しいため（理由と確認の経緯は`PLAN.md`「段階4b」）。`.golangci.yaml`の`depguard`で、ジャーナル層・モデル層からSDKをimportできないようにし、SDKに触れるのが入口だけであることを機械的に固定する
- **公開する操作**：中心は記録作成。6つの種類それぞれの作成、回答・返信、`done`・`reopen`、`edit`（新しい本文を引数で受け取る。`$EDITOR`は開かない）。読む側は`context`、`show`、`search`だけ。**`delete`・`undo`・`archive`・`review`・`format`は公開しない**（消す・移すような操作を、AIの判断だけで実行させないため）
- **質問と回答、バグと返信は別のツールにする。** CLIの`qa add`は最初の語がIDらしいかで質問か回答かを決めるが（CLI設計§4.2）、MCPは入力欄でIDと本文を区別できるので、この判定を使わない
- **記録者の自動付与**：`author.kind`は常に`ai`、`author.name`は接続時にクライアントが名乗る名前（`clientInfo.name`）。`MTQG_AUTHOR_*`やgitの`user.name`は見ない（人間の設定を、AIの記録に引き継がない・5.2）
- **戻り値**：結果は、対応するCLIコマンドの`--json`と同じJSONオブジェクトにする。形の約束を`cli.md`の1か所に保つため。`context`と`search`だけは、AIのコンテキストに入る分量のため専用の形（一覧は要約にとどめ、詳細は`show`で取りに行く）。エラーはJSON-RPCのプロトコルエラーにせず、ツールの結果（`isError:true`）として`--json`と同じ`{"error":{...}}`の形で返し、サーバーは動き続ける
- **対象リポジトリ**：起動時に1度だけ決めるのではなく、**ツールを呼ぶたびに`.mtqg/`を探す**。起動時に決めると、サーバーが起動した後に`mtqg init`されたリポジトリを見つけられない。毎回探せば、見つからないことはサーバー起動の失敗ではなくツールごとのエラー（`not_initialized`）になる。複数のリポジトリを扱うAIアプリは、グローバルオプション`-C`で対象を明示する
- **設定**：エージェントのプロジェクト設定（Claude Codeなら`.mcp.json`）に書く。コミットしておけば、cloneした人のエージェントも同じようにつながる。`mtqg init --agent`が書く（11.3）

### 11.3 AIエージェント向け：エージェントのフック

#### 位置づけ

- **フックという仕組みそのものはエージェント側の機能**。「いつ呼ぶか」はClaude Code等のエージェントが決める
- **mtqgが用意するのは、フックから呼ばれるコマンドと、それを設定する導入コマンド**
- MCPとの役割分担：MCPは「AIが自分の判断で使う入口」。フックは**読み込みと記録漏れの確認を、AIの判断に頼らず必ず行わせる**。何を記録するかの判断はAIにしかできないため、記録そのものはMCPでAIに任せる

#### 使われ方（Claude Codeの例）

| タイミング | エージェント側のフック | mtqgがすること |
|---|---|---|
| セッション開始 | SessionStart | `context`を生成し、AIのコンテキストに入れる |
| コンテキスト圧縮の直後 | SessionStart（compact時） | `context`を入れ直す。記録済みの過程は圧縮を越えて残る |
| 応答の終了 | Stop | 記録漏れの可能性があれば、終了を止めて記録を促す |

#### mtqgとして用意する機能

| 機能 | 役割 | エージェント依存 |
|---|---|---|
| `mtqg context`（分量指定つき） | 入れる中身を作る | なし |
| セッションの記録と判定 | 終了時に記録を促すべきか判断する | なし |
| `mtqg hook <agent> <event>` | エージェントとの入出力を変換する | あり |
| `mtqg init --agent <agent>` | エージェントの設定ファイルに書き込む | あり |

エージェント依存の部分（アダプタ）は薄く保ち、判断はすべて依存しない共通機能に置く（促すかどうかの判断はモデル層、セッションの状態の読み書きはジャーナル層）。

**1. `mtqg context`（分量指定つき）**

- 分量の上限（`--max-tokens`）を指定できる。分量は文字数からの近似で数える（ASCIIの4文字＝1トークン、ほかは1文字＝1トークン）。トークナイザは`golang.org/x/`に無く、依存の基準で足せないため。近似であることを仕様に書き、実際のトークン数のように扱わない
- 上限を超える場合に削る順序は、仕様で固定する（`docs/reference/cli.md`）：最近の記録、用語の定義、回答・返信の本文、古い質問とbug、古いtodoの順。ruleは削らず、本文も切らない（5.1）
- **最新の3件の質問と3件のbugは、最後まで削らない。** 質問とbugをすべて削ってからtodoを削る順にすると、todoが多く予算が厳しいときに質問が1件も見えなくなる。質問は「未決だから自分で決めるな」と伝える情報で、真っ先に失うと、AIが未決のことを知らずに決めてしまう。交互に削る案は、質問が減る一方になり、未決が見えることの保証にならないので採らない
- 削る順序を決めるのはモデル層の1か所、測るのと文章にするのはCLIの層。CLIは、収まる最小の削り方を二分探索する（1件ずつ削って組み立て直すと、数万件で遅い）
- セッション開始のたびに実行されるため、一瞬で終わること

**2. セッションの記録と判定**

- セッション開始時に、開始時刻、`HEAD`（`git rev-parse HEAD`）、作業ツリーのダイジェスト（`git status --porcelain -z`から`.mtqg/`を含む行を除いてハッシュ化したもの）を覚えておく
- 終了（`stop`）のたびに読み直して比べ、**「作業が行われた」（`HEAD`かダイジェストが変わった）のに「記録が0件」（`journal.jsonl`に、開始時刻以降の`ts`を持つイベントが、誰が書いたかを問わず1つも無い）**のときだけ促す
- 比べる前に、開始時刻を秒へ切り詰める。`ts`は秒の精度なので、切り詰めないと、開始と同じ秒に書かれた記録を「開始より前」と見なし、記録済みなのに促してしまう
- 判定は、ファイル単位の変更を見る。セッション開始より前からあった未コミットの変更や、すでに変更済みのファイルへの追記は、`git status --porcelain`の行が変わらないので「作業」に数えない
- 一度促したセッションには印を付け、二度目は促さない。圧縮で`session-start`がもう一度呼ばれても、最初に覚えた状態を保つ（覚え直すと、それより前の未記録の変更が「無かったこと」になる）
- この状態はコミットしない（`.mtqg/.local/sessions/`・6.3）。セッションIDは、`[A-Za-z0-9_-]`だけの短い文字列ならそのままファイル名にし、それ以外はsha256の先頭16桁にする（エージェントが渡す値を無条件でパスに使わない。`os.Root`が外へは出さないので二重の備え）。読めない・壊れたファイルは「セッションが無い」として扱う。7日より古いものは`session-start`のたびに掃除する

```
.mtqg/.local/sessions/<session-id>.json
  {"started_at": "...", "head": "...", "status_digest": "...", "prompted": false}
```

**3. `mtqg hook <agent> <event>`（アダプタ）**

1. エージェントが標準入力に渡すJSON（セッションID、作業ディレクトリ等）を読む
2. 1・2の共通機能を呼ぶ
3. 結果をそのエージェントが期待する形式で出力する

```
mtqg hook claude-code session-start
  入力: {"session_id":"abc","cwd":"...","source":"startup"}
  処理: セッション開始を記録 → context を生成
  出力: context のテキスト

mtqg hook claude-code stop
  入力: {"session_id":"abc","stop_hook_active":false,...}
  処理: 開始以降の作業と記録を判定
  出力: 促す必要あり → {"decision":"block","reason":"..."}
        不要         → 何も出さない
```

- **`--json`を持たない。** 出力の形はエージェント自身のフックの約束事で決まり、mtqg独自の形にする余地がない
- **エージェントのターンを壊さない。** `<agent>`・`<event>`が分かった後は、読めない入力・`.mtqg/`が無い・gitが使えない、のどれも終了コード0にする

**4. `mtqg init --agent <agent>`（導入コマンド）**

- エージェントの設定ファイル（Claude Codeなら`.claude/settings.json`のフックと`env`、`.mcp.json`）に、フックとMCPの設定を書き込む
- 指示ファイル（CLAUDE.md、AGENTS.md等）への一行の追記もまとめて行う
- 既存の設定を壊さずに足し、何度実行しても重複しない。既存の値（`env`の既存のキー、他のフック、既存の`mcpServers`の項目）は上書きしない。`-n`で書き込む内容を事前に表示する
- 設定のJSONは、読み込んで変えたい部分だけ触り、キーを決まった順に並べて書き戻す（既存の並びを保つトークン単位の編集は、手間に見合わない）。手で書いたファイルは、初回だけキーの並びが変わる。変化がなければ書かない
- 書き込むのはエージェントの設定ファイルであり、gitの設定には触れない（4.3）。書き込みは、リポジトリのルートを開いた`os.Root`経由で行う

**使う側から見た姿**：`mtqg init --agent claude-code`を一度実行するだけで、以後はセッション開始時に経緯が読み込まれ、圧縮後も経緯が戻り、終了時に記録漏れが確認される。

#### 注意点

- **速さと分量**：`context`はセッション開始・圧縮のたびに実行されるため、速度と出力の分量が直接体験に響く
- **安全性**：コミットされたフック設定は、cloneした他人の環境で自動的にコマンドを実行する。設定の中身は`mtqg`の呼び出しだけに留める
- **仕様の変化**：フックのイベントや入出力の形式はエージェント側の都合で変わりうる。アダプタを変えるときは、各ツールの公式ドキュメントで確認する
- **対話中の質問は、フックでは拾えない。** Claude Codeが人間に選択肢を聞く機能（`AskUserQuestion`）は、ツールのフックの対象外。対話で決まったことの記録は、AIが自分で`qa`を書く運用（指示ファイル）に任せる

### 11.4 人間向け：VSCode拡張

人間が作業の流れの中で記録し、状態と過程を見るための入口。**記録作成のアシストと、状態・過程の表示に絞る**。

#### UIを豊かにする理由：人間との作業のため

- **AIエージェントとの作業では、UIはほぼ必要ない**。AIは画面を見ず、MCPで記録し、フックで`context`を受け取れば足りる（11.2、11.3）
- **人間との作業で威力が出る**。人間には記録を強制できず、使いたくなる体験で1.6の問題を越えるしかない（1.6）
- 人間同士の質問や相談は、今はSlackやDiscordで行われ、流れて消えていく（1.1の「それぞれの主体に閉じた場所」の代表）。見慣れたチャットの形にすることで、**人がすでに持っている「チャットで相談する」習慣を、そのままリポジトリの中に持ち込める**。新しい作法を覚えさせる必要がない

#### UIの言語：英語、文字に頼らない

- UIの文言（ボタン、見出し、メニュー、通知）は**英語**（10.6）。入力と記録の中身は日本語など、どの言語でもよい
- そもそも**文字にあまり頼らないUIにする**。チェックボックス、アイコン、色、スレッドの形など、見れば分かる要素で状態を伝え、ラベルは最小限にする。そうすれば英語だけでも使う人を選ばない
- 翻訳の仕組み（多言語化）は持たない。普通に作れば英語で足りるはず

#### 原則：UIは豊かにするが、機能は足さない

- UIは、**過程を残すアシスト**として豊かにする。新しいデータや操作を増やすのではなく、すでにある記録を「書きやすく、見やすく」するためのもの
- 2.2の「仕組みと使われ方を分ける」の延長。仕組み（追記するだけ）は変えず、使われ方の側だけを磨く
- 参考にするUIの機能（Keepのリマインダー・色分け・ピン留め、Slackの通知・リアクション等）は真似ない。2.7の問い「課題を管理するための機能か、過程を残すための情報か」で判断する

#### 画面構成：ToDo・QA・Bugs・Rules・用語集の表と、Slack風のメモ

| 画面 | 形 | 表示範囲 |
|---|---|---|
| ToDo | Google Keep風のカード | 全件（デフォルトは未完了のみ） |
| QA | 表 | 全件（デフォルトは未回答のみ） |
| Bugs | 表（QAと同じ形） | 全件（デフォルトは未クローズのみ） |
| Rules | ただの表 | 全件 |
| 用語集 | ただの表 | 全件 |
| メモ | Slack・Discord風のタイムライン（他の種類も含む） | 最近の分から表示し、遡るときに読み込む |

- 6つの画面はタブで切り替える。どれも、CLIの`--json`が返す**同じデータの見え方**にすぎない
- **データモデルとの対応**：メモのタイムラインは、種類を問わずすべての記録を時系列で流す基本の画面。ToDo・QA・Bugs・Rules・用語集は、そこから種類ごとに取り出し、構造に合った形で見せる画面。5.1の「memoが基本、todo・qa・glossaryは構造を持つ派生、bugはqaと同じ構造、ruleは構造がmemoと同じで振る舞いがglossaryと同じ」、3章の名前の順序と同じ関係
- **種類を足したら、この表も見直す。** 画面の一覧は、種類の一覧と別の場所にあるので、種類を足しても自動では追いつかない
- 各画面の実際のレイアウト（列の配置、余白など）は、VSCode拡張のリポジトリで決める

**表示範囲の考え方**

- ToDo・QA・Bugs・Rules・用語は「管理する対象」なので、件数に自然な上限がある。未完了のToDoや未回答の質問が数百件という状態は、ツールの性能より先に人間の側が破綻する。用語集も数百語あれば大きな部類。**完了済み・回答済み・クローズ済みを含めても全件表示で困らない**
- メモは「流れていく記録」なので、件数に上限がない。ここだけSlackと同じく、最近の分から表示して遡るときに読み込む
- 件数が増え続けるものだけが、件数が増えても困らないUIになっている
- デフォルトをOpenのみにすることで、「今やるべきこと、答えるべきことが残っている」ことが一目で分かる。Keepで未完了のメモが並んでいた使用感にも近い

**ToDo：Google Keep風のカード**

使う側から見た「管理されている状態」（2.2）を見せる。

- チェックボックス付きのカードを並べる。チェックすれば完了（内部では状態変更の追記）
- デフォルトは未完了のみ。切り替えで完了済みも表示する

**QA：表**

- デフォルトは未回答の質問のみ。「答えるべきものが残っている」ことが一目で分かることが、この画面の一番大事な役割
- 切り替えで回答済みも表示する。質問を開くと回答が見える
- 「AIが推測で書いた回答」と「人間が確定させた回答」（5.2）を、小さなバッジで見分けられるようにする

**Bugs：表**

- QAと**同じ形の別画面**にする。モデル層の実装はqaと共通（5.1）だが、質問と不具合は読み手にとって意味が違うので、1つの画面で切り替えるより、画面を分けた方が探しやすい
- デフォルトは未クローズ（open）のみ。「対処すべき不具合が残っている」ことが一目で分かることが、QAと同じくこの画面の一番大事な役割
- 切り替えでクローズ済みも表示する。バグを開くと返信（やり取り）が見える

**Rules：ただの表**

- 用語集と**同じ「ただの表」の形**にする。ruleは`word`を持たないので列は本文・記録者・日付だけ
- 用語集と同じく**全件表示、archiveされない**（振る舞いが用語集と同じ・5.1）。メモのタイムラインに埋もれさせない（読めばそのまま従える決まり事を、流れていく記録の中に混ぜると見落とされる）

**用語集：ただの表**

- 用語、定義、記録者、日付の列
- 同じ用語が別々に定義されている場合（9章）だけ、並べて目立たせる

**メモ：Slack・Discord風のタイムライン**

チャットは、もともと追記だけで成り立っているUIであり、mtqgの仕組みと作法が一致する。

| チャットの見慣れた作法 | mtqgの仕組み |
|---|---|
| 新しい発言は下に追加され、過去の発言は動かない | 追記するだけ（2.3） |
| 発言を直すと「（編集済み）」と表示される | 訂正の事実を追記し、直したことを見せる（2.4） |
| 消すと「このメッセージは削除されました」と跡が残る | 削除の事実を追記し、消えないことを正直に見せる（2.5）。`log --json --events`が削除した記録も返す |
| 質問への返信がスレッドにぶら下がる | qaの回答は親への参照を持つ記録（5.1） |
| 発言者のアイコンと名前が並ぶ | 記録者（5.2）。人間とAIの記録が同じタイムラインに並ぶ |

利用者に仕組みを説明しなくても、チャットに慣れていれば自然に理解できる。人間とAIの記録が並ぶことで、1.1の「主体の軸」がつながっている様子も目に見える。

タイムラインには、memo以外の種類も構造が見える形で流れる。

- todoはチェックボックス付きの投稿として流れ、完了は「✓ Marked as done」という控えめな行で表示する
- qaはスレッドになり、回答は返信としてぶら下がる
- bugもスレッドになり、返信がぶら下がる（qaと同じ扱い）
- glossaryは「Defined a term」という投稿として流れる
- ruleは「Adopted a rule」という投稿として流れる（glossaryと対にした表現）

入力欄は、普段はmemoとして投稿し、`/todo`、`/qa`、`/bug`、`/glossary`、`/rule`のようなスラッシュコマンドで種類を書き分ける。新しい操作を足さず、見慣れた作法で書き分けられるようにする。

#### 提供する操作

- **記録作成**：メモのタイムラインの入力欄（スラッシュコマンドで種類を書き分け）や、各画面から、memo・qa・todo・bug・glossary・ruleを作る。記録者は自動で付ける。成果物の位置は付けない（ファイル名は本文に書く・5.5）
- **状態の操作**：ToDoのカード、QA・Bugsの表、タイムラインの投稿やスレッドから、完了・回答（返信）・訂正・削除を行う（いずれも内部では追記）

#### 実装

- 画面はVSCodeの**Webview**で作る。サイドバーやエディタのタブに、HTML・CSS・JavaScriptで作った画面を表示でき、VSCodeのテーマ色にも馴染ませられる
- データの解釈はCLIに任せる。拡張本体はCLIの`--json`出力と記録コマンドを呼び、Webviewは表示と操作に徹する（11.1）
- 本体とは別のリポジトリに置く（10.9）
- 対象はまずVSCode系のエディタ（Cursor等を含む）に絞る。他のエディタは必要になってから考える

採らない、または後で判断するもの：

- ファイル監視、警告表示など重いLSP機能は採らない（2.7）
- 用語へのホバーでglossaryの定義を表示する、他のエディタにも同じ機能を提供するためにLSP化する、といった機能は、2.6の基準で必要性が確認できてから検討する
- メンション（「この質問は誰に聞いているか」）は、過程を残す情報になりうるため、2.7の問いで判断する

### 11.5 gitとの接点：mtqgは何もしない

`.mtqg/`は普通のテキストファイルとしてコミットされるので、GitHub等のコミット画面やPRの差分には、**コードの変更と、追加された記録の行がそのまま並んで表示される**。

```
src/parser.go
- if (c == '/' && next == '/') {
+ if (c == '/' && (next == '/' || next == '*')) {

.mtqg/journal.jsonl
+ {"id":"7c1e9a3b5d2f4e6a8b0c1d2e3f4a5b6c","op":"create","type":"qa","status":"open","text":"ブロックコメントの入れ子に対応する？",...}
+ {"id":"e4b8d2f6a0c34e5b9d7f1a3c5e7b9d1f","op":"create","type":"qa","re":"7c1e9a3b5d2f4e6a8b0c1d2e3f4a5b6c","text":"初版では非対応。需要が出たら再検討",...}
```

これを見れば「このコード変更の背景には、この質問と回答がある」と誰でも分かる。**コードと過程の紐づけは、gitとGitHubが最初から持っている仕組みだけで成立する。**

- PR単位で見れば、記録とコードが別々のコミットに入っていても、PR全体の差分に両方が並ぶ
- レビュアーは記録の行に直接コメントできる
- コードから逆にたどる場合も、`git blame`でコミットを見つけ、その差分を見れば分かる

mtqgがすることは、**差分として読みやすい形で書き出す**ことだけ（7.2）。紐づけのための機能（トレーラーの規約、gitフック、履歴の解析）は作らない（2.7）。
