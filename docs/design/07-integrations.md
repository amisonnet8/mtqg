# mtqg 設計：外部ツール連携

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 11. 記録作成のアシスト：外部ツール連携

### 11.1 位置づけと構成の原則

外部ツール連携は、**残らない過程を残す作業のアシスト**（1.2）と、**「管理してくれている」体験**（2.4）のためにだけ用意する。2.7に挙げた、役割を超える連携は採らない。

- 補助ツールは**データ形式を自前で解釈しない**。解釈はGoのバイナリの1か所に集約する
- 使う相手ごとに入口を分けるが、中の共通コアとデータは1つ。どの入口から書いた記録も、どの入口からも同じように見える

| 相手 | 入口 | 1.6の「使わずに済ませられてしまう」の越え方 |
|---|---|---|
| AIエージェント | MCP、エージェントのフック | 仕組みで必ず読ませ、記録を促す。UIは要らない |
| 人間 | CLI、VSCode拡張（豊かなUI） | 使いたくなる体験にする |

```
mtqg（単一バイナリ）
 ├─ CLI       ── 人間（ターミナル）
 ├─ mtqg mcp  ── AIエージェント・AIアプリ（AI用の入口）
 ├─ mtqg hook ── エージェントのフックから呼ばれる
 └─ --json    ── エディタ拡張など
       ↓
    共通コア（モデル層 → ジャーナル層・10.7）
       ↓
    .mtqg/journal.jsonl ／ <git-dir>/mtqg/
```

### 11.2 AIエージェント向け：MCPサーバー（AI用の入口）

`mtqg mcp`としてMCPサーバーを提供する。人間にとってのCLIに当たる、AIにとって一番使いやすい入口。

- **起動**：AIエージェントがセッション開始時にサブプロセスとして起動し、標準入出力でやり取りする。常駐もネットワークのポートも使わない
- **公開する操作**：中心は記録作成（`memo_add`、`todo_add`、`todo_done`、`qa_ask`、`qa_answer`、`glossary_define`など）。読む側は`context`、`show`、`search`など必要な分だけ
- **記録者の自動付与**：接続時にクライアントが名乗る名前から、`author`を`{"kind":"ai","name":"claude-code"}`のように自動で付ける（5.2）
- **戻り値の分量**：AIのコンテキストに入るため、一覧はIDと要約にとどめ、詳細は`show`で取りに行く
- **対象リポジトリ**：起動時の作業ディレクトリから`git rev-parse`で特定する。複数のリポジトリを扱うAIアプリに備え、対象を明示できる引数も用意する
- **設定**：エージェントのプロジェクト設定（Claude Codeなら`.mcp.json`）に書く。コミットしておけば、cloneした人のエージェントも同じようにつながる

#### 実装（段階4b、2026-09-25）

`mtqg mcp`を実装した。設計から実際に変えた点・決めた点。

- **`internal/mcp/`は作らず`internal/cli/`に置いた。** MCPのハンドラが要るもの（エラーの文言、記録のJSONの形、`context`の文章、本文の正規化、ジャーナルの開き方）は、すべて既に`internal/cli/`に1か所ずつある。プロトコル層は依存ライブラリ（後述）が丸ごと引き受けるので、mtqgに残るのは「引数の解釈・文言・出力の形」だけで、これはCLIの層の役目。段階4aで`internal/hook/`を作らなかった判断（フックの出力が`context`の文章そのもの）と同じ構図。`.golangci.yaml`の`depguard`で、ジャーナル層・モデル層からSDKへのimportを禁じ、機械的な歯止めにした
- **MCPプロトコル（JSON-RPC 2.0、stdio）の実装は公式Go SDK`github.com/modelcontextprotocol/go-sdk`（Anthropic公式）を採用した。** CLAUDE.mdの依存ポリシー（標準ライブラリと`golang.org/x/`だけ）の例外として人間が承認。理由・実際に確定した依存の内訳・Trivyの結果は`PLAN.md`「段階4b」に記録した
- **対象リポジトリは、起動時の作業ディレクトリから1度だけ特定するのではなく、ツール呼び出しのたびに`.mtqg/`を探す。** この節の元の下書きは「起動時の作業ディレクトリから`git rev-parse`で特定する」だったが、これだとサーバー起動後に`mtqg init`されたリポジトリを見つけられない。毎回探す形にすると、サーバー起動の失敗ではなくツールごとのエラー（`not_initialized`）として自然に扱え、実装も単純になる。複数のリポジトリを扱うAIアプリ向けの明示的な引数は、既存のグローバルオプション`-C`をそのまま使うことにし、専用の引数は作らなかった
- **公開するツールは18個。** 設計の例（`memo_add`・`todo_add`・`todo_done`・`qa_ask`・`qa_answer`・`glossary_define`）に、`rule_add`・`bug_report`・`bug_reply`・各種の`done`/`reopen`・`edit`を加えた（`edit`は人間の要望で追加。`$EDITOR`を開かず、新しい本文を引数で受け取る）。`delete`・`undo`・`archive`・`review`・`format`は公開しない（破壊的・複雑な操作をAIの判断だけで実行させないため）。**質問と回答、バグと返信は別ツールにした**：CLIの`qa add`は最初の語がIDらしいかで質問か回答かを決めるが（設計§4.5）、MCPのツールは入力欄でID・本文を区別できるので、この判定を使わない
- **ツールの結果は、対応するCLIコマンドの`--json`と同じJSONオブジェクトにした**（`context`・`search`は分量のため専用の形）。形の約束を`cli.md`の1か所に保つため。エラーはJSON-RPCのプロトコルエラーにせず、ツール結果（`isError:true`）として、`--json`が標準エラー出力に書くのと同じ`{"error":{...}}`の形で返す（サーバー自体は動き続ける）
- **記録者**：`author.kind`は常に`ai`、`author.name`は接続時の`clientInfo.name`。`MTQG_AUTHOR_*`やgitのuser.nameは見ない（人間の環境変数をAIの記録に引き継がない、という既存の原則と同じ）

### 11.3 AIエージェント向け：エージェントのフック

#### 位置づけ

- **フックという仕組みそのものはエージェント側の機能**。「いつ呼ぶか」はClaude Code等のエージェントが決める
- **mtqgが用意するのは、フックから呼ばれるコマンドと、それを設定する導入コマンド**
- MCPとの役割分担：MCPは「AIが自分の判断で使う入口」。フックは**読み込みと記録漏れの確認を、AIの判断に頼らず必ず行わせる**。何を記録するかの判断はAIにしかできないため、記録そのものはMCPでAIに任せる

#### 想定する使われ方（Claude Codeの例）

| タイミング | エージェント側のフック | mtqgがすること |
|---|---|---|
| セッション開始 | SessionStart | `context`を生成し、AIのコンテキストに入れる |
| コンテキスト圧縮の直後 | SessionStart（compact時） | `context`を入れ直す。記録済みの過程は圧縮を越えて残る |
| 応答の終了 | Stop | 記録漏れの可能性があれば、終了を止めて記録を促す |

#### mtqgとして用意する機能

| 機能 | 役割 | エージェント依存 |
|---|---|---|
| `mtqg context`（分量指定つき） | 入れる中身を作る | なし |
| セッションの記録と判定 | 終了時に記録を促すべきか判断する | なし |
| `mtqg hook <agent> <event>` | エージェントとの入出力を変換する | あり |
| `mtqg init --agent <agent>` | エージェントの設定ファイルに書き込む | あり |

エージェント依存の部分（アダプタ）は薄く保ち、判断はすべて依存しない共通機能に置く。

**1. `mtqg context`（分量指定つき）**

- `--max-tokens`のような分量の上限を指定できる
- 上限を超える場合の優先順位を決めて削る（例：未回答・未確定のqa → 未完了のtodo → glossary → 新しいmemo → 古いmemo）
- セッション開始のたびに実行されるため、一瞬で終わること

**2. セッションの記録と判定**

- セッション開始時に、セッションIDと開始時刻を記録する
- 終了時に、開始時刻以降にこの記録元から記録が書かれたかを数える
- 記録を促すのは「記録が0件」かつ「一定の作業が行われた」ときだけ（判定方法は要検討）
- 一度促したセッションには印を付け、二度目は促さない
- この状態はコミット不要（`.mtqg/.local/sessions/`。2026-09-19の決定、下の「実装」参照。`<git-dir>/mtqg/`は使わない）

```
.mtqg/.local/sessions/<session-id>.json
  {"started_at": "...", "head": "...", "status_digest": "...", "prompted": false}
```

**3. `mtqg hook <agent> <event>`（アダプタ）**

1. エージェントが標準入力に渡すJSON（セッションID、作業ディレクトリ等）を読む
2. 1・2の共通機能を呼ぶ
3. 結果をそのエージェントが期待する形式で出力する

```
mtqg hook claude-code session-start
  入力: {"session_id":"abc","cwd":"...","source":"startup"}
  処理: セッション開始を記録 → context を生成
  出力: context のテキスト

mtqg hook claude-code stop
  入力: {"session_id":"abc","stop_hook_active":false,...}
  処理: 開始以降の記録件数を判定
  出力: 促す必要あり → {"decision":"block","reason":"Record any unrecorded questions or decisions with mtqg"}
        不要         → 何も出さない
```

**4. `mtqg init --agent <agent>`（導入コマンド）**

- エージェントの設定ファイル（Claude Codeなら`.claude/settings.json`と`.mcp.json`）に、フックとMCPの設定を書き込む
- 指示ファイル（CLAUDE.md、AGENTS.md等）への一行の追記もまとめて行う
- 既存の設定を壊さずに追記し、何度実行しても重複しない。`--dry-run`で書き込む内容を事前に表示する
- 書き込むのはエージェントの設定ファイルであり、gitの設定には触れない（4.3）

**使う側から見た姿**：`mtqg init --agent claude-code`を一度実行するだけで、以後はセッション開始時に経緯が読み込まれ、圧縮後も経緯が戻り、終了時に記録漏れが確認される。

#### 注意点

- **速さと分量**：`context`はセッション開始・圧縮のたびに実行されるため、速度と出力の分量が直接体験に響く
- **安全性**：コミットされたフック設定は、cloneした他人の環境で自動的にコマンドを実行する。設定の中身は`mtqg`の呼び出しだけに留める

#### 実装（段階4a、2026-09-25）

`mtqg hook claude-code`（`session-start`・`stop`）と`mtqg init --agent claude-code`を実装した。MCP（11.2）とVSCode拡張（11.4）は次の区切りに送った。上の設計から実際に変えた点・決めた点。

- **セッションの状態は`.mtqg/.local/sessions/`に置いた（上のコード例も直した）。** この節の元の下書きは`<git-dir>/mtqg/sessions/`と書いたままだったが、2026-09-19（`history.md`）の時点で既に「`<git-dir>/mtqg/`を廃止し`.mtqg/.local/`に移す」と決めていた（セッションの記録も名指しで含めて）。実装時に見つけた古いままの記述をここで直した。gitの私的な領域には何も置かない（`.claude/rules/git-integration.md`）という線引きとも合う。セッションIDをファイル名にしているため、複数のworktreeが同じ`.mtqg/.local/sessions/`を共有しても衝突しない
- **セッションIDはファイル名にそのまま使わない。** `[A-Za-z0-9_-]`だけの短い文字列ならそのままファイル名にし、それ以外（記号や長すぎるもの）はsha256の先頭16桁にする。エージェントが渡すIDを無条件でパスに使うと`..`のような値が渡ったときに危ういため（`os.Root`が`.mtqg/`の外へは出さないので実害はないが、二重の備えとして）
- **`stop`が促す条件の実装**：セッション開始時の`git rev-parse HEAD`と`git status --porcelain -z`（`.mtqg/`を含む行を除いてダイジェスト化したもの）を覚えておき、`stop`のたびに読み直して比べる。「記録が0件」の判定は、`journal.jsonl`の全イベント（誰が書いたかを問わない）の`ts`がセッション開始時刻以降かどうかで見る。**落とし穴**：イベントの`ts`は秒精度だが、セッション開始時刻はフックの時計（サブ秒まで持つ）をそのまま記録していたため、開始と同じ秒に書かれた記録が「開始より前」と誤判定されることがあった（丸めの向きの問題）。`model.ShouldPrompt`で比較直前にセッション開始時刻を秒へ切り詰めて解消した（`.claude/rules/testing.md`に記録）
- **`--json`を持たない。** `hook`の出力はエージェント自身のフックの約束事で決まり、mtqg独自の形にする余地がないため、cli-output.mdの「すべてのコマンドに`--json`を用意する」の例外とした
- **`mtqg init --agent`は`.mcp.json`をまだ書かない**（MCPサーバーが無いため）。`.claude/settings.json`の`hooks`と`env`、`CLAUDE.md`への1行だけ
- **既存の設定を壊さない実装**：`.claude/settings.json`は`map[string]any`に読み、変更したい部分だけ触ってから書き戻す。書き戻しはキーをアルファベット順に並べる（`encoding/json/v2`の`Deterministic`オプション）。**手書きのファイルは初回だけキーの並びが変わる**（2回目以降は変化がなければ書かない）。設計時点で考えていた「既存の並びを保ったまま書き戻す」（トークン単位の編集）は実装の手間に見合わないと判断し、単純化した
- **仕様の変化**：フックのイベントや入出力の形式はエージェント側の都合で変わりうる。アダプタ実装時に各ツールの公式ドキュメントで確認する

#### 実地配線と確認（段階4a、2026-09-25）

マージ後、このリポジトリ自身に`mtqg init --agent claude-code`を実行して配線した（安定版バイナリ、`-n`で差分を確認してから本実行）。`SessionStart`は次のセッションの開始で実地に確認できた：`SessionStart:resume`が発火し、`mtqg context`の内容がそのままセッション冒頭に入った。

`Stop`は、判定ロジックの動作は確認できたが、実際のセッションでの目視確認は手段が無く打ち切った。記録せずに応答を終える実験を重ねる過程で、判定の性質が2つ実地で分かった：①セッション開始より前からあった未コミットの変更は「セッション中の作業」としてカウントされない（`start`と`now`のGitStatusDigestが同じまま）。②既に変更済みのファイルへさらに追記しても`git status --porcelain`の行自体は変わらないため、StatusDigestも変わらない（ファイル単位の変更検出で、diffの中身までは見ない）。いずれも設計どおりの挙動。この2つを踏まえて条件（セッション開始後に未変更のファイルへ触れる）を揃えても、会話上に促しは現れなかった。`.mtqg/.local/sessions/`のファイルから使われていそうな`session_id`を推測し、`mtqg hook claude-code stop`をその入力で手動シミュレートしたところ、`{"decision":"block","reason":...}`が正しく返り、判定ロジック自体は動くと確認できた。ただし、**Claude Codeが実際にフックへ渡す`session_id`はエージェント（Claude Code自身）からは見えない**ため、この推測が実セッションのものだったかは確認できていない。

### 11.4 人間向け：VSCode拡張

人間が作業の流れの中で記録し、状態と過程を見るための入口。**記録作成のアシストと、状態・過程の表示に絞る**。

#### UIを豊かにする理由：人間との作業のため

- **AIエージェントとの作業では、UIはほぼ必要ない**。AIは画面を見ず、MCPで記録し、フックで`context`を受け取れば足りる（11.2、11.3）
- **人間との作業で威力が出る**。人間には記録を強制できず、使いたくなる体験で1.6の問題を越えるしかない（1.6）
- 人間同士の質問や相談は、今はSlackやDiscordで行われ、流れて消えていく（1.1の「それぞれの主体に閉じた場所」の代表）。見慣れたチャットの形にすることで、**人がすでに持っている「チャットで相談する」習慣を、そのままリポジトリの中に持ち込める**。新しい作法を覚えさせる必要がない

#### UIの言語：英語、文字に頼らない

- UIの文言（ボタン、見出し、メニュー、通知）は**英語**（10.6）。入力と記録の中身は日本語など、どの言語でもよい
- そもそも**文字にあまり頼らないUIにする**。チェックボックス、アイコン、色、スレッドの形など、見れば分かる要素で状態を伝え、ラベルは最小限にする。そうすれば英語だけでも使う人を選ばない
- 翻訳の仕組み（多言語化）は持たない。普通に作れば英語で足りるはず

#### 原則：UIは豊かにするが、機能は足さない

- UIは、**過程を残すアシスト**として豊かにする。新しいデータや操作を増やすのではなく、すでにある記録を「書きやすく、見やすく」するためのもの
- 2.2の「仕組みと使われ方を分ける」の延長。仕組み（追記するだけ）は変えず、使われ方の側だけを磨く
- 参考にするUIの機能（Keepのリマインダー・色分け・ピン留め、Slackの通知・リアクション等）は真似ない。2.7の問い「課題を管理するための機能か、過程を残すための情報か」で判断する

#### 画面構成：ToDo・QA・用語集の表と、Slack風のメモ

| 画面 | 形 | 表示範囲 |
|---|---|---|
| ToDo | Google Keep風のカード | 全件（デフォルトは未完了のみ） |
| QA | 表 | 全件（デフォルトは未回答のみ） |
| 用語集 | ただの表 | 全件 |
| メモ | Slack・Discord風のタイムライン（他の種類も含む） | 最近の分から表示し、遡るときに読み込む |

- 4つの画面はタブで切り替える。どれも、CLIの`--json`が返す**同じデータの見え方**にすぎない
- **データモデルとの対応**：メモのタイムラインは、種類を問わずすべての記録を時系列で流す基本の画面。ToDo・QA・用語集は、そこから種類ごとに取り出し、構造に合った形で見せる画面。5.1の「memoが基本、todo・qa・glossaryは構造を持つ派生」、3章の名前の順序と同じ関係

**表示範囲の考え方**

- ToDo・QA・用語は「管理する対象」なので、件数に自然な上限がある。未完了のToDoや未回答の質問が数百件という状態は、ツールの性能より先に人間の側が破綻する。用語集も数百語あれば大きな部類。**完了済み・回答済みを含めても全件表示で困らない**
- メモは「流れていく記録」なので、件数に上限がない。ここだけSlackと同じく、最近の分から表示して遡るときに読み込む
- 件数が増え続けるものだけが、件数が増えても困らないUIになっている
- デフォルトをOpenのみにすることで、「今やるべきこと、答えるべきことが残っている」ことが一目で分かる。Keepで未完了のメモが並んでいた使用感にも近い

**QA：表**

- 切り替えで回答済みも表示する。質問を開くと回答が見える

**メモ：Slack・Discord風のタイムライン**

チャットは、もともと追記だけで成り立っているUIであり、mtqgの仕組みと作法が一致する。

| チャットの見慣れた作法 | mtqgの仕組み |
|---|---|
| 新しい発言は下に追加され、過去の発言は動かない | 追記するだけ（2.3） |
| 発言を直すと「（編集済み）」と表示される | 訂正の事実を追記し、直したことを見せる（2.4） |
| 消すと「このメッセージは削除されました」と跡が残る | 削除の事実を追記し、消えないことを正直に見せる（2.5） |
| 質問への返信がスレッドにぶら下がる | qaの回答は親への参照を持つ記録（5.1） |
| 発言者のアイコンと名前が並ぶ | 記録者（5.2）。人間とAIの記録が同じタイムラインに並ぶ |

利用者に仕組みを説明しなくても、チャットに慣れていれば自然に理解できる。人間とAIの記録が並ぶことで、1.1の「主体の軸」がつながっている様子も目に見える。

タイムラインには、memo以外の種類も構造が見える形で流れる。

- todoはチェックボックス付きの投稿として流れ、完了は「✓ Marked as done」という控えめな行で表示する
- qaはスレッドになり、回答は返信としてぶら下がる
- glossaryは「Defined a term」という投稿として流れる

入力欄は、普段はmemoとして投稿し、`/todo`、`/qa`、`/glossary`のようなスラッシュコマンドで種類を書き分ける。新しい操作を足さず、見慣れた作法で書き分けられるようにする。

#### 提供する操作

- **記録作成**：メモのタイムラインの入力欄（スラッシュコマンドで種類を書き分け）や、各画面から、memo・qa・todo・glossaryを作る。選択範囲やカーソル位置から作った場合は、成果物の位置（5.5）を自動で付ける。記録者は自動で付ける
- **状態の操作**：ToDoのカード、QAの表、タイムラインの投稿やスレッドから、完了・回答・訂正・削除を行う（いずれも内部では追記）

#### 実装

- 画面はVSCodeの**Webview**で作る。サイドバーやエディタのタブに、HTML・CSS・JavaScriptで作った画面を表示でき、VSCodeのテーマ色にも馴染ませられる
- データの解釈はCLIに任せる。拡張本体はCLIの`--json`出力と記録コマンドを呼び、Webviewは表示と操作に徹する（11.1）
- 対象はまずVSCode系のエディタ（Cursor等を含む）に絞る。他のエディタは必要になってから考える

採らない、または後で判断するもの：

- ファイル監視、警告表示など重いLSP機能は採らない（2.7）
- 用語へのホバーでglossaryの定義を表示する、他のエディタにも同じ機能を提供するためにLSP化する、といった機能は、2.6の基準で必要性が確認できてから検討する
- メンション（「この質問は誰に聞いているか」）は、過程を残す情報になりうるため、2.7の問いで判断する

### 11.5 gitとの接点：mtqgは何もしない

`.mtqg/`は普通のテキストファイルとしてコミットされるので、GitHub等のコミット画面やPRの差分には、**コードの変更と、追加された記録の行がそのまま並んで表示される**。

```
src/parser.go
- if (c == '/' && next == '/') {
+ if (c == '/' && (next == '/' || next == '*')) {

.mtqg/journal.jsonl
+ {"id":"b21c09-7","op":"create","type":"qa","status":"open","text":"ブロックコメントの入れ子に対応する？",...}
+ {"id":"b21c09-9","op":"create","type":"qa","re":"b21c09-7","text":"初版では非対応。需要が出たら再検討",...}
```

これを見れば「このコード変更の背景には、この質問と回答がある」と誰でも分かる。**コードと過程の紐づけは、gitとGitHubが最初から持っている仕組みだけで成立する。**

- PR単位で見れば、記録とコードが別々のコミットに入っていても、PR全体の差分に両方が並ぶ
- レビュアーは記録の行に直接コメントできる
- コードから逆にたどる場合も、`git blame`でコミットを見つけ、その差分を見れば分かる

mtqgがすることは、**差分として読みやすい形で書き出す**ことだけ（7.2）。紐づけのための機能（トレーラーの規約、gitフック、履歴の解析）は作らない（2.7）。

### 11.6 作る順番の案

11章の外部ツール連携は、**CLIを完成させ、サンプルPJで問題を吸収した後（v0.2）**に着手する（12.2の段階4）。ここからmtqg自身の開発にもmtqgを使う。この開発で出た問題が片付いたらv1とする（12.4）。

1. AIエージェント向けの組み込み（指示ファイル → フック → MCP）
2. VSCode拡張（記録作成と一覧）

AI側を先にするのは、記録の多くがAIとのやり取りから生まれるため。人間側の記録の摩擦がつらくなってきたら、VSCode拡張の順番を前に出す。**人間と一緒に作業するプロジェクトに導入する段階では、VSCode拡張は必須になる**（11.4）。

各機能が本当に必要か、どこまで必要かは、推測ではなく、サンプルPJで集めた「11章で解くべき問題」（12.3）をもとに決める。
