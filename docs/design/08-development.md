# mtqg 設計：開発の進め方と先行事例

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/` が正**であり、食い違う場合は reference に従う。節番号（§N.N）は設計文書全体で通し番号になっている。

## 12. 開発の進め方

### 12.1 方針：CLIを完成させてから、mtqg自身にmtqgを導入する

当初は「簡易的な実装を作り、mtqgの開発そのものにmtqgを使いながら収束させる」としていたが、撤回する。

**CLIを先に完成させ、別のサンプルPJで使って問題を吸収する。mtqg自身への導入は、その後の外部ツール連携（11章）の開発から始め、その開発で出た問題まで片付けてから、データ形式をv1として確定する。**

理由：

- **試す場と本番の記録が分かれる**：サンプルPJのデータは使い捨てにできるので、スキーマを何度変えても、過去データを書き換えても構わない。mtqg本体の記録（11章の開発中）はv0の形式で書き、v1確定時にAIがv1の形式へ一度だけ変換する（12.4）。v1以降は「追記だけ」の原則（2.3、5.6）を守る
- **11章の開発でも形式の不満が出る**：MCPやフックから記録すると、CLIだけでは見えなかったデータ形式の不足が出うる。それを吸収してからv1にする
- **使ってみて初めて分かる不満を、形式を固める前に吸収できる**
- **記録する対象と使う道具が一致する**：11章の機能はどれも「記録の摩擦を下げる」ためのもの。CLIだけで記録しながらそれらを作ると、どこに摩擦があるかを作り手自身が体験しながら作れる。これが本当の意味でのドッグフーディングになる
- **AIとの作業の記録がちょうど始まる**：MCPやフックの開発はAIエージェントと進めるため、mtqgが残したい「AIに聞かれて、こう答えた」が大量に生まれる時期から使い始めることになる

### 12.2 段階

| 段階 | すること | 区切り | mtqg自身の記録 |
|---|---|---|---|
| 1. CLIを作る | 記録作成、表示、`context`、`status`、`--json`出力、シェル補完。最初からジャーナル層・モデル層・CLIの層を分けて書く（10.7） | 完了で**v0.1** | 使わない（従来通りPLAN.md・このメモ） |
| 2. サンプルPJで使う | 別のサンプルPJにmtqgを導入し、CLIだけで記録しながら開発する | | 使わない |
| 3. 問題を吸収する | 出た問題をCLIに反映する。2と3を繰り返す | 完了で**v0.2**（12.4） | 使わない |
| 4. 外部ツール連携 | 11章の機能を、mtqgで記録しながら開発する（11.6） | | **ここから使う**（v0の形式） |
| 5. 問題を吸収する | 4で出た問題を片付ける。4と5を繰り返す | 完了で**v1**（12.4） | 使う |
| 6. v1を確定する | 4〜5の記録をAIがv1の形式に変換し、形式をv1として確定する | | 使う（v1の形式） |
| 7. 移行 | PLAN.md等によるルール運用から完全に移行する | | 使う |

段階1〜3の経緯は、従来通りPLAN.mdやこのメモに残す。段階4でmtqg本体に導入するとき、そこから大事な判断だけをmemoやqaとして初期記録に書き起こす。これも追記なので原則に反しない。

（ここでのv0.1・v0.2・v1はmtqg本体の区切り。CLI設計の文書の版番号「CLI検討案（v0.2）」とは別物）

### 12.3 サンプルPJ

**選び方**：mtqgの弱点が表に出る場面を含むものにする。

- 何日かにわたり、**セッションをまたいで**進む（1.1の時間の軸）
- 仕様を決めながら進み、**質問・判断・用語の合意が自然に生まれる**。作り方が決まりきったものだとmemoとtodoしか使わず、qaやglossaryが試せない
- **AIエージェントと一緒に**作る（主体の軸）
- 少しでよいので、**ブランチ・worktree・別の端末**で並行して記録する（場所の軸）。記録元ID（6章）、unionマージ（7.4）、並行した状態変更の表示（7.6）はここでしか試せない
- 規模は、数日から2週間程度で終わり、仕様に少し迷いどころがあるもの。小さすぎると問題が出ず、大きすぎるとCLIの改善が進まない

**AIエージェントにもCLIで記録させる**：指示ファイルに「作業開始時に`mtqg context`を読むこと」「質問や決定が生じたら`mtqg`で記録すること」と書き、MCPもフックもない状態で使わせる。

**出た問題は2つに分けて残す**：

| 分類 | 例 | 行き先 |
|---|---|---|
| CLIで直すもの | コマンドが分かりにくい、表示が足りない、データ形式の不足 | 段階3でCLIに吸収する |
| 11章で解くもの | AIが記録を忘れる、`context`を読まない、引数を間違える、人間が記録を面倒に感じる | 段階4の要否と範囲を決める材料にする |

後者は、MCPやフックが本当に必要か、どこまで必要かを推測ではなく体験から決めるための実例になる。

**評価の物差し**：1.2の理想（体験はほぼ同じで、記録がもっと細かく、リポジトリに残る）に照らし、「Google Keepに手で書いていたときより楽になったか」「Keepに戻りたくならないか」を自分の体験として判断する。

#### 12.3.1 qsokuからの報告（2026-09-23）

サンプルPJに選んだqsoku（`/home/vscode/qsoku`。開発時は`/workspaces/qsoku`にマウント。`PLAN.md`「段階2：サンプルPJ」参照）を、amisonnet8とClaude Codeが2026-09-23の1日・9ステップ（仕様執筆→qsokufileの解析→`//`置き換え→実行→管理用コマンド→シェル連携・補完→e2e→docsの実測→仕上げ）で最後まで作り切り、報告を受け取った。記録の内訳：memo 25、todo 10、question/answer 30、bug 2、glossary 4（削除した検証用の記録を含む、大まかな件数）。記録者は一貫してqsoku側で`MTQG_AUTHOR_KIND=ai`・`MTQG_AUTHOR_NAME=claude-code`と`amisonnet8`（人間）。各項目のIDは、qsoku側の`.mtqg/journal.jsonl`（このリポジトリの外）を指す。

**CLIで直すもの（段階3で吸収する候補）**

1. **`mtqg t --help`が種類別のヘルプを出さない。** `t`（`todo`の1文字略記）と`--help`を組み合わせても、全コマンド共通のヘルプがそのまま出る。todoの使い方だけを知りたいときに紛らわしい（memo `1afa42ad87`）
2. **`mtqg log`で、閉じたqaの質問側は暗くなるが回答側は暗くならない。** 人間からの指摘：`question`の行は閉じると暗くなるが、対応する`answer`の行は暗くならない。同じ組として一緒に暗くなってほしい（memo `1494f7982c`、人間の記録）
3. **同じ記録への並行した変更（ステータス変更と本文編集）自体には、`mtqg review`も`mtqg status`も印を付けない。** worktree側で1つのtodoを`done`、main側で同じtodoの本文を`edit`、両方コミットして`git merge --no-ff`すると、unionマージ自体は衝突なく成功するが、`mtqg review`は何も報告せず、`mtqg status`にも変化が出ない。`mtqg show <id>`の履歴を読んで初めて`create → status open→done → edit`の順に気づける。**一方、同じglossary語を両側で別の定義文で`g add`した場合は、`mtqg review`の「Duplicate glossary definitions」に3つの定義（元・worktree・main）が正しく並んで検知された。** つまり「並行した状態変更の表示」は、今のところ**glossaryの重複定義**という形でしか実地で機能を確認できておらず、todo/qa/bugのような「同じ記録への並行編集」を検知・表示する経路が無い（memo `2b4deeb094`・`eca203d5a1`）

**MCP・フックで解くもの（段階4の要否の材料）**

1. **対話中の質問・回答がmtqgに自動では残らない。** AIが手で`q add`→`q add <id> <回答>`→`q done`と写す必要があり、写し忘れのリスクがある。人間から明示的に「質問・回答・doneをその場で記録してほしい。`mtqg q list`で後から振り返れるようにしたい。これがほしかった機能」という要望があり、qsoku側の運用ルールに書いて対応した。**対話ツールの呼び出しとその回答を自動で`q`として残せるフックやラッパーがあれば、この手作業自体が不要になる**（memo `221e36add2`。この要望自体が「11章で解くもの」の具体的なユースケース）
2. **memoとbugの使い分けをAIが自分では一貫させられなかった。** 実装の欠陥をその場で直したケースで、最初`memo`にのみ記録し、人間から「`mtqg bug`に登録しないのか？基準は？」と指摘されて初めて`bug`として記録し直した。「もう直したから記録は軽くていい」という判断バイアスがあり、"見つけた時点でbugかどうか"を機械的に判定させる後押し（例：修正を伴うコード変更のコミットがあれば`bug`を提案するフック）があるとよいかもしれない（bug `95dc1bcf38`）
3. **手作業の変異確認（mutation-check相当）で、「生き残ったが実は無意味なテスト」を見つけられた一方、機械的な仕組みがあればもっと網羅的にできたはず。** エスケープ処理を無効化する変異に対してテストケースがたまたま出力が同じになり検知できなかった例があった（作り直して検知）（memo `86f1cab280`）

**うまく機能したこと**

- `mtqg context`の「Attention」欄：`.mtqg/`を`init`した直後、コミット漏れの記録に「1 mtqg record is not committed」という形で実際に気づけた（memo `c660369683`）
- `.gitattributes`の`merge=union`による`journal.jsonl`の自動マージ：2回の並行記録シナリオとも、ファイル自体の衝突は一度も起きなかった
- `q list`での質問・回答の振り返り：仕様執筆時の8件の質問（文字種・重複名・コメント処理・補完方式・CIのOS・`$EDITOR`のフォールバック・終了コードなど）はすべてここから拾い直せた
- `mtqg context`を各ステップの起点にする運用：進捗管理文書（PLAN.md相当）を一切作らず、todoの開閉状況とmemoだけで9ステップを最後まで通せた
- 未回答質問・未解決bugの新しい3件を要約から必ず残す仕様（段階1 Step 5の決定）：todoが多い段階でも質問が要約から消えることはなかった

**評価の物差しについて：** 「Google Keepに手で書いていたときより楽になったか」の判断は、AI（Claude Code）自身では判断しきれない人間の作業感覚に依る部分が大きく、空欄のまま人間の判断に委ねられた。AI側の実感としては、`mtqg context`への集約と`q list`での振り返りは明確にPLAN.md相当の文書より楽だったが、質問・回答の手作業での記録（MCP項目1）は毎回のオーバーヘッドとして残った。

この報告を踏まえた段階3着手の判断は`PLAN.md`「段階2：サンプルPJ」に記録する。

### 12.4 区切りの条件（決定）

段階ごとの繰り返しは終わりなく続けられてしまうため、区切りを先に決めておく。

| 区切り | 条件 |
|---|---|
| **v0.1** | CLI（段階1の範囲）ができた |
| **v0.2** | サンプルPJを1つ最後までやり切り、その間に出た「CLIで直すもの」（12.3）が片付いた |
| **v1** | 11章の機能をmtqgで記録しながら開発し（11.6）、その間に出た問題が片付いた |

**v1確定前のデータ形式（v0）**

- v1確定前は、`.mtqg/version`を`0`、各行の`v`を`0`とする。**0は「形式が未確定」を意味する**
- v0の間は、形式を変えても`version`を上げず、過去の行の書き換え・破棄・変換を許す（5.6の原則はv1から適用）
- サンプルPJ（段階2〜3）のデータは使い捨てにしてよい

**v1確定時の変換**

段階4〜5でmtqg自身に記録したデータは、捨てずに**AIがv1の形式へ変換する**。

- まず`.mtqg/SCHEMA.md`をv1として書き起こす（5.3）。変換はこのSCHEMA.mdを仕様としてAIに行わせる
- `id`・`ts`・`origin`・`author`は変えない。変えるのは形式（フィールド名、構造、`v`）だけで、記録の中身は変えない
- 変換後、mtqgのv1の実装で全行が警告なく読めること、変換前後で件数と状態（未完了・未クローズ）が一致することを確かめる
- 変換と`.mtqg/version`を`1`にする変更は、1つのコミットにまとめる。変換前の形はgitの履歴に残る
- これはv0からv1への一度きりの作業で、`mtqg upgrade`（5.6、v1以降の形式の変更用）とは別に扱う

## 13. 先行事例（設計判断の比較対象）

- **git-bug**：課題をgitオブジェクトとして分散管理し、専用refに保存。論理時計で順序付け。mtqgは、版管理やgit運用への負荷に踏み込むこれらの方式を採らない（4.2、7.5）
- **Beads**（Steve Yegge）：コーディングエージェント向けの課題トラッカーで、JSONLをリポジトリ内に置きgitで共有する。連番IDでの衝突からハッシュベースIDへ移行した経緯があるとされる（要確認）。6章と同じ問題の実例

mtqgの独自性：

- 課題（todo）に限らず、memo・qa・glossaryを含めた、成果物に残らない過程全体を扱う
- 版管理はgitに任せ、自らは「追記するだけ」と「記録作成のアシスト」に徹する
- 重複や食い違いを、エラーではなく事実として見せる
