# mtqg 設計：CLI

> 設計時点の判断と、その理由の記録。**現在の仕様は `docs/reference/cli.md` が正**であり、食い違う場合は reference に従う。

> **種類は6つになった**（bugを2026-09-21、ruleを2026-09-25に追加。`history.md`）。この文書は4種類の時点で書かれており、qaについての記述（4章、`done`・`reopen`がtodoとqaにあること、`log`が束ねる種類など）は、bugにもそのまま当てはまる。ruleは構造がmemoと同じで、`docs/design/03-data-model.md`§5.1に理由がある。過去の理由は書き換えずに残してある。

旧「CLI検討案」。設計§12.2「段階1：CLIを作る」で作るもののたたき台として書かれた。サンプルPJ（設計§12.3）で使って直し、v1で確定する。

本文中の「CLI設計§N」と括弧内の番号（4.5など）はこの文書の節を指す。「設計§N」は、他の設計文書の節を指す。

前提となる原則（設計文書より）：

- 追記するだけ。版管理はgitに任せる（設計§2.3）／gitの運用には何も要求しない（設計§4.3）
- 使う側には「管理してくれている」ように見せる（設計§2.4）
- 記録作成は手厚くアシストし、読む側は必要な分だけ（設計§5.4）
- **一番残したいのは「作業に取り掛かるときの気づき」**。書き込みの速さが最優先

## 1. 設計の方針

| 方針 | 理由 |
|---|---|
| 体系は`mtqg <種類> <動詞>`で統一する | 種類ごとにできることが違う（qaにdone、memoにdoneがない等）ので、コマンドも種類で分ける |
| **動詞は6語に絞る** | 種類ごとに違う単語を覚えるのが面倒。`ask`→`add`、`answer`→`add`、`close`→`done`に寄せた |
| 登録は**引用符なしの1行**で書ける | 気づきは数秒で消える。`"`を打つ手間すら惜しい |
| 種類名は**1文字に略せる**（`m`/`t`/`q`/`g`） | 体系は崩さず、入力だけ短くする。例外規則は作らない |
| 読む側は**人間向け表示と`--json`の二重化** | 補助ツールは`--json`を使う（設計§10.5） |
| gitには**触らない** | コミットもpushもしない（設計§4.3） |

覚える動詞は`add`・`done`・`reopen`・`list`・`edit`・`delete`の**6語だけ**。
うち4語（`add`・`list`・`edit`・`delete`）は4種類すべて共通で、`done`・`reopen`だけがtodoとqaにある。

## 2. コマンド全体

| | memo (m) | todo (t) | qa (q) | glossary (g) |
|---|---|---|---|---|
| **add**（登録） | `add <本文>` | `add <本文>` | `add <質問>` | `add <用語> <定義>` |
| **add**（回答） | — | — | `add <質問id> <回答>` | — |
| **done** | — | `done <id>` | `done <質問id>` | — |
| **reopen** | — | `reopen <id>` | `reopen <質問id>` | — |
| **list** | 全件 | 未完了（`--all`で全件） | 未クローズ（`--all`で全件） | 全件 |

`edit`と`delete`は、どの種類でも「IDを渡して本文を直す／消す」だけで違いがないため、**種類なしのコマンド**にした（下記）。種類が要るのは「書くとき」と「見るとき」だけで、IDがあるなら種類は要らない。

### 種類をまたぐコマンド

| コマンド | 内容 |
|---|---|
| `mtqg edit <id> <本文>` | 記録を直す（glossaryは定義を直す。用語名は変えられない） |
| `mtqg delete <id>` | 記録を消す（表示から除外。gitの履歴には残る） |
| `mtqg status` | 概況と、未コミットの記録の件数 |
| `mtqg log [--limit N] [--kind K]` | 4種類を時系列で束ねて見る |
| `mtqg show <id>` | 1件の詳細とイベント履歴 |
| `mtqg search <語>` | 本文の部分一致 |
| `mtqg context [--max-tokens N]` | AI・フック向けの要約（設計§11.3） |
| `mtqg review` | 並行した状態変更、用語の重複定義 |
| `mtqg format [ファイル]` | イベント行を含むテキストを読める形にする（4.6） |
| `mtqg undo` | 直前のケアレスミスをなかったことにする（4.5） |
| `mtqg archive <開始>..<終了> [-n]` | 期間を指定して、終わったものを普段の視界から外す（4.7、設計§9.1） |
| `mtqg init` / `mtqg version` | 初期化、バージョン（mtqg本体と、リポジトリのデータ形式の両方を表示） |
| `mtqg upgrade` | データ形式を上げる（設計§5.6）。形式v2が出るまで作らない |

### 種類名の短縮

種類名は1文字に略せる。**動詞は常に必要**（省略しない）。規則はこれ1つだけで、例外は作らない。

種類ごとの動詞は`add`・`done`・`reopen`・`list`の4語だけ（`edit`・`delete`は種類なし）。

| 正式 | 短縮 |
|---|---|
| `mtqg memo add <本文>` | `mtqg m add <本文>` |
| `mtqg todo done <id>` | `mtqg t done <id>` |
| `mtqg qa add <質問>` | `mtqg q add <質問>` |
| `mtqg glossary add <用語> <定義>` | `mtqg g add <用語> <定義>` |

さらに短くしたい場合は、シェルのaliasで対応する（`alias mm='mtqg m add'`）。

### 共通のオプション

| オプション | 内容 |
|---|---|
| `-C <パス>` | そのパスから`.mtqg/`を探す（gitの`-C`と同じ。設計§4.4） |
| `--json` | すべてのコマンドで機械可読の出力 |
| `--all` | 一覧で、終わったものも含める |
| `-`（本文の代わり） | 標準入力から読む |
| 本文なしで実行 | `$EDITOR`が開く |

## 3. 登録のしかた

```
mtqg m add エラーメッセージは英語で統一する
mtqg t add ブロックコメントの読み飛ばし
mtqg q add ブロックコメントの入れ子に対応する？
mtqg g add トークン 字句解析で切り出す最小単位
```

- 残りの引数を**連結**する。引用符は要らない
- シェルの特殊文字（`#` `*` `(` `)` `&` `|` `<` `>`）は引用符が要る。日本語主体なら困る場面は少ないが、注意書きとして案内する
- `-`を渡すと標準入力から読む（`git log -1 --format=%s | mtqg m add -`）
- 本文なしで実行すると`$EDITOR`が開く（長い記録、複数行向け）
- 出力は作られた記録のIDのみ（`a7f3c2-19`）。速さを邪魔しない

## 4. qaの扱い

> **bugも同じ形**（2026-09-21に追加）。以下の質問・回答・状態・IDの規則は、`bug`と返信にそのまま当てはまる（質問→バグ、回答→返信）。違いは、何について書くかだけ。`q add`の最初の引数の規則（4.5の周辺、`docs/design/history.md`）も`b add`に同じく適用する。`--json`と`context`を決めるStep 5より前に種類を揃えるため、Step 4.5として足した。

### 4.1 回答は「親を持つmemo」

回答は、構造を持たない本文に**親（質問）への参照**が付いたもの。回答にも独自のIDを振る。

- 独自の構造を持つのは、**質問のほう**（開いている／閉じたという状態を持ち、回答をぶら下げる）
- 回答にIDがあるので、`edit`も`delete`も他の種類と同じ規則で指せる（`--answer`のような特別扱いが要らない）
- **親を持てるのは「質問に対する回答」だけ**。回答への回答（入れ子）は許さない。memoやtodoにも親は持たせない
  - 「ToDoに補足を書きたい」等がサンプルPJで繰り返し出たら、そのとき広げる（データ形式は`re`を持つ記録が増えるだけなので後から広げられる）

### 4.2 IDが指すもの

| ID | できること |
|---|---|
| 質問のID | `add`（回答を足す）、`done`、`reopen`、`mtqg edit`（質問文）、`mtqg delete`（回答も一緒に） |
| 回答のID | `mtqg edit`（回答）、`mtqg delete`（その回答だけ） |

**deleteの範囲**：

- **質問を消すと、ぶら下がる回答も表示から消える**。回答だけ残っても意味が通らないため。他の人やAIが書いた回答も含まれるので、そのことを表示で知らせる

```
$ mtqg delete b21c09-7
Deleted: "ブロックコメントの入れ子に対応する？"
2 answers are also hidden (claude-code, yamada)
They remain in git history
```

- **回答を消すと、その回答だけが消える**。質問のクローズ状態は変えない。結果として「回答がないままクローズ」になることはあるが、それは4.3の「答えずに終了」と同じ状態なので問題ない

### 4.3 状態（質問ごと）

「回答があるか」と「終わったか」は別の軸なので、4通りある。

| 状態 | 回答 | クローズ | `qa list`の既定 |
|---|---|---|---|
| 未回答 | 0件 | 開 | 表示 |
| 回答あり・確定待ち | 1件以上 | 開 | 表示（回答の件数を添える） |
| 回答済み | 1件以上 | 閉 | `--all` |
| 答えずに終了（自己解決、不要になった） | 0件 | 閉 | `--all` |

- 「回答を足す」と「終わらせる」は**別の操作**にした。`add … --done`のような同時指定は置かない（一貫性を優先）
- AIが暫定で答え、人間の確定を待つ状態（回答あり・確定待ち）を表せる。回答者が人間かAIかは記録者で分かる（設計§5.2）

### 4.4 回答が複数あるとき

- 追記だけなので、回答は何件でも並ぶ。上書きしない
- `qa list`は最新の回答1件と件数、`show`は全件を時系列で表示する
- 互いに知らずに別々の回答を書いた場合を`review`で「並行した回答」として出すかは、サンプルPJで判断する（9章の食い違い検出と同じ考え方）

### 4.5 undo：直前のケアレスミスをなかったことにする

**要件**：打ち間違いによる意味のない記録を、なかったことにしたい。

よく起きそうな例：

```
mtqg q add 初版では非対応。需要が出たら再検討
```

回答のつもりが、質問IDを入れ忘れたために**新しい質問**として登録されてしまう。コマンドとしては正しいのでエラーにならず、`qa list`に未回答として並び続け、`context`にも入ってAIを混乱させる。

- 対象は、**意味のない直前のミス**。記録としての価値がないもの
- `delete`（削除の事実を追記し、跡が残る）とは別物として扱う。打ち間違いの跡は誰の役にも立たない
- 何を取り消したかを表示する

**方式：同じ端末から書いた最後の行を消す**

追記だけの設計なので、**その行を取れば直前の状態に戻る**。`add`でも`done`でも`edit`でも`delete`でも、同じ方法で戻せる。打ち消しのための新しい`op`は作らない（読み取り側に「deleteとundoの違い」を持ち込まないため）。

- 戻すのは**直前に実行したmtqgのコマンド1回ぶん**。連続undoはしない
- 対象は**イベントファイルの中で、自分の記録元IDと、今の端末と同じ端末識別子を持つ最後の行**
- **コミット済みかどうかは見ない**。ケアレスミスをコミットしてしまった場合は`delete`を使う
- 共有済み（pushして他のブランチに取り込まれた）の行を消すと、次のunionマージで戻ってくることがある（設計§7.4）。共有後は`delete`を使う
- 何を取り消したかを表示する。意図と違うものが消えたら、その場で気づける

**なぜ「ファイルの末尾」ではなく「同じ端末の最後の行」か**

同じworktreeで、人間のCLIとAIエージェントのMCPが同時に記録するのが普通の使い方（設計§11.2）。単に末尾を消すと、**打ち間違いを取り消したつもりでAIが書いた記録を消してしまう**。しかも誰も気づかない。

**端末識別子（`tty`）**

記録時刻や記録元IDと同じく、**自動で付ける付帯情報**（設計§5.5）。

```
tty = hash(tty のパス)[:8]     tty が取れなければ省く
```

- 同じターミナルで実行すれば同じ値、別のタブ・別のウィンドウなら別の値になる
- 生のttyパスではなくハッシュ化した短い値にする。他人には意味を持たず、同一性の判定だけできる（記録はコミットされ、他の人にも見えるため）
- MCPサーバー、CI、環境によってはエディタの統合ターミナルなど、ttyが取れない場合は**値なし**。その場合は「値なしの行」どうしを同じ端末として扱う

**精度を上げる案（誤爆が起きてから検討する）**：

- シェルのプロセスID・起動時刻を混ぜる（ターミナルを閉じて開き直したとき、同じtty番号が再利用される場合に効く）
- 環境変数（`MTQG_TTY`）があればそれを優先する。シェルの設定で作ってもらう

```
$ mtqg q add 初版では非対応。需要が出たら再検討
b21c09-20
$ mtqg undo
Undone: qa add "初版では非対応。需要が出たら再検討" (b21c09-20)
```

**未決（サンプルPJで判断する）**：

- 端末識別子をttyのパスだけで足りるか（誤爆が起きるか）
- 取り消す記録に後続のイベントがある場合（書いたtodoをAIがすぐ完了にした等）に断るか

**決定（2026-09-21、段階1 Step 6。理由は`history.md`）**：

- 断るのは、`create`の行を消すと他のイベントが記録のないまま残るときだけ。`status`・`edit`・`delete`の行は、後に何があっても消す
- 端末識別子は、端末のデバイス番号のハッシュ（標準入力・出力・エラー出力の順で最初の端末）。`MTQG_TTY`があれば優先する。Windowsと端末のないときは値なし。「最後の行」は、`ts`が最後、同じ秒ならファイルの中で最後
- 誤爆が実際に起きるかは、引き続きサンプルPJで判断する

### 4.6 format：生のイベント行を読める形にする

`.mtqg/`は普通のテキストとしてコミットされるので、`git show`やPRの差分には**jsonlの生の行**が並ぶ（設計§11.5）。読み書きの主役はそれでよいが、手元で確認するときは整形したい。

```
$ git show 3f9a1c0 | mtqg format
todo  a7f3c2-6   ブロックコメント /* */ の読み飛ばし   claude-code  10:18
qa    b21c09-7   ブロックコメントの入れ子に対応する？   claude-code  09:10
answer b21c09-9  初版では非対応。需要が出たら再検討     yamada       09:41
done  a7f3c2-3   行コメント // の読み飛ばし            yamada       10:15
```

**時刻順の1つの表にまとまる**

イベントは1ファイル（`.mtqg/journal.jsonl`）に追記されるが、unionマージは行の順序を保証しない（設計§7.4）。`format`は渡されたテキストからイベント行を拾い、**時刻順に並べ直して1つの表にする**ので、ファイル内の行順に関係なく時系列で読める。時刻はここでローカル時間に直す。

```
$ git show 3f9a1c0 | mtqg format
10:18  todo  a7f3c2-6   ブロックコメント /* */ の読み飛ばし   claude-code
10:32  memo  a7f3c2-19  エラーメッセージは英語で統一する方針   yamada
11:05  qa    b21c09-13  エラー位置は行と列の両方を出しますか？  claude-code
11:32  todo  b21c09-18  コメント処理のテストケースを追加      claude-code
```

（GitHub等のPR画面では生のJSONのまま見える。そこは割り切る。経緯が入っていることが分かり、本文を拾い読みできれば足りる）

**方式：テキストの中からイベント行を拾って整形する**

- 行頭の`+`や`-`は取り除いてから読む（unified diffは、gitに限らず`diff -u`やホスティングサービスのAPIでも使われる共通の形式）
- **JSONとして読めない行は黙って飛ばす**。gitのヘッダ（`commit`／`Author`／`Date`）もコードの差分も自動的に落ちるので、パスを絞らずに丸ごと渡せる
- git固有の形式には依存しない。設定で変わりうる部分（コミットのヘッダの体裁など）を当てにしない

| 入力の部分 | 性質 | `format`の扱い |
|---|---|---|
| `commit`／`Author`／`Date` | git固有・設定で変わる | 当てにしない（読めたら区切りに使う程度） |
| `diff --git`、`@@` | unified diff＋git拡張 | 飛ばす |
| `+`／`-`で始まる行 | unified diff（共通） | 記号を外して中身を読む |
| JSONでない行 | — | 飛ばす |

**どこからでも渡せる**

```
git show 3f9a1c0 | mtqg format          あるコミットの差分
git diff | mtqg format                   まだコミットしていない分
git diff main...feature | mtqg format    ブランチ間・PRの範囲
cat .mtqg/journal.jsonl | mtqg format   生のjsonl
grep コメント .mtqg/journal.jsonl | mtqg format   grepの結果
mtqg format .mtqg/journal.jsonl    ファイルを直接
```

grepやjqの結果を流し込めるので、`search`（本文の部分一致だけ・10.3）より凝った検索をしたい場合の逃げ道にもなる。

**`+`／`-`の記号**

- **既定では出さない**。mtqgは追記だけなので、差分を渡すとほぼ全行が`+`になり、記号はノイズにしかならない
- **消えた行があるときだけ明示する**。`undo`や履歴の書き換えでしか現れないため、見逃したくない
- `--mark`で常に記号を出せるようにする

### 4.7 archive：期間の指定

```
$ mtqg archive 2021-01-01..2024-09-18
$ mtqg archive 2021..2023
$ mtqg archive 202404..2024-09 -n
```

期間は、**`<開始>..<終了>`を1つの引数**で書く。gitの範囲指定（`main..feature`）と同じ形。オプション（`--from`／`--to`）にはしない。

**解釈のルール**

1. **`.`が2つ以上続く部分**で、開始と終了に分ける（`..`でも`.....`でもよい）。**`..`は必須**で、ない場合はエラー
2. それぞれから**`-`を全部取り除く**（`-`はあってもなくてもよく、位置も問わない）
3. 残った数字の**桁数**で単位を決める：8桁なら年月日、6桁なら年月、4桁なら年
4. **左右は同じ単位でなければエラー**
5. 年・年月の場合、開始側はその期間の最初の日、終了側は最後の日と解釈する。両端を含む。日付はローカル時間

```
2021-01-01..2024-09-18    → 2021-01-01..2024-09-18
20210101....20240918      → 2021-01-01..2024-09-18
2021-0101..202409-18      → 2021-01-01..2024-09-18
2021..2023                → 2021-01-01..2023-12-31
202404..2024-09           → 2024-04-01..2024-09-30
2023..2023                → 2023-01-01..2023-12-31（1年分）
```

**エラーにするもの**

- `..`がない（`2023`だけ、など）
- 桁数が8・6・4以外
- 左右の単位が違う（`2021..2024-09`など）
- 存在しない日付（`20240231`など）
- 開始が終了より後
- 数字・`-`・`.`以外の文字が入っている

**解釈した結果を必ず表示する**

入力を寛容にする分、実行時の表示の先頭で、どう解釈したかを正規化した形で見せる。

```
$ mtqg archive 2021-0101..202409-18
Range: 2021-01-01..2024-09-18
Archived: 412 memos, 138 todos, 57 questions -> .mtqg/archive/2021-01-01..2024-09-18.jsonl
```

- ファイル名は、どう指定しても`YYYY-MM-DD..YYYY-MM-DD`の正規化した形。同じ期間なら同じファイルになる
- **`-n`**（`--dry-run`）を付けると、移さずに同じ表示だけを出す。意図と違う解釈に実行前に気づける
- 「2年前」のような相対的な指定は持たない。実行した日で意味が変わる指定より、ファイル名と同じ絶対の日付のほうが後から見て分かりやすい

### context

**目的**：AIがセッション開始時に最初に読むもの（11.3のフックから自動で呼ばれる）。**AIが次の記録を正しく作るための前提**を渡す。目的は次の3つ。

1. 前回までの経緯を引き継ぐ。**目的の1つは、AIが勝手に同じ議論を繰り返したり、すでに決まったことを蒸し返したりしないようにすること**。「何が決まったか」だけでなく「何が未決か」を前面に出す
2. 今やるべきこと、答えるべきことを渡す
3. 用語の合意を渡して、言葉の食い違いを防ぐ

**README・CLAUDE.md等との役割分担**：プロジェクトの説明、現在の仕様、ビルドやテストの手順は`context`に入れない。それらは**永続的な知識**で、READMEや指示ファイルが持つもの。`context`が持つのは**そこに至る議論（成果物に残らない過程）**。混ぜると「READMEにはUTF-8対応、contextにはUTF-16を検討中」のような食い違いが起き、AIが混乱する。

**冒頭の「読み方の指示」**

決定事項を別区画にせず、**受け取ったAIに判断させる**。決定かどうかは意味の判断であり、AIが得意なこと。書く側に「これは決定か」を分類させると記録の摩擦が増えるため、データモデルもタグも増やさない。

決定だけを抽出しない利点もある。決定を区画として切り出すと、それが**強い決定なのか、暫定なのか、単なる提案なのか**が失われる。qaの回答とmemoをそのまま渡し、文脈ごとAIに読ませるほうが正確（設計§5.1で決定理由をmemoに含めた判断と同じ）。

**区画の順番と理由**

| 順 | 区画 | 理由 |
|---|---|---|
| 1 | 注意 | 行動が必要なもの |
| 2 | 未完了のToDo | 今やること。最も削りたくない |
| 3 | 未クローズの質問 | 勝手に決めさせないための情報 |
| 4 | 最近の記録 | 直前の流れ。種別（memo/glossary/qa回答）だけ示し、分類はAIに任せる |
| 5 | 用語 | 必要なときに参照する辞書的な位置 |

**書き方の方針**

- Markdownの見出しと箇条書き。AIが構造を読み取りやすく、人間が見ても分かる
- **IDを必ず添える**。AIがそのまま`show`や`done`に使える
- 記録者と時刻を添える。誰の判断か、いつのことかで重みが変わる
- 本文は1行に収める。長いものは切り詰めて`show`に誘導する
- **省略は「(7 more; see mtqg log)」のように件数と見る方法を書く**。`...`だけにしない
- 食い違いは**対象の名前まで書く**（「2 definitions」だけでなく「Glossary term "ブロックコメント" has conflicting definitions」）
- 「未コミット」は主語を明示する（コードの変更と誤読されるため）
- **空の区画は出さない**

**分量と削り方**

- 既定は**2000トークン程度**。毎セッションの先頭に入り、圧縮のたびに入り直すため、これ以上は重い。`--max-tokens`で変えられる
- 上限を超えたら次の順に削る：**最近の記録**（10件→5件→3件→0件）→ **用語**（定義文を落として用語名だけ→用語ごと）→ **質問の回答本文** → **古い質問**
- **ToDoは削らない**。それでも超える場合だけ件数を減らし、「(N more)」と書く
- 削ったら取りに行ける形にする。**全部を渡そうとせず、AIが自分で掘れるようにする**

**`--json`のとき**

区画ごとの配列と、削られたかどうか、全体の件数を返す。VSCode拡張や他の道具は、これを使って自分で表示を作る。

**未決**：冒頭の指示文は毎回100〜150トークンほど使う。外せるオプション（`--no-guide`）を用意するかは要検討。構成全体はサンプルPJで実際にAIに読ませて直す（設計§12.3）。

## 6. IDの指定

- 完全形は`<記録元ID>-<連番>`（例：`a7f3c2-19`）
- **前方一致の短縮を許す**（gitのコミットハッシュと同じ）。`a7f-19`、一意なら`19`でもよい
- 曖昧なときは候補を出してエラーにする
- 種類に合わない操作（`mtqg qa done`をtodoのIDに、`mtqg todo done`をqaのIDに等）はエラーにし、正しいコマンドを案内する

## 7. データの形（設計§7.1に対応）

`.mtqg/journal.jsonl`（1ファイル）に1行1イベントで追記する。合流はunionマージ（設計§7.4）。

アーカイブした項目の行は`.mtqg/archive/<開始>..<終了>.jsonl`に移る（設計§9.1）。どちらも同じ形式で、戻すときは`journal.jsonl`の末尾に結合するだけでよい。mtqgのコマンドは`archive/`を読まない（読みたいときは`mtqg format`）。読み取り側は中身が完全に一致する行を1つとして扱う。

```jsonl
{"id":"b21c09-7","op":"create","type":"qa","status":"open","text":"ブロックコメントの入れ子に対応する？","v":1,"ts":"…Z","origin":"b21c09","author":{"kind":"ai","name":"claude-code"}}
{"id":"b21c09-9","op":"create","type":"qa","re":"b21c09-7","text":"初版では非対応。需要が出たら再検討","v":1,"ts":"…Z","origin":"b21c09","author":{"kind":"human","name":"yamada"}}
{"id":"b21c09-7","op":"status","from":"open","status":"done","v":1,"ts":"…Z","origin":"a7f3c2","author":{"kind":"human","name":"yamada"}}
```

| コマンド | `op` | 主なフィールド |
|---|---|---|
| `memo add` / `todo add` / `qa add <質問>` / `glossary add` | `create` | `type`、`text`（glossaryは`word`＋`text`）、todoとqaの質問は`status:"open"` |
| `qa add <質問id> <回答>` | `create` | `type:"qa"`、`re`（親の質問id）、`text` |
| `done` / `reopen` | `status` | `from`、`status` |
| `edit` | `edit` | `text`（どの種類でも） |
| `delete` | `delete` | （なし） |

- `re`があれば回答、なければ質問
- 書き出し規則は設計§7.2。キーの順は`id, op, type, re, from, status, word, text, at, v, ts, origin, author, tty`で固定、値がないフィールドは省く、全行を改行で終える
- **時刻（`ts`）はUTCで持つ**（`"2026-09-17T01:32:00Z"`）。文字列の並びがそのまま時系列になり、比較が単純。**表示のときに各自のロケールの時間へ直す**
- 書き込みは1行を1回で追記。採番はカウンタをロックしてから（設計§10.4）
- 衝突マーカーが残っていたら、読み込み時は警告し、書き込みは断る（設計§7.4）
- 書く前に`.mtqg/version`を読み、**宣言された形式で書く**。知らない番号なら読み書きとも断る（設計§5.6）
- 各行の`v`には、宣言された形式の番号を入れる

## 8. 設定

なるべく持たない。

| 項目 | 既定 | 決め方 |
|---|---|---|
| 記録者の名前 | `git config user.name` | 自動（設計§5.2） |
| 記録者の種別 | `human` | MCPからはAI（設計§11.2） |
| エディタ | `$EDITOR` | 環境変数 |
| 表示の色 | 端末が対応していれば付ける | `--no-color`、`NO_COLOR` |

設定ファイル（`.mtqg/config`等）は、必要性が出るまで作らない。

`mtqg init`がすること：

- **どこで実行しても**、カレントディレクトリから上にたどる（設計§4.4）。`.git`に当たったら、その隣（リポジトリのルート）に作る。途中で`.mtqg/`に当たったらエラー（「すでにあります：<パス>」）。gitリポジトリの外ならエラー

- `.mtqg/journal.jsonl`、`.mtqg/.gitattributes`（`*.jsonl text eol=lf merge=union`）、`.mtqg/version`、`.mtqg/SCHEMA.md`を作る
- `version`には、そのmtqgが扱える最新の形式の番号を書く。以降は`mtqg upgrade`するまで変わらない
- `<git-dir>/mtqg/origin-id`に記録元IDを発行する（設計§6.3）
- **gitの設定には触らない。コミットもしない**（設計§4.3）。「`.mtqg/`をコミットしてください」と案内するだけ

`.mtqg/`が見つからないとき（他のコマンド）：

```
$ mtqg t add コメント処理のテストを足す
No .mtqg/ found. Run `mtqg init` (will be created at /home/me/sample-parser)
```

- 読むコマンドでも書くコマンドでも自動では作らない。案内だけする
- 作成先（`.git`のあるディレクトリ）を表示し、どこに作られるかをinitの前に分かるようにする
- （`mtqg init --agent`は段階4以降。既存の`.mtqg/`があっても動く別の用途なので、そのときに扱いを決める）

v0.1のCLIに**入れないもの**（設計§12.2の段階4以降）：`mtqg mcp`、`mtqg hook`、`mtqg init --agent`。

## 9. 作る順番（段階1の中の順序）

最初から、ジャーナル層・モデル層・CLIの層を分けて書く（設計§10.7）。1の段階で、ジャーナル層の読み込み・追記と、`.mtqg/`の探索・ロック・カウンタが揃う。以降はモデル層とCLIの層を足していく。

| 順 | 入れるもの | ねらい |
|---|---|---|
| 1 | `init`、`m add`、`t add`、`t done`、`t list`、`status` | **これだけでGoogle Keepの代わりになる**。ここから自分で使い始められる |
| 2 | `q add`／`done`／`reopen`／`list`、`g add`／`list`、`show`、`log` | 4種類が揃う |
| 3 | `context`、全コマンドの`--json` | AIに渡せる。サンプルPJでAIにも使わせる |
| 4 | `edit`、`delete`、`undo`、`search`、`review`、`format` | 直す・消す・取り消す・探す・食い違いを見る・差分を読む |
| 5 | `archive` | 長く使い始めてから要る。サンプルPJでは期間を短くして試す |
| 6 | シェル補完 | 動的（`mtqg completion <shell>`が固定のスクリプトを出し、候補は`mtqg candidates`が`args.go`の表から計算する）。bash・zsh・fish・PowerShell。文法を2か所に持たない（設計§11.1と同じ考え方）。仕様は`docs/reference/cli.md`、判断は`docs/design/history.md` |

1が動いた時点でサンプルPJを始められる。
