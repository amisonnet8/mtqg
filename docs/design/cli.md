# mtqg 設計：CLI

> 今の設計と、その判断の理由。**現在の仕様は `docs/reference/cli.md` が正**であり、食い違う場合は reference に従う。

本文中の「CLI設計§N」と括弧内の番号（4.5など）はこの文書の節を指す。「設計§N」は、他の設計文書の節を指す。

種類は6つ（memo・todo・qa・bug・glossary・rule）。qaについての記述（4章など）は、bugにもそのまま当てはまる（質問→バグ、回答→返信）。ruleは構造がmemoと同じ（設計§5.1）。

前提となる原則（設計文書より）：

- 追記するだけ。版管理はgitに任せる（設計§2.3）／gitの運用には何も要求しない（設計§4.3）
- 使う側には「管理してくれている」ように見せる（設計§2.4）
- 記録作成は手厚くアシストし、読む側は必要な分だけ（設計§5.4）
- **一番残したいのは「作業に取り掛かるときの気づき」**。書き込みの速さが最優先

---

## 1. 設計の方針

| 方針 | 理由 |
|---|---|
| 体系は`mtqg <種類> <動詞>`で統一する | 種類ごとにできることが違う（qaにdone、memoにdoneがない等）ので、コマンドも種類で分ける |
| **動詞は6語に絞る** | 種類ごとに違う単語を覚えるのが面倒。`ask`→`add`、`answer`→`add`、`close`→`done`に寄せた |
| 登録は**引用符なしの1行**で書ける | 気づきは数秒で消える。`"`を打つ手間すら惜しい |
| 種類名は**1文字に略せる**（`m`/`t`/`q`/`b`/`g`/`r`） | 体系は崩さず、入力だけ短くする。例外規則は作らない |
| 読む側は**人間向け表示と`--json`の二重化** | 補助ツールは`--json`を使う（設計§10.5） |
| gitには**触らない** | コミットもpushもしない（設計§4.3） |

覚える動詞は`add`・`done`・`reopen`・`list`・`edit`・`delete`の**6語だけ**。
うち`add`・`list`・`edit`・`delete`はすべての種類に共通で、`done`・`reopen`だけが状態を持つtodo・qa・bugにある。

## 2. コマンド全体

| | memo (m) | todo (t) | qa (q) | bug (b) | glossary (g) | rule (r) |
|---|---|---|---|---|---|---|
| **add**（登録） | `add <本文>` | `add <本文>` | `add <質問>` | `add <バグ>` | `add <用語> <定義>` | `add <本文>` |
| **add**（回答・返信） | — | — | `add <質問id> <回答>` | `add <バグid> <返信>` | — | — |
| **done** | — | `done <id>` | `done <質問id>` | `done <バグid>` | — | — |
| **reopen** | — | `reopen <id>` | `reopen <質問id>` | `reopen <バグid>` | — | — |
| **list** | 全件 | 未完了（`--all`で全件） | 未クローズ（`--all`で全件） | 未クローズ（`--all`で全件） | 全件 | 全件 |

`edit`と`delete`は、どの種類でも「IDを渡して本文を直す／消す」だけで違いがないため、**種類なしのコマンド**にした（下記）。種類が要るのは「書くとき」と「見るとき」だけで、IDがあるなら種類は要らない。

### 種類をまたぐコマンド

| コマンド | 内容 |
|---|---|
| `mtqg edit <id> <本文>` | 記録を直す（glossaryは定義を直す。用語名は変えられない） |
| `mtqg delete <id>` | 記録を消す（表示から除外。gitの履歴には残る） |
| `mtqg status` | 概況と、未コミットの記録の件数 |
| `mtqg log [--limit N] [--kind K]` | すべての種類を時系列（新しい順）で束ねて見る |
| `mtqg show <id>` | 1件の詳細とイベント履歴 |
| `mtqg search <語>` | 本文の部分一致 |
| `mtqg context [--max-tokens N]` | AI・フック向けの要約（設計§11.3） |
| `mtqg review` | 並行した変更、用語の重複定義、親のない回答・返信 |
| `mtqg format [ファイル]` | イベント行を含むテキストを読める形にする（4.6） |
| `mtqg undo` | 直前のケアレスミスをなかったことにする（4.5） |
| `mtqg archive <開始>..<終了> [-n]` | 期間を指定して、終わったものを普段の視界から外す（4.7、設計§9.1） |
| `mtqg init` / `mtqg version` | 初期化、バージョン（mtqg本体と、リポジトリのデータ形式の両方を表示） |
| `mtqg upgrade [-n]` | データ形式を上げる。SCHEMA.mdが古ければ書き直す（設計§5.6、11.4） |
| `mtqg init --agent <agent>` / `mtqg hook <agent> <event>` / `mtqg mcp` | AIエージェントとの連携（設計§11.2、11.3） |
| `mtqg completion <shell>` / `mtqg candidates` | シェル補完（9章） |

### 種類名の短縮

種類名は1文字に略せる。**動詞は常に必要**（省略しない）。規則はこれ1つだけで、例外は作らない。

| 正式 | 短縮 |
|---|---|
| `mtqg memo add <本文>` | `mtqg m add <本文>` |
| `mtqg todo done <id>` | `mtqg t done <id>` |
| `mtqg qa add <質問>` | `mtqg q add <質問>` |
| `mtqg glossary add <用語> <定義>` | `mtqg g add <用語> <定義>` |

さらに短くしたい場合は、シェルのaliasで対応する（`alias mm='mtqg m add'`）。

### 共通のオプション

| オプション | 内容 |
|---|---|
| `-C <パス>` | そのパスから`.mtqg/`を探す（gitの`-C`と同じ。設計§4.4） |
| `--json` | すべてのコマンドで機械可読の出力（`mtqg hook`・`mtqg mcp`を除く） |
| `--all` | 一覧で、終わったものも含める |
| `--full-id` | IDを完全な32桁で表示する（人間向けの表示だけ） |
| `--no-color` | 色を付けない（`NO_COLOR`も同じ） |
| `-`（本文の代わり） | 標準入力から読む |
| 本文なしで実行 | `$EDITOR`が開く |

## 3. 登録のしかた

```
mtqg m add エラーメッセージは英語で統一する
mtqg t add ブロックコメントの読み飛ばし
mtqg q add ブロックコメントの入れ子に対応する？
mtqg g add トークン 字句解析で切り出す最小単位
```

- 残りの引数を**連結**する。引用符は要らない
- シェルの特殊文字（`#` `*` `(` `)` `&` `|` `<` `>`）は引用符が要る。日本語主体なら困る場面は少ないが、注意書きとして案内する
- `-`を渡すと標準入力から読む（`git log -1 --format=%s | mtqg m add -`）
- 書く本文がないと`$EDITOR`が開く（長い記録、複数行向け。`edit`は今の本文を入れて開く）。開く前に、IDが記録に当てはまることを確かめる（長い本文を書いてから断らない）
- 出力は作られた記録のIDのみ（`81e74ef5e8`）。速さを邪魔しない

## 4. qaの扱い

以下の質問・回答・状態・IDの規則は、`bug`と返信にそのまま当てはまる（質問→バグ、回答→返信）。違いは、何について書くかだけ。qaとbugの解釈はモデル層の1か所にまとめ、種類ごとに分けない。

### 4.1 回答は「親を持つmemo」

回答は、構造を持たない本文に**親（質問）への参照**（`re`）が付いたもの。回答にも独自のIDを振る。

- 独自の構造を持つのは、**質問のほう**（開いている／閉じたという状態を持ち、回答をぶら下げる）
- 回答にIDがあるので、`edit`も`delete`も他の種類と同じ規則で指せる（`--answer`のような特別扱いが要らない）
- **親を持てるのは「質問に対する回答」と「バグに対する返信」だけ**。回答への回答（入れ子）は許さない。memoやtodoにも親は持たせない
  - 「ToDoに補足を書きたい」等が繰り返し出たら、そのとき広げる（データ形式は`re`を持つ記録が増えるだけなので後から広げられる）
- **返信は親と同じ`type`を持つ。** `qa`の`re`は質問、`bug`の`re`はバグを指す。別の`type`を指す`re`（他のツールが書いたもの）は、返信として結び付けず、エラーにもしない。どの親の下にも出ず、`review`が「親のない回答・返信」として見せる。`show`は、`re`の先が無いときは「そういう記録は無い」、別の種類のときは「それはバグでなく質問だ」のように言い、親の種類を言い切らない

### 4.2 IDが指すもの

| ID | できること |
|---|---|
| 質問のID | `add`（回答を足す）、`done`、`reopen`、`mtqg edit`（質問文）、`mtqg delete`（回答も一緒に） |
| 回答のID | `mtqg edit`（回答）、`mtqg delete`（その回答だけ） |

**`q add`は、最初の引数だけで質問と回答を見分ける。** 引数の数では分けられない（質問も回答も「先頭の語＋残り」の同じ形で、残りは連結する）。

- 最初の引数が16進数の4桁以上だけでできていれば回答先のID、そうでなければ全体が質問の本文
- **IDの形なのに当てはまる記録がなければ、質問にせずエラーにして、質問にしたいなら全体を引用符で括るよう案内する。** 黙って新しい質問ができる事故（下の4.5の例）を、そもそも起こさないため。引用符で括ると中に空白が入り、16進数だけでなくなるので、それが逃げ道（`--`は、後ろの語が別の引数のままなので逃げ道にならない）。英語の質問が`Face`・`Dead`のような16進の語で始まると止まる代償は受け入れる
- `b add`も同じ規則。判定は1か所のコードで、種類ごとに実装を分けない
- **種類を取り違えたIDはエラーにし、正しいコマンドがあれば案内する**（`b add <質問id>`、`q add <バグid>`、返信への返信、`q done <バグid>`など）。`journal.jsonl`には何も書かない

**deleteの範囲**：

- **質問を消すと、ぶら下がる回答も表示から消える**。回答だけ残っても意味が通らないため。他の人やAIが書いた回答も含まれるので、そのことを表示で知らせる

```
$ mtqg delete 9a7c41e0b5
Deleted: "ブロックコメントの入れ子に対応する？"
2 answers are also hidden (claude-code, yamada)
They remain in git history
```

- **回答を消すと、その回答だけが消える**。質問のクローズ状態は変えない。結果として「回答がないままクローズ」になることはあるが、それは4.3の「答えずに終了」と同じ状態なので問題ない

### 4.3 状態（質問ごと）

「回答があるか」と「終わったか」は別の軸なので、4通りある。

| 状態 | 回答 | クローズ | `qa list`の既定 |
|---|---|---|---|
| 未回答 | 0件 | 開 | 表示 |
| 回答あり・確定待ち | 1件以上 | 開 | 表示（回答の件数を添える） |
| 回答済み | 1件以上 | 閉 | `--all` |
| 答えずに終了（自己解決、不要になった） | 0件 | 閉 | `--all` |

- 「回答を足す」と「終わらせる」は**別の操作**にした。`add … --done`のような同時指定は置かない（一貫性を優先）
- AIが暫定で答え、人間の確定を待つ状態（回答あり・確定待ち）を表せる。回答者が人間かAIかは記録者で分かる（設計§5.2）
- 状態は一覧の末尾の列に言葉で書く（`unanswered`、`2 answers, awaiting confirmation`など）。色だけで意味を伝えない

### 4.4 回答が複数あるとき

- 追記だけなので、回答は何件でも並ぶ。上書きしない
- `qa list`は最新の回答1件と件数、`show`は全件を時系列で表示する
- 互いに知らずに別々の回答を書いた場合を`review`で「並行した回答」として出すかは、未決（10章）

### 4.5 undo：直前のケアレスミスをなかったことにする

**要件**：打ち間違いによる意味のない記録を、なかったことにしたい。

よく起きそうな例：

```
mtqg q add 初版では非対応。需要が出たら再検討
```

回答のつもりが、質問IDを入れ忘れたために**新しい質問**として登録されてしまう。コマンドとしては正しいのでエラーにならず、`qa list`に未回答として並び続け、`context`にも入ってAIを混乱させる。

- 対象は、**意味のない直前のミス**。記録としての価値がないもの
- `delete`（削除の事実を追記し、跡が残る）とは別物として扱う。打ち間違いの跡は誰の役にも立たない
- 何を取り消したか（種類、したこと、本文、ID）を必ず表示する。意図と違うものが消えたら、その場で気づける

**方式：同じ記録者・同じ端末から書いた最後の行を消す**

追記だけの設計なので、**その行を取れば直前の状態に戻る**。`add`でも`done`でも`edit`でも`delete`でも、同じ方法で戻せる。打ち消しのための新しい`op`は作らない（読み取り側に「deleteとundoの違い」を持ち込まないため）。

- 戻すのは**直前に実行したmtqgのコマンド1回ぶん**。連続undoはしない
- 対象は、**今の記録者と、今の端末と同じ端末識別子（`tty`）を持つ行のうち、最後のもの**
- 「最後」は、`ts`が最後のもの、**同じ秒ならファイルの中で最後に書かれたもの**。`id`はランダムなので、同じ秒の並びに`id`を使うと、1秒以内に2回書いて`undo`したときに、どちらが消えるか決まらない。追記はロックの中で順に書かれるので、同じ秒の中ではファイルの順が実際の順に一番近い。時計の進んだ機械が書いた行は、時刻が追いつくまで「最新」になる（消したものは必ず表示するので、取り違えは見える）
- **同じ内容の行が複数あれば、すべて消す。** 読み込みは同じ内容の行を1つのイベントとして扱うので、1つだけ消しても取り消したことにならない
- **断るのは、`create`の行を消すと、他のイベントが記録のないまま残るときだけ**（その記録への状態変更・`edit`・`delete`、またはその質問・バグへの回答・返信）。断るときは何も書かず、いくつあるかを言い、`delete`を案内する。`status`・`edit`・`delete`の行は、後に何があっても消す（消しても読み方が壊れないため）。「後続があれば必ず断る」と、`status`の取り消しのような、消しても壊れない場面まで断ってしまう
- **コミット済みかどうかは見ない**。ケアレスミスをコミットしてしまった場合は`delete`を使う
- 共有済み（pushして他のブランチに取り込まれた）の行を消すと、次のunionマージで戻ってくることがある（設計§7.4）。共有後は`delete`を使う

**なぜ「ファイルの末尾」ではなく「同じ記録者・同じ端末の最後の行」か**

同じworktreeで、人間のCLIとAIエージェントのMCPが同時に記録するのが普通の使い方（設計§11.2）。単に末尾を消すと、**打ち間違いを取り消したつもりでAIが書いた記録を消してしまう**。しかも誰も気づかない。

**端末識別子（`tty`）**

記録時刻と同じく、**自動で付ける付帯情報**（設計§5.5）。端末のデバイス番号か`MTQG_TTY`のsha256の先頭8桁で、標準入力・標準出力・標準エラー出力の順で最初に端末のものを使う。Windowsと、どれも端末でないとき（パイプ越しのAI、MCPサーバー、CI）は値なしで、値なしの行どうしは同じ端末として扱う。

- 同じターミナルで実行すれば同じ値、別のタブ・別のウィンドウなら別の値になる。パイプ越しに書くAIエージェントと、端末で書く人は別の端末になる
- 生の値ではなくハッシュ化した短い値にする。他人には意味を持たず、同一性の判定だけできる（記録はコミットされ、他の人にも見えるため）
- `MTQG_TTY`は、端末を作り分ける逃げ道（デバイス番号は再利用されるので、記録者が同じだと前の端末の行が対象になりうる）であり、本物のバイナリのテストで端末を作り分けるためにも要る

```
$ mtqg q add 初版では非対応。需要が出たら再検討
f19a4c7e26
$ mtqg undo
Undone: qa add "初版では非対応。需要が出たら再検討" (f19a4c7e26)
```

### 4.6 format：生のイベント行を読める形にする

`.mtqg/`は普通のテキストとしてコミットされるので、`git show`やPRの差分には**jsonlの生の行**が並ぶ（設計§11.5）。読み書きの主役はそれでよいが、手元で確認するときは整形したい。`format`は`.mtqg/`を要らない。

**時刻順の1つの表にまとまる**

イベントは1ファイル（`.mtqg/journal.jsonl`）に追記されるが、unionマージは行の順序を保証しない（設計§7.4）。`format`は渡されたテキストからイベント行を拾い、**時刻順に並べ直して1つの表にする**ので、ファイル内の行順に関係なく時系列で読める。時刻はここでローカル時間に直し、日付も付ける（任意の期間の差分を渡すため）。

```
$ git show 3f9a1c0 | mtqg format
2026-09-17 10:18  todo      3f1c9a2b7e  ブロックコメント /* */ の読み飛ばし   claude-code
2026-09-17 10:32  memo      0e6d3b9f58  エラーメッセージは英語で統一する方針   yamada
2026-09-17 11:05  question  6e9b3d1f42  エラー位置は行と列の両方を出しますか？  claude-code
2026-09-17 11:20  done      7f2b9e4a10  行コメント // の読み飛ばし            yamada
```

- 種類の列は、作成の行だけ種類（`question`・`answer`・`bug`・`reply`など）を書き、それ以外の行は`done`・`reopen`・`edit`・`delete`を書く（状態の変更・編集・削除の行には、種類が書かれていない）

（GitHub等のPR画面では生のJSONのまま見える。そこは割り切る。経緯が入っていることが分かり、本文を拾い読みできれば足りる）

**方式：テキストの中からイベント行を拾って整形する**

- 行頭の`+`や`-`は取り除いてから読む（unified diffは、gitに限らず`diff -u`やホスティングサービスのAPIでも使われる共通の形式）
- **JSONとして読めない行は黙って飛ばす**。gitのヘッダ（`commit`／`Author`／`Date`）もコードの差分も自動的に落ちるので、パスを絞らずに丸ごと渡せる
- git固有の形式には依存しない。設定で変わりうる部分（コミットのヘッダの体裁など）を当てにしない
- **diffの変更なしの行（先頭が空白）は表に出さない。** `git show`のhunkは変更の前後に文脈の行を付けるので、出すと「そのコミットで書かれていない行」が混ざる。ただし、同じ入力にある記録の状態変更・削除に本文を貸す（状態変更だけのコミットでも、近くに作成の行があれば、何についての変更か分かる）。素の`journal.jsonl`の行は先頭に空白がないので、影響を受けない

| 入力の部分 | 性質 | `format`の扱い |
|---|---|---|
| `commit`／`Author`／`Date` | git固有・設定で変わる | 当てにしない |
| `diff --git`、`@@` | unified diff＋git拡張 | 飛ばす |
| `+`／`-`で始まる行 | unified diff（共通） | 記号を外して中身を読む |
| 先頭が空白の行 | unified diffの文脈 | 表に出さず、本文を貸すだけ |
| JSONでない行 | — | 飛ばす |

**どこからでも渡せる**

```
git show 3f9a1c0 | mtqg format          あるコミットの差分
git diff | mtqg format                   まだコミットしていない分
git diff main...feature | mtqg format    ブランチ間・PRの範囲
cat .mtqg/journal.jsonl | mtqg format   生のjsonl
grep コメント .mtqg/journal.jsonl | mtqg format   grepの結果
mtqg format .mtqg/journal.jsonl    ファイルを直接
```

grepやjqの結果を流し込めるので、`search`（本文の部分一致だけ・設計§10.3）より凝った検索をしたい場合の逃げ道にもなる。アーカイブのファイルも、これで読む（mtqgの他のコマンドは`archive/`を読まない）。

**`+`／`-`の記号**

- **既定では出さない**。mtqgは追記だけなので、差分を渡すとほぼ全行が`+`になり、記号はノイズにしかならない
- **消えた行があるときだけ明示する**。`undo`や履歴の書き換えでしか現れないため、見逃したくない
- `--mark`で常に記号を出せるようにする

### 4.7 archive：期間の指定

```
$ mtqg archive 2021-01-01..2024-09-18
$ mtqg archive 2021..2023
$ mtqg archive 202404..2024-09 -n
```

期間は、**`<開始>..<終了>`を1つの引数**で書く。gitの範囲指定（`main..feature`）と同じ形。オプション（`--from`／`--to`）にはしない。

**解釈のルール**

1. **`.`が2つ以上続く部分**で、開始と終了に分ける（`..`でも`.....`でもよい）。**`..`は必須**で、ない場合はエラー
2. それぞれから**`-`を全部取り除く**（`-`はあってもなくてもよく、位置も問わない）
3. 残った数字の**桁数**で単位を決める：8桁なら年月日、6桁なら年月、4桁なら年
4. **左右は同じ単位でなければエラー**
5. 年・年月の場合、開始側はその期間の最初の日、終了側は最後の日と解釈する。両端を含む。日付はローカル時間

```
2021-01-01..2024-09-18    → 2021-01-01..2024-09-18
20210101....20240918      → 2021-01-01..2024-09-18
2021-0101..202409-18      → 2021-01-01..2024-09-18
2021..2023                → 2021-01-01..2023-12-31
202404..2024-09           → 2024-04-01..2024-09-30
2023..2023                → 2023-01-01..2023-12-31（1年分）
```

**エラーにするもの**（コマンドラインの誤りとして終了コード2）

- `..`がない（`2023`だけ、など）
- 桁数が8・6・4以外
- 左右の単位が違う（`2021..2024-09`など）
- 存在しない日付（`20240231`など）
- 開始が終了より後
- 数字・`-`・`.`以外の文字が入っている

**解釈した結果を必ず表示する**

入力を寛容にする分、実行時の表示の先頭で、どう解釈したかを正規化した形で見せる。

```
$ mtqg archive 2021-0101..202409-18
Range: 2021-01-01..2024-09-18
Archived: 412 memos, 138 todos, 57 questions, 61 answers -> .mtqg/archive/2021-01-01..2024-09-18.jsonl
Skipped: 3 open todos, 1 open question, 24 glossary entries
```

- ファイル名は、どう指定しても`YYYY-MM-DD..YYYY-MM-DD`の正規化した形。同じ期間なら同じファイルになる
- `Archived:`の行には回答・返信の件数も出す（移った行がすべて数に表れる）。何も移さないときは`Archived: nothing`で、ファイルは作らない
- **`-n`**（`--dry-run`）を付けると、何も書かずに、1行目の終わりに`(dry run)`を付けて同じ表示を出す。意図と違う解釈に実行前に気づける。「同じ表示」だけだと、移したのか移す予定なのか見分けがつかない
- 「2年前」のような相対的な指定は持たない。実行した日で意味が変わる指定より、ファイル名と同じ絶対の日付のほうが後から見て分かりやすい
- `--json`は件数だけを返す（移した記録の一覧は出さない。数百件の規模でも出力が小さく、中身は`format`で読める）

## 5. 出力の形

**表示の言語は英語**（設計§10.6）。mtqg自身が出す文言（エラー、案内、見出し、列名、結果の表示、`--help`）は英語で、利用者が書いた記録の中身は書いたときの言語のまま表示する。「枠は英語、中身は日本語」になる。実際の出力例は`docs/reference/cli.md`にあり、テストが実際に動かして確かめている。ここでは形を決めた理由を書く。

**人間向けの表示**

- IDは先頭10桁（`--full-id`で32桁）。時刻はローカル時間で、今日なら`HH:MM`、それ以前は日付
- 端末に出すときだけ、端末の幅に合わせて本文を`...`で切る。パイプやファイルには切らずに出す（AIが読む出力から情報を落とさない）。桁は表示の幅で揃える（全角は2列）
- 記録に含まれる制御文字は`U+FFFD`に置き換える。他人の記録（cloneしたリポジトリの`journal.jsonl`）に端末のエスケープシーケンスが入っていると、一覧が端末の動作を変えてしまうため
- `show`は本文を全文で出す（端末でも切らない）。切るのは一覧・`log`の1行の本文だけ
- 色は端末が対応していれば付けるが、**色だけで意味を伝えない**

**`--json`**

- **常にJSONオブジェクト1つで、最初のフィールドが`command`。** 素の配列にすると、件数などの付帯情報を足す場所がなくなり、後からフィールドを足すと形が変わってしまう。読む側は知らないフィールドを無視する約束にして、変えるのは足すことだけにする（VSCode拡張が別リポジトリでも、本体と拡張を同時に更新しなくて済む）。版つきの封筒（`{"v":..,"data":..}`）は、1段深くなるだけなので採らない
- **IDは常に完全な32桁、時刻はUTC、本文は書かれたまま。** `--full-id`・色・端末の幅・制御文字の置き換えは、人間の画面のための加工なので、機械には持ち込まない（制御文字はJSONのエスケープに任せる）
- **エラーと警告も、標準エラー出力に1行のJSON**（`kind`で機械が見分け、`message`は人間向けと同じ文言）。標準出力にJSONで返すと、パイプの相手が「成功した結果」と読み違えやすい

### context

**目的**：AIがセッション開始時に最初に読むもの（設計§11.3のフックから自動で呼ばれる）。**AIが次の記録を正しく作るための前提**を渡す。目的は次の3つ。

1. 前回までの経緯を引き継ぐ。**目的の1つは、AIが勝手に同じ議論を繰り返したり、すでに決まったことを蒸し返したりしないようにすること**。「何が決まったか」だけでなく「何が未決か」を前面に出す
2. 今やるべきこと、答えるべきことを渡す
3. 用語の合意を渡して、言葉の食い違いを防ぐ

**README・CLAUDE.md等との役割分担**：プロジェクトの説明、現在の仕様、ビルドやテストの手順は`context`に入れない。それらは**永続的な知識**で、READMEや指示ファイルが持つもの。`context`が持つのは**そこに至る議論（成果物に残らない過程）**。混ぜると「READMEにはUTF-8対応、contextにはUTF-16を検討中」のような食い違いが起き、AIが混乱する。

**冒頭の「読み方の指示」と、決定の扱い**

決定事項を推測で抜き出して別区画にせず、**受け取ったAIに判断させる**。決定かどうかは意味の判断であり、AIが得意なこと。決定を区画として切り出すと、それが**強い決定なのか、暫定なのか、単なる提案なのか**が失われる。qaの回答とmemoをそのまま渡し、文脈ごとAIに読ませるほうが正確（設計§5.1で決定理由をmemoに含めた判断と同じ）。

例外は**rule**で、書いた人が「この先も効き続ける、読めば従える決まり事」として種類を選んだものなので、Rules区画に全文で出し、冒頭の指示で従うよう伝える。mtqgがmemoから決まり事を推測することはしない。

**区画の順番と理由**

| 順 | 区画 | 理由 |
|---|---|---|
| 1 | Attention | 行動が必要なもの（用語の重複定義、並行した変更、未コミットの記録） |
| 2 | Rules | 従う決まり事。削らず、本文も切らない（設計§5.1） |
| 3 | Open todos | 今やること |
| 4 | Open questions | 勝手に決めさせないための情報 |
| 5 | Open bugs | 対処すべき不具合 |
| 6 | Recent records | 直前の流れ。種類だけ示し、分類はAIに任せる |
| 7 | Glossary | 必要なときに参照する辞書的な位置 |

**書き方の方針**

- Markdownの見出しと箇条書き。AIが構造を読み取りやすく、人間が見ても分かる
- **IDを必ず添える**。AIがそのまま`show`や`done`に使える
- 記録者と時刻を添える。誰の判断か、いつのことかで重みが変わる
- 本文は1行に収める（ruleを除く）。長いものは切り詰めて`show`に誘導する
- **省略は「(7 more; see mtqg log)」のように、その区画の中で件数と見る方法を書く**。`...`だけにしない
- 食い違いは**対象の名前まで書く**（「2 definitions」だけでなく「Glossary term "ブロックコメント" has conflicting definitions」）
- 「未コミット」は主語を明示する（コードの変更と誤読されるため）
- **空の区画は出さない**
- 最初の行のブランチ名は`git branch --show-current`で読む（設計§10.2）

**分量と削り方**

- 既定は**2000トークン程度**。毎セッションの先頭に入り、圧縮のたびに入り直すため、これ以上は重い。`--max-tokens`で変えられる。数え方は文字数からの近似（設計§11.3）
- 削る順序と、最新の3件の質問・bugを削らない理由は設計§11.3。削ったら取りに行ける形にする。**全部を渡そうとせず、AIが自分で掘れるようにする**

**`--json`のとき**

区画ごとの配列と、削られたかどうか、全体の件数を返す。VSCode拡張や他の道具は、これを使って自分で表示を作る。

## 6. IDの指定

- 完全形は16進32桁（UUIDv4からハイフンを除いたもの。設計§6）。表示は先頭10桁
- **4桁以上の前方一致の短縮を許す**（gitのコミットハッシュと同じ。gitの省略ハッシュも最短4桁）。1〜3桁を受け付けないのは、`a`・`add`・`bad`・`be`・`cab`のような英語の語と重なり、4.2の「最初の引数がIDかどうか」の判定で事故になるため
- 曖昧なときは、止まって、候補を**完全なID**で並べる（利用者がそこから好きな長さを写して打ち直せるように）
- 種類に合わない操作（`mtqg qa done`をtodoのIDに、`mtqg todo done`をqaのIDに等）はエラーにし、正しいコマンドを案内する（4.2）

## 7. データの形（設計§7.1に対応）

`.mtqg/journal.jsonl`（1ファイル）に1行1イベントで追記する。合流はunionマージ（設計§7.4）。

アーカイブした項目の行は`.mtqg/archive/<開始>..<終了>.jsonl`に移る（設計§9.1）。どちらも同じ形式で、戻すときは`journal.jsonl`の末尾に結合するだけでよい。mtqgのコマンドは`archive/`を読まない（読みたいときは`mtqg format`）。読み取り側は中身が完全に一致する行を1つとして扱う。

```jsonl
{"id":"9a7c41e0b5d24f6e8a1c3b5d7f9e0a2c","op":"create","type":"qa","status":"open","text":"ブロックコメントの入れ子に対応する？","v":1,"ts":"…Z","author":{"kind":"ai","name":"claude-code"}}
{"id":"4d8e0a6c27b14c9d8e2f4a6b8c0d1e3f","op":"create","type":"qa","re":"9a7c41e0b5d24f6e8a1c3b5d7f9e0a2c","text":"初版では非対応。需要が出たら再検討","v":1,"ts":"…Z","author":{"kind":"human","name":"yamada"}}
{"id":"9a7c41e0b5d24f6e8a1c3b5d7f9e0a2c","op":"status","from":"open","status":"done","basis":2,"v":1,"ts":"…Z","author":{"kind":"human","name":"yamada"}}
```

| コマンド | `op` | 主なフィールド |
|---|---|---|
| `memo add` / `todo add` / `qa add <質問>` / `bug add <バグ>` / `glossary add` / `rule add` | `create` | `type`、`text`（glossaryは`word`＋`text`）、todo・質問・バグは`status:"open"` |
| `qa add <質問id> <回答>` / `bug add <バグid> <返信>` | `create` | 親と同じ`type`、`re`（親のid）、`text` |
| `done` / `reopen` | `status` | `from`、`status`、`basis` |
| `edit` | `edit` | `text`（どの種類でも）、`basis` |
| `delete` | `delete` | （なし） |

- `re`があれば回答・返信、なければ質問・バグ
- 書き出し規則は設計§7.2。キーの順は`id, op, type, re, from, status, basis, word, text, v, ts, author, tty`で固定、値がないフィールドは省く、全行を改行で終える
- **時刻（`ts`）はUTCで持つ**（`"2026-09-17T01:32:00Z"`）。**表示のときに各自のロケールの時間へ直す**
- 書き込みはロックの中で、1行を1回で追記する（設計§10.4）
- 衝突マーカーが残っていたら、読み込み時は警告し、書き込みは断る（設計§7.4）
- 書く前に`.mtqg/version`を読み、**宣言された形式で書く**。知らない番号なら読み書きとも断る（設計§5.6）
- 各行の`v`には、宣言された形式の番号を入れる

## 8. 設定

なるべく持たない。

| 項目 | 既定 | 決め方 |
|---|---|---|
| 記録者の名前 | `git config user.name` | 自動（設計§5.2）。`MTQG_AUTHOR_NAME`で名乗れる |
| 記録者の種別 | `human` | AIはCLIなら`MTQG_AUTHOR_KIND=ai`で名乗る。MCPからは常にAI（設計§5.2、11.2） |
| エディタ | `$EDITOR` | 環境変数。空なら`nano` |
| 表示の色 | 端末が対応していれば付ける | `--no-color`、`NO_COLOR` |

設定ファイル（`.mtqg/config`等）は持たない。

`mtqg init`がすること：

- **どこで実行しても**、カレントディレクトリから上にたどる（設計§4.4）。`.git`に当たったら、その隣（リポジトリのルート）に作る。途中で`.mtqg/`に当たったらエラー（「すでにあります：<パス>」）。gitリポジトリの外ならエラー
- `.mtqg/journal.jsonl`、`.mtqg/.gitattributes`（`*.jsonl text eol=lf merge=union`）、`.mtqg/.gitignore`（`.local/`）、`.mtqg/version`、`.mtqg/SCHEMA.md`を作る
- `version`には、そのmtqgが扱える最新の形式の番号を書く。以降は`mtqg upgrade`するまで変わらない
- **gitの設定には触らない。コミットもしない**（設計§4.3）。「`.mtqg/`をコミットしてください」と案内するだけ
- `mtqg init --agent <agent>`は、`.mtqg/`が無ければ作り、あればそのまま使い、エージェントの設定ファイルに書き込む（設計§11.3）。触ったファイルごとに`Created:`・`Updated:`・`Unchanged:`を言う

`.mtqg/`が見つからないとき（他のコマンド）：

```
$ mtqg t add コメント処理のテストを足す
No .mtqg/ found. Run `mtqg init` (will be created at /home/me/sample-parser)
```

- 読むコマンドでも書くコマンドでも自動では作らない。案内だけする
- 作成先（`.git`のあるディレクトリ）を表示し、どこに作られるかをinitの前に分かるようにする

## 9. シェル補完

- **動的にする。** `mtqg completion <shell>`は固定のスクリプトを出すだけで、TABのたびに`mtqg candidates`へ「次に何が来られるか」を聞く。静的（表をスクリプトに焼き込む）だと、種類・動詞・オプションの文法が、`args.go`の表とスクリプトの2か所にでき、食い違う（解釈は1か所・設計§11.1と同じ考え方）。IDを出せるのも動的だけ（記録を読む必要がある）
- **候補を出すコマンドを隠さない。** 隠しコマンド（`__complete`のような）にせず、`candidates`として`help`と`--json`のコマンド一覧に出し、仕様に書く。隠すと「あるのに文書にない」ものになり、AIや別のツールが「次に何が来られるか」を聞くのにも使えなくなる
- **4つのシェル（bash・zsh・fish・PowerShell）。** mtqgは3つのOSで動くので、PowerShellも入れる
- **IDまで補完する。** `done`は未完了のもの、`reopen`は完了したもの、`show`・`edit`・`delete`は見えている記録すべて、`q add`・`b add`の1語目は質問（バグ）。**本文は補完しない**（何を打つかはmtqgが知らない）。用語（`g add <TAB>`）も補完しない：重複定義を誘い、`review`が食い違いとして見せるものと反対の向きになる
- **1文字の短縮形は候補に出さない。** `t<TAB>`は`todo`になる。短縮形は打つ人のためのもので、補完のあとに残る語は長い形のほうが読める
- **打ちかけの語は`--word=<語>`で渡し、空の引数を渡さない。** 空の引数を落とすシェルがある（fishでは、空のリストを展開した引数が引数ごと消える）。落とされると、「新しい語の先頭で押した」のか「1つ前の語で押した」のかが分からなくなる。`--word=`は、空でも1つの引数として必ず届く
- **`candidates`は何があっても終了コード0で、標準エラー出力に何も出さない。** TABのたびに警告が出ると、打っている行が壊れる。`.mtqg/`が無い・形式が新しすぎる・読めない行がある、は「記録が無い」として扱う。説明は1行にして60桁で切る（`--json`でも。行き先が常にシェルのメニューなので、「本文は書かれたまま」の例外）
- **本物のシェルで確かめる。** シェルごとに単語の扱いが違う（空の語を落とす、`=`で語を切る）ので、スクリプトが行を正しく渡しているかは、本物のシェルでしか分からない（同じ入力を4つのシェルに打たせ、同じ候補が出ることを確かめる）

## 11. VSCode拡張のための読み方

VSCode拡張（別リポジトリ・設計§11.4）は`--json`だけでつながる。拡張の画面のために足した読み方。

### 11.1 `log --json --events`は削除した記録も返す

メモのタイムラインを、Slack・Discordのように「消しても跡が残る」形にするため（設計§11.4）。

- **`delete`は「表示から除外する」という設計の芯（設計§8）は変えない。** `log --events`以外のすべての読み取り（`show`・`search`・各`list`・`--events`無しの`log`）は、削除した記録を見せない。`--events`という「イベント履歴を見たい」という明示的な要求の中でだけ、削除の事実（`op:"delete"`イベント）も一緒に見えるようにする
- **有効にするのは別のフラグでなく`--events`。** 別のフラグ（`--deleted`）にすると、`--events`と組み合わせないと同じ情報にならず、フラグの意味が2つに割れる
- **`deleted:true`は、削除した記録自身だけでなく、削除した質問・バグに属する回答・返信（それ自身は削除されていない）にも付ける。** 「表示から隠れている」という利用者から見た事実を伝えるフィールドなので、隠れている理由（自分が消えたか、親が消えたか）では分けない。その場合、`events`は親の削除イベントを含まない（その記録自体には何も起きていない）
- **`--before`も、`--events`のときだけ削除した記録のIDを受け付ける。** ページの末尾が削除した記録になりうるので、そのIDを次のページの`--before`に渡せないと、ページングが削除の直後で壊れる
- **`deleted`を設定するのは`log`の`--events`の分岐だけ。** 記録をJSONにする共通の関数では設定しない。他のコマンドに`deleted`が漏れないよう、設定する場所を1つに保つ
- **`log --events`は、`show --json`と違い、質問・バグの返信の`create`を含めない。** `show`は1件の記録についての画面なので子（返信）を畳み込む意味があるが、`log`は元から一覧で、返信はその一覧の別の行として既に出ている。畳み込むと件数×返信の走査に近くなり、得られる情報は増えない

### 11.2 `log --before`はカーソル型

- `--limit`を毎回大きくして全件取り直す方式でも動くが、メモのタイムラインのように件数に上限がない種類（設計§11.4）では、既存の件数を毎回数え直さない、本当のインクリメンタル読み込みが要る

### 11.3 成果物の位置は持たない

- 記録時の位置を残す`at`（CLIの`--at`、MCPの`path`・`line`）は、VSCode拡張で実際に使うと「位置に紐付ける」という発想自体が分かりにくかったため、廃止した（設計§5.5）。ファイル名は本文に書く
- 形式のバージョンは上げない。`at`は任意のフィールドで、書かなくなっても既存の読み手が誤読することはなく、「知らないフィールドを無視できる変更では番号を上げない」（設計§5.6）が当てはまる。既存の行の`at`は書き換えず、読むときに無視する

### 11.4 SCHEMA.mdの鮮度マーカー

`docs/reference/schema.md`は、形式を変えずに中身が変わることがある（説明の追記、フィールドの廃止など）。`mtqg upgrade`のSCHEMA.mdの書き換えを形式のバージョンの上昇だけに連動させると、既存のリポジトリの`.mtqg/SCHEMA.md`が古いまま取り残される。そこで、SCHEMA.mdの書き換えを形式のバージョンから切り離し、SCHEMA.md自体に「どのmtqgの版の内容か」を示すマーカー`<!-- schema as of mtqg X.Y.Z -->`を持たせる。

- **`.mtqg/version`を`X.Y.Z`のような形にして鮮度も持たせる案は採らない。** 古いmtqgは、`.mtqg/version`の中身が数字でなければ「形式が新しすぎる」という優雅な拒否ではなくエラーで止まるので、形を変えるだけで既存のバイナリを壊す。`.mtqg/version`は、形式そのものを上げるとき以外、値も形も変えない
- マーカーは`docs/reference/schema.md`のソースに**静的に**書く（Versioning節の末尾）。`.mtqg/SCHEMA.md`は埋め込んだ中身をそのまま書くだけで、マーカーも付いてくる（書くときに作らない）
- コードの側に手で管理する定数（`journal.SchemaVersion`）を置き、**テストでマーカーと定数の一致を確かめる**（`qsoku check`に含まれる）。2つは別々の場所の手書きの値なので、ずれたら落ちるようにする。`schema_ja.md`は埋め込まれないので対象にしない
- `mtqg upgrade`は、既存の`.mtqg/SCHEMA.md`のマーカーが無いか定数より古ければ、SCHEMA.mdだけを書き直す（形式は変えない）。マーカーが新しい場合（新しいmtqgが書いた後、古いmtqgで`upgrade`した場合）は触らない。古いバイナリが新しい文書を巻き戻さないため
- 比べるときは`X.Y.Z`を3つの整数として比べる（文字列で比べると`"1.9.0" < "1.10.0"`が偽になる）
- 何も書く必要が無いとき（形式もSCHEMA.mdの鮮度も変わらない）は、`journal.jsonl`の衝突マーカーを理由に断らない。`upgrade`が衝突マーカーで断るのは、書くものがあるときだけ
