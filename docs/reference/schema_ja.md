# mtqg ジャーナルの形式

*[English](schema.md) | **日本語***

> 英語版 `schema.md` の日本語訳。内容は英語版と同じに保つ。食い違う場合は英語版が正（英語版が `.mtqg/SCHEMA.md` として各プロジェクトに書き出される）。

この文書は、mtqgが記録をどう保存するかを定める。英語版は、`mtqg init`が各プロジェクトに書き出す`.mtqg/SCHEMA.md`の元であり、mtqgのコマンドがなくても、人やAIが記録を読めるようにするためのもの。

**形式のバージョン：0（未確定）。** mtqg v1までは、形式が予告なく変わることがあり、既存の行が書き換え・変換されることがある。形式1以降は、[バージョン](#バージョン)の互換性のルールが適用される。

## mtqgが記録するもの

mtqgは、プロジェクトの過程のうち、コードに残らない部分を残す。作業中の気づき、やること、質問とその答え、合意した用語、この先も効き続ける決まり事。記録には6つの種類がある。

| 種類 | 意味 | 状態 |
|---|---|---|
| `memo` | 自由なメモ。決定、発見、理由、引き継ぎ | なし |
| `todo` | やること | `open` / `done` |
| `qa` | 質問、または質問への回答 | 質問：`open` / `done`、回答：なし |
| `bug` | 不具合の報告、およびそれについてのやり取り（返信） | バグ：`open` / `done`、返信：なし |
| `glossary` | 用語（`word`）とその定義（`text`） | なし |
| `rule` | 従うべき決まり事。編集・削除するまで効き続ける | なし |

`qa`と`bug`は同じ形をしている：返信を付けられる記録と、その返信。違いは、何について書くかだけ。バグは、直ったとき、またはもう追わないときに`done`になる。

版の管理はgitに任せる。mtqgは行を**追記するだけ**で、変更・回答・訂正・削除も、すべて新しい行で表す。

## ファイル

```
.mtqg/
  .gitattributes     *.jsonl text eol=lf merge=union
  .gitignore         .local/
  version            このディレクトリの形式のバージョン（整数1つと改行）
  SCHEMA.md          この文書（英語版）
  journal.jsonl      現在のすべてのイベント
  archive/           mtqg archive で視界から外したイベント
    2021-01-01..2024-09-18.jsonl
  .local/            このマシンだけの一時的なファイル（コミットされない）
```

- `.local/`以外のすべてのファイルは、普通のファイルとしてgitにコミットされる
- `journal.jsonl`は、普段の視界にあるすべてのイベントを持つ
- `archive/<開始>..<終了>.jsonl`は、その期間でアーカイブされた項目のイベントを持つ（開始と終了を含む、ローカルの日付、常に`YYYY-MM-DD`の形で書く）。mtqgのコマンドは`archive/`を読まない
- `.local/`は、このマシンでだけ意味を持つもの（書き込みのロック、書き直しに使う一時ファイルなど）を置く。gitに無視され（`.mtqg/.gitignore`）、他の読み手が必要とするものは何もなく、mtqgが動いていないときはいつ消してもよい

## 行の形式

- JSON Lines：**1行に1イベント**、各行が1つのJSONオブジェクト
- UTF-8（BOMなし）。改行はLF。**最後の行も含め、すべての行がLFで終わる**
- 本文中の改行は`\n`とエスケープされる。1イベントが複数行にまたがることはない

例：

```jsonl
{"id":"6b0d549b6f03475a8600a35a099950d8","op":"create","type":"todo","status":"open","text":"C言語対応やりたい","v":0,"ts":"2026-09-17T00:00:00Z","author":{"kind":"human","name":"yamada"}}
{"id":"1012f037b64c44228c38fb2918f135d2","op":"create","type":"qa","status":"open","text":"ブロックコメントの入れ子に対応する？","v":0,"ts":"2026-09-17T00:10:00Z","author":{"kind":"ai","name":"claude-code"}}
{"id":"95e761d177314f10b06bf2efc6f87718","op":"create","type":"qa","re":"1012f037b64c44228c38fb2918f135d2","text":"初版では非対応。需要が出たら再検討","v":0,"ts":"2026-09-17T00:41:00Z","author":{"kind":"human","name":"yamada"},"tty":"3e9a0b12"}
{"id":"7f3a2b1c09d84e6fa5b17c2d3e4f5a60","op":"create","type":"bug","status":"open","text":"空の入力でパーサーが落ちる","v":0,"ts":"2026-09-17T00:50:00Z","author":{"kind":"human","name":"yamada"}}
{"id":"f28c105d1fb14c2390c192cfd3ac94af","op":"create","type":"glossary","word":"トークン","text":"字句解析で切り出す最小単位","v":0,"ts":"2026-09-17T01:00:00Z","author":{"kind":"human","name":"yamada"}}
{"id":"3d8e4a0b12c94f77b6a08d1e5f2c9b34","op":"create","type":"bug","re":"7f3a2b1c09d84e6fa5b17c2d3e4f5a60","text":"macOSでも再現した。空のファイルには最初のトークンがない","v":0,"ts":"2026-09-17T01:20:00Z","author":{"kind":"ai","name":"claude-code"}}
{"id":"6b0d549b6f03475a8600a35a099950d8","op":"status","from":"open","status":"done","v":0,"ts":"2026-09-17T01:30:00Z","author":{"kind":"ai","name":"claude-code"}}
```

## フィールド

| フィールド | 型 | 現れる場所 | 意味 |
|---|---|---|---|
| `id` | 文字列 | すべて | イベントが対象とする記録のID（[ID](#id)を参照） |
| `op` | 文字列 | すべて | `create`、`status`、`edit`、`delete`のいずれか |
| `type` | 文字列 | `create` | `memo`、`todo`、`qa`、`bug`、`glossary`、`rule`のいずれか |
| `re` | 文字列 | 回答・返信の`create` | この記録が返信する先の記録のID。この記録と同じ`type`を持つ |
| `from` | 文字列 | `status` | 変更前の状態（書いた側から見えていたもの） |
| `status` | 文字列 | todo・質問・バグの`create`、`status` | イベント後の状態（`open`または`done`） |
| `basis` | 整数 | `status`、`edit`（省略可） | その記録が持っていたイベントの数（`create`を含む）。書いた側が、このイベントを書く直前に見ていたもの。同じ記録への、知らないうちの変更を見分けるのに使う（下記） |
| `word` | 文字列 | glossaryの`create` | 用語 |
| `text` | 文字列 | `create`、`edit` | 本文。glossaryでは定義 |
| `at` | オブジェクト | 任意 | プロジェクトのどこについて書いたか（下記） |
| `v` | 整数 | すべて | その行を書いたときの形式のバージョン |
| `ts` | 文字列 | すべて | イベントの時刻。UTC、`Z`付きのRFC 3339（`2026-09-17T01:32:00Z`） |
| `author` | オブジェクト | すべて | 内容に責任を持つ者：`{"kind": "human" \| "ai", "name": 文字列}` |
| `tty` | 文字列 | 任意 | その行を書いた端末を見分ける短いハッシュ |

値がないフィールドは**省く**。`null`とは書かない。

`at`は書いた時点の事実を記録するもので、コードが変わっても更新されない。

```json
"at": {"path": "docs/spec.md", "line": 42, "head": "3f9a1c0"}
```

`author.kind`は、内容に責任を持つ者の種別。人間の決定をAIが書き留めた場合、記録者は人間になる（本文に、AIが代わりに書いたことを書く）。

## 操作

| `op` | 意味 | フィールド |
|---|---|---|
| `create` | 新しい記録 | `type`、`text`。glossaryは`word`、todoと質問とバグは`status:"open"`、回答と返信は`re` |
| `status` | todo・質問・バグの状態の変更 | `from`、`status`、`basis` |
| `edit` | 本文の置き換え | `text`、`basis` |
| `delete` | 記録を隠す | なし |

- `re`を持つ`qa`の記録は**回答**、持たないものは**質問**。`re`を持つ`bug`の記録は**返信**、持たないものは**バグ**。回答と返信に返信は付けられない。`re`を持つのは回答と返信だけ
- **返信は、返信先の記録と同じ`type`を持つ**：`qa`の記録の`re`は質問のID、`bug`の記録の`re`はバグのID。`re`が別の`type`の記録を指している記録は、その記録への返信ではない
- `edit`が置き換えるのは`text`だけ。glossaryの`word`は変えられない
- `delete`は記録を普段の表示から隠す。質問やバグを削除すると、その回答や返信も隠れる。行はファイルにもgitの履歴にも残る

## ID

- 記録のIDは、ランダムなUUID（バージョン4）を**ハイフンを除いた小文字の16進32桁**で書いたもの（例：`81e74ef5e8e24d949ed904759531985d`）
- IDは記録を作るとき（`op:"create"`）に決まり、その記録についての後のイベントはすべて同じ`id`を持つ
- クローン・ブランチ・マシンの間で、IDのために調整する必要はない
- ツールは通常、先頭の10桁（`81e74ef5e8`）だけを表示し、入力には一意に決まる前方一致を受け付ける。保存するデータは常に完全なIDを使うので、短い前方一致が後から曖昧になっても、参照（`re`）は正確なまま

## 読み方：現在の状態の組み立て

1. `journal.jsonl`を1行ずつ読む。空行は無視する。次のどれかに当てはまる行は、警告を出して飛ばす：正しいJSONオブジェクトでない、不正なUTF-8を含む、`id`か`op`が無い
2. 中身が完全に一致する行は、1つのイベントとして扱う
3. イベントを`ts`で並べ、同じ`ts`なら`id`で並べる。**ファイル内の行の順序に依存しない。** マシン間の時計のずれで順序が入れ替わることはあり、それは許容する
4. その順で、`id`ごとにイベントを適用する。`create`で記録が始まり、`status`で状態が決まり、`edit`で本文が置き換わり、`delete`で隠れる。時刻がその記録の`create`より前のイベント（書いた側の時計が遅れている）も、無視せずに数える：`create`の後に、ほかの変更と順に適用する。`create`のない`id`のイベントは無視する
5. 知らないフィールドは無視する

イベントの重複はエラーではない。同じ状態の変更が複数回あっても、結果は同じになる。

**並行した変更は、エラーではなく事実として扱う。** 1つの記録に対する2つの`status`イベントが、同じ`from`から別々に（たとえば2つのブランチで）書かれた場合、両方を残してそのまま見せる。mtqgはどちらが正しいかを決めない。同様に、同じ`word`を持つ2つのglossaryの記録も、両方を残して並べて見せる。`basis`（下記）は、`status`イベントでも`edit`でも、同じ場面を同じように捉える。2つの変更が同じフィールドを変えていなくても検知できる。

## マージ

`.mtqg/.gitattributes`は、`*.jsonl`に`merge=union`を指定している。2つのブランチがどちらも行を追記した場合、gitは両側の行を残す。イベントは追記されるだけで、読み取り側は行の順序に依存しないので、両側を残すことは常に正しい。

### journal.jsonlの衝突を解決する

`.gitattributes`のマージ指定を使わないマージもある（たとえばWeb画面でのマージ）。その場合、`journal.jsonl`に通常の衝突マーカーが入ることがある。解決の方法：

- **両側の行をすべて残す。** マーカーの行（`<<<<<<<`、`=======`、`>>>>>>>`）だけを消す
- **どちらか一方を選ばない。** 一方を選ぶと記録が消える
- 行の順序は問わない

衝突マーカーが残っている間、mtqgは読むときに警告し、書き込みを断る。

### 戻ってくる行

`mtqg undo`は行を1つ消し、`mtqg archive`は行を`archive/`に移す。それらの行がすでに他のブランチに取り込まれていると、後のunionマージで`journal.jsonl`に戻ってくることがある。中身が同じ行は1つのイベントとして扱われ（上記）、戻ってきたアーカイブ済みの項目は視界に戻るだけなので、もう一度アーカイブすればよい。また、他のブランチがそのすぐ隣の行を変えていた場合にも戻ってくる。たとえば2つのブランチが、`journal.jsonl`で隣り合う行をそれぞれアーカイブしたとき、マージ後は両方の行が`journal.jsonl`にあり、移した側のブランチのアーカイブのファイルにもあるので、失われる行はない。

## アーカイブ

`mtqg archive <開始>..<終了>`は、**最後のイベント**がその期間（ローカルの日付、両端を含む）に入る項目の行を、`journal.jsonl`から`archive/<開始>..<終了>.jsonl`に移す。どの項目が移るかは種類で決まる。

| 種類 | アーカイブされる条件 |
|---|---|
| `todo` | 状態が`done` |
| `qa`の質問 | 状態が`done`。回答も一緒に移る |
| `bug` | 状態が`done`。返信も一緒に移る |
| `memo` | 常に |
| `glossary` | されない |
| `rule` | されない |

- **質問・バグの最後のイベントは、自分のイベントと、回答・返信のイベント（削除したものを含む）のうち一番新しいもの。** 2023年に閉じた質問に2025年に回答が付いていたら、2023年までの期間ではアーカイブされない。移る行がすべて期間内の日付になるようにするため
- **削除した記録は、種類も状態も問わずアーカイブされる**（最後のイベント、つまり`delete`かそれより後のものが期間に入るとき）。すでに視界から外れているため
- 回答・返信は、その質問・バグが`journal.jsonl`にあれば、それに従う。ないもの（`re`が何も指さない、または別の`type`の記録を指す）は、memoと同じく1つの項目として扱う
- 1つの項目の行は、すべて一緒に、バイト列のまま移る。読めない行と、`create`が`journal.jsonl`にない`id`のイベントは、移らずに残る
- アーカイブのファイルは、入れる行があるときに作る。同じ期間をもう一度アーカイブすると追記する。行は`journal.jsonl`と同じくLFで終わる

戻すときは、アーカイブのファイルを`journal.jsonl`の末尾に結合して消す。

```
cat .mtqg/archive/2021-01-01..2024-09-18.jsonl >> .mtqg/journal.jsonl
rm .mtqg/archive/2021-01-01..2024-09-18.jsonl
```

## バージョン

- `.mtqg/version`は、ディレクトリの形式を整数1つで宣言する
- 自分の知る番号より新しい`version`を見た読み手は、**読むのも書くのも断らなければならない**
- 書き手は、より新しい形式を知っていても、`version`が宣言する形式で書く。形式を上げるのは明示的な格上げのときだけで、そのとき`version`と`SCHEMA.md`を同時に書き換える。既存の行は書き換えない
- 各行は、書いたときの形式`v`を持つ。読み手は各行をその行の`v`で解釈する
- 古い読み手が無視しても読み違えないフィールドの追加では、バージョンを変えない。フィールドの意味の変更や、新しい`op`の追加では変える
- 形式`0`は「まだ確定していない」ことを意味する。mtqg v1のリリース時に`1`になり、形式0で書かれた記録はそのとき一度だけ変換される

## 書き出し規則

イベントを書くツールは、差分が読みやすく、同じイベントが同じ行になるよう、mtqgと同じ形で行を書くこと。

- 詰めたJSON。トークンの間に空白を入れない
- キーはこの順。ないものは省く：
  `id, op, type, re, from, status, basis, word, text, at, v, ts, author, tty`
  `author`の中は`kind, name`
- ASCII以外の文字をエスケープしない。`<`、`>`、`&`もエスケープしない
- すべての行をLFで終える
- 追記だけ。1行全体を1回の書き込みで書く

読み手は、キーの順序・空白・エスケープの違いを問わず、正しいJSONであれば受け付けなければならない。キー名は大文字と小文字を区別する。1行の中で同じキーが複数回現れたら、最後の値を使う。
